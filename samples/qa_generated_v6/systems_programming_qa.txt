Q: What is the typical memory layout of a process in a Unix-like operating system?
A: A process memory layout consists of several distinct regions arranged from low to high addresses: the text segment containing executable code, the data segment for initialized global variables, the BSS segment for uninitialized globals, the heap growing upward for dynamic allocations, and the stack growing downward for function call frames. Between the heap and stack lies unmapped memory that allows both regions to grow. The kernel reserves the highest addresses for its own mappings, typically above 0xC0000000 on 32-bit systems or in the upper canonical address range on 64-bit systems.

Q: How do stack and heap memory differ in terms of allocation, performance, and use cases?
A: Stack memory uses automatic allocation with a simple pointer adjustment, making it extremely fast but limited in size (typically 1-8 MB) and scope-bound. Heap memory requires explicit allocation through malloc/new, involves complex bookkeeping to track free blocks, and can fragment over time, but offers virtually unlimited size and lifetime independent of function scope. Stack is ideal for local variables and function parameters with known sizes, while heap suits dynamic data structures, large allocations, and objects that must outlive their creating function.

Q: What are calling conventions and why do they matter for systems programming?
A: Calling conventions define the contract between caller and callee functions regarding how arguments are passed (registers vs stack), who saves which registers (caller-saved vs callee-saved), how return values are communicated, and how the stack is cleaned up. Common conventions include cdecl, stdcall, fastcall on x86, and the System V AMD64 ABI which passes the first six integer arguments in RDI, RSI, RDX, RCX, R8, R9. Understanding calling conventions is essential for writing assembly, interfacing with foreign code, debugging crashes, and implementing features like variadic functions or exception handling.

Q: How does a system call transition execution from user space to kernel space?
A: A system call begins when user code places the syscall number in a designated register (RAX on x86-64) and arguments in others, then executes a special instruction like SYSCALL or INT 0x80. This triggers a processor mode switch from ring 3 to ring 0, saves the user context, and jumps to the kernel's syscall entry point via the LSTAR MSR or interrupt descriptor table. The kernel validates arguments, performs the requested operation with elevated privileges, stores the result in RAX, and returns via SYSRET or IRET, restoring user mode and the saved context.

Q: What is memory-mapped I/O and how does it differ from port-mapped I/O?
A: Memory-mapped I/O assigns device registers to addresses in the physical memory space, allowing drivers to read and write hardware using ordinary load/store instructions to specific memory locations. Port-mapped I/O uses a separate address space accessed through special instructions like IN and OUT on x86, requiring different opcodes for device communication. Memory-mapped I/O offers simpler programming, can leverage cache coherency protocols, and allows larger address ranges, while port-mapped I/O provides clear separation between memory and I/O operations but is largely x86-specific and limited to 64K ports.

Q: What is endianness and what problems can arise from endianness mismatches?
A: Endianness describes byte ordering within multi-byte values: big-endian stores the most significant byte at the lowest address, while little-endian stores the least significant byte first. Mismatches cause severe bugs when sharing binary data between systems, reading file formats, or interpreting network protocols (which typically use big-endian "network byte order"). Programmers must use conversion functions like htonl/ntohl, carefully serialize data with explicit byte ordering, or use format-specific readers. x86 and ARM (in default mode) are little-endian, while network protocols, Java class files, and many file formats are big-endian.

Q: Why does data alignment matter and what performance penalties result from misaligned access?
A: Data alignment ensures values are stored at addresses divisible by their size (4-byte integers at addresses divisible by 4). CPUs fetch data in cache-line-sized chunks, and misaligned access can require two fetches when data spans a boundary, doubling memory latency. Some architectures like older ARM or SPARC generate hardware faults on misaligned access rather than handling it transparently. Compilers insert padding in structures to maintain alignment, which is why sizeof may exceed the sum of member sizes. The alignas/alignof keywords and compiler attributes provide explicit control over alignment requirements.

Q: What role does a linker play in the build process and how does it resolve symbols?
A: The linker combines multiple object files and libraries into an executable by resolving symbolic references between compilation units. When one file calls a function defined elsewhere, the compiler generates an undefined symbol; the linker finds the definition in another object file or library and patches the call site with the correct address. Static linking copies library code into the executable, while dynamic linking records dependencies resolved at load time. The linker also assigns final virtual addresses, creates relocation entries for position-independent code, and generates sections like the PLT and GOT for dynamic symbol resolution.

Q: How do shared libraries work and what is the role of the PLT and GOT?
A: Shared libraries are loaded once into memory and mapped into multiple process address spaces, saving RAM and enabling updates without recompilation. The Procedure Linkage Table (PLT) contains stub code for each external function call, initially jumping to the dynamic linker. The Global Offset Table (GOT) holds the actual function addresses, initially pointing to resolver code. On first call, the dynamic linker locates the symbol, updates the GOT entry with the real address, and subsequent calls jump directly through the GOT. This lazy binding defers resolution cost until functions are actually used.

Q: What are Unix signals and how does signal handling affect program execution?
A: Signals are software interrupts delivered to processes for events like SIGINT (Ctrl+C), SIGSEGV (memory fault), or SIGTERM (termination request). When a signal arrives, the kernel interrupts normal execution and invokes the registered handler function, which runs in the process context but with a restricted set of safe operations (async-signal-safe functions only). Signal handlers must be reentrant since they can interrupt any code, including malloc or printf, making non-local jumps or complex logic dangerous. The sigaction interface provides fine control over signal masking, handler flags, and signal information delivery.

Q: What is epoll and how does it improve upon select/poll for handling many concurrent connections?
A: Epoll is a Linux-specific I/O event notification mechanism that scales to thousands of connections efficiently. Unlike select/poll which require passing the entire file descriptor set on each call (O(n) overhead), epoll maintains the set in kernel space: epoll_create makes an instance, epoll_ctl adds/removes descriptors, and epoll_wait returns only the ready ones. This edge-triggered or level-triggered interface avoids scanning inactive connections. Epoll achieves O(1) notification for active descriptors regardless of total count, making it essential for high-performance servers like nginx and Node.js.

Q: How does kqueue differ from epoll and what additional capabilities does it provide?
A: Kqueue is the BSD equivalent of epoll, available on macOS, FreeBSD, and related systems, offering a unified interface for multiple event types beyond just I/O. A single kqueue instance can monitor file descriptor readiness, file system changes (vnode events), process lifecycle events, signals, and timers using the same kevent structure. The kevent call both modifies the subscription list and retrieves events atomically. This unified model simplifies event loop implementations compared to combining epoll with inotify and signalfd, though it sacrifices some of epoll's edge-case tuning options.

Q: What is the difference between static and dynamic linking, and what are the tradeoffs?
A: Static linking incorporates all library code directly into the executable at build time, producing a self-contained binary that runs without external dependencies but consumes more disk space and memory. Dynamic linking stores references resolved at runtime by the dynamic loader, enabling smaller executables, shared memory for common libraries, and security updates without recompilation. However, dynamic linking introduces DLL hell / dependency conflicts, startup latency from symbol resolution, and potential ABI breakage between library versions. Systems programming often favors static linking for deployment simplicity in containers or embedded systems.

Q: How does the loader prepare a dynamically linked executable for execution?
A: When the kernel exec's a dynamically linked program, it maps the executable and transfers control to the dynamic loader (ld-linux.so) specified in the PT_INTERP header. The loader parses the executable's dynamic section to find required libraries, recursively loads them via mmap, resolves symbol references by searching library symbol tables, applies relocations to patch code and data with resolved addresses, and executes initialization functions (.init and .ctors sections). Only after this setup completes does the loader jump to the program's entry point, with the GOT and PLT configured for lazy or immediate binding.

Q: What memory protection mechanisms does the operating system provide and how do they prevent common vulnerabilities?
A: The OS enforces page-level permissions (read, write, execute) via hardware MMU, preventing code execution on stack/heap (NX/DEP) and writes to code sections. Address Space Layout Randomization (ASLR) randomizes stack, heap, library, and executable base addresses, making return-oriented programming harder. Stack canaries detect buffer overflows before return, and guard pages between stack frames catch overflows into adjacent stacks. Modern systems add Control Flow Integrity (CFI), pointer authentication (ARM PAC), and shadow stacks to thwart sophisticated attacks bypassing older protections.
