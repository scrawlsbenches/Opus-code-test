Q: What are the six architectural constraints that define a RESTful API?
A: REST (Representational State Transfer) is defined by six architectural constraints: client-server separation, statelessness, cacheability, uniform interface, layered system, and optional code-on-demand. Client-server separation means the client and server evolve independently. Statelessness requires that each request contains all information needed to process it, with no session state stored on the server. Cacheability allows responses to be marked as cacheable or non-cacheable to improve performance. The uniform interface constraint standardizes how resources are identified and manipulated through URIs and standard HTTP methods. Layered systems allow intermediary servers like load balancers and caches without clients knowing. These constraints work together to create scalable, maintainable, and loosely coupled systems.

Q: How does GraphQL differ from REST, and when should you choose one over the other?
A: GraphQL and REST represent fundamentally different approaches to API design. REST uses multiple endpoints with fixed data structures, while GraphQL provides a single endpoint where clients specify exactly what data they need through queries. GraphQL eliminates over-fetching (getting more data than needed) and under-fetching (requiring multiple requests to get all needed data) problems common in REST APIs. Choose REST when you have simple, predictable data requirements, need aggressive caching, or want to leverage existing HTTP infrastructure. Choose GraphQL when clients have diverse data needs, you want to reduce round trips for complex data requirements, or you need strong typing and introspection capabilities. Many modern applications use both: REST for simple CRUD operations and GraphQL for complex data aggregation scenarios.

Q: What are the main differences between authentication and authorization, and how should APIs implement both?
A: Authentication verifies who a user is (identity), while authorization determines what that authenticated user is allowed to do (permissions). Authentication typically involves validating credentials like API keys, JWT tokens, or OAuth access tokens to establish identity. Authorization happens after authentication and involves checking if the authenticated user has permission to access specific resources or perform certain actions. APIs should implement authentication at the gateway or middleware level to validate tokens before processing requests. Authorization can be implemented through role-based access control (RBAC), attribute-based access control (ABAC), or scope-based permissions in OAuth. Best practices include using industry-standard protocols like OAuth 2.0 and OpenID Connect, never storing plain-text credentials, implementing token expiration and refresh mechanisms, and logging all authentication and authorization events for security auditing.

Q: How should APIs implement rate limiting, and what information should be communicated to clients?
A: Rate limiting protects APIs from abuse, ensures fair resource usage, and maintains service availability for all clients. Common strategies include fixed window (X requests per time period), sliding window (smoother distribution), token bucket (allows bursts), and leaky bucket (constant rate) algorithms. APIs should communicate rate limit status through standard HTTP headers: X-RateLimit-Limit (maximum requests allowed), X-RateLimit-Remaining (requests left in current window), X-RateLimit-Reset (when the limit resets), and Retry-After (how long to wait after hitting limits). When limits are exceeded, return a 429 Too Many Requests status code with a clear error message. Consider implementing tiered rate limits based on authentication level, API plan, or endpoint sensitivity. Rate limits should be documented clearly, and clients should be given tools to monitor their usage programmatically.

Q: What are the best practices for API versioning, and what are the tradeoffs of different approaches?
A: API versioning allows you to evolve your API while maintaining backward compatibility for existing clients. The three main approaches are URI versioning (/v1/users), header versioning (Accept: application/vnd.api+json;version=1), and query parameter versioning (/users?version=1). URI versioning is most visible and cache-friendly but clutters URLs and requires updating all endpoint references. Header versioning keeps URLs clean and follows REST principles but is harder to test in browsers and less discoverable. Query parameter versioning is easy to implement but mixes concerns and can complicate caching. Best practices include versioning from day one, maintaining at least two versions during transitions, providing clear deprecation timelines (typically 6-12 months), and documenting breaking vs. non-breaking changes. Consider using semantic versioning internally and only incrementing the public version for breaking changes.

Q: How should APIs handle and communicate errors to clients?
A: Effective error handling improves developer experience and helps clients recover gracefully from failures. APIs should use appropriate HTTP status codes: 4xx for client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity) and 5xx for server errors (500 Internal Server Error, 503 Service Unavailable). Error responses should follow a consistent format containing an error code (machine-readable identifier), message (human-readable description), details (specific field-level errors for validation), and optionally a documentation URL. Never expose internal implementation details, stack traces, or sensitive information in production error responses. Include correlation IDs in error responses to help with debugging and support requests. Consider implementing problem details format (RFC 7807) for standardized error responses. Log detailed error information server-side while returning sanitized messages to clients.

Q: What pagination strategies exist for APIs, and how do you choose the right one?
A: Pagination is essential for APIs returning large datasets to manage response size and server load. Offset-based pagination (page=2&limit=20) is simple to implement but suffers from inconsistency when data changes between requests and becomes slow for large offsets. Cursor-based pagination (after=abc123&limit=20) uses opaque tokens pointing to specific records, providing consistent results and better performance but making random page access impossible. Keyset pagination (created_after=2024-01-01&limit=20) uses actual field values as cursors, offering good performance but requiring a stable sort order. For most APIs, cursor-based pagination is recommended because it handles real-time data changes well and performs consistently regardless of dataset size. Always include pagination metadata in responses: total count (when feasible), links to next/previous pages, and current page information. Use sensible defaults and maximum limits to prevent clients from requesting too much data.

Q: What makes good API documentation, and what tools can help create it?
A: Good API documentation is accurate, complete, well-organized, and includes working examples. Essential elements include authentication instructions, endpoint reference with request/response schemas, error code explanations, rate limiting details, and quickstart guides. Interactive documentation where developers can make real API calls significantly improves adoption. Use the OpenAPI Specification (formerly Swagger) to define your API in a machine-readable format that can generate documentation, client SDKs, and server stubs. Tools like Swagger UI, Redoc, and Stoplight render OpenAPI specs into beautiful documentation. Include code examples in multiple programming languages, explain common use cases and workflows, and maintain a changelog documenting all API changes. Documentation should be versioned alongside the API and treated as a first-class product. Gather feedback from developers and iterate on documentation based on common support questions.

Q: How should APIs handle idempotency, and why is it important?
A: Idempotency means that making the same request multiple times produces the same result as making it once, which is crucial for reliable distributed systems where network failures can cause retry scenarios. GET, PUT, and DELETE are naturally idempotent by HTTP specification, but POST typically is not. For non-idempotent operations like creating resources or processing payments, implement idempotency keys: unique client-generated tokens sent with requests that the server uses to detect and deduplicate retries. Store idempotency keys with their responses for a reasonable time window (typically 24-48 hours), and return the cached response for duplicate requests. This prevents issues like double-charging customers or creating duplicate records when clients retry after network timeouts. Include the Idempotency-Key header in your API design, document the idempotency behavior of each endpoint, and return appropriate status codes (200 for cached response, 201 for first-time creation).

Q: What security considerations should be addressed when designing public APIs?
A: API security requires defense in depth across multiple layers. Always use HTTPS/TLS to encrypt data in transit and validate certificates properly. Implement proper authentication using tokens (JWT, OAuth) rather than API keys in query parameters, which can be logged. Apply the principle of least privilege through fine-grained authorization controls. Validate and sanitize all input to prevent injection attacks, and use parameterized queries for database operations. Implement rate limiting to prevent brute force and denial-of-service attacks. Use CORS headers appropriately to control cross-origin access. Protect against common vulnerabilities like SQL injection, XSS (through proper output encoding), and CSRF (using anti-CSRF tokens). Set appropriate security headers including Content-Security-Policy, X-Content-Type-Options, and Strict-Transport-Security. Regular security audits, penetration testing, and keeping dependencies updated are essential ongoing practices.

Q: What is HATEOAS and how does it relate to REST API design?
A: HATEOAS (Hypermedia as the Engine of Application State) is a REST constraint where API responses include hyperlinks that guide clients to related actions and resources. Instead of clients constructing URLs based on documentation, servers provide links dynamically based on the current resource state. For example, an order response might include links to cancel the order (if cancelable), view the customer, or track shipment (if shipped). This makes APIs more self-documenting and evolvable since clients follow links rather than hardcoding URL patterns. Implementing HATEOAS allows servers to change URLs without breaking clients and enables discoverability of API capabilities. Common formats include HAL (Hypertext Application Language), JSON-LD, and JSON:API. While full HATEOAS implementation is rare in practice, providing relevant links for navigation and related resources improves API usability. The main tradeoff is increased response payload size and implementation complexity.

Q: How should APIs handle partial updates versus full resource replacement?
A: HTTP provides PUT for full resource replacement and PATCH for partial updates, each with distinct use cases. PUT requires clients to send the complete resource representation; any omitted fields are set to null or defaults, making it simple but potentially dangerous for large resources. PATCH sends only the fields to update, reducing bandwidth and race conditions but requiring careful implementation. For PATCH, consider using JSON Patch (RFC 6902) which provides operations like add, remove, replace, move, and copy, or JSON Merge Patch (RFC 7386) which is simpler but cannot distinguish between null values and field removal. Implement optimistic locking using ETags or version numbers to prevent lost updates when multiple clients modify the same resource. Return the updated resource in the response so clients have the current state. Document clearly which approach your API supports and how null values and missing fields are handled.

Q: What strategies help maintain backward compatibility when evolving APIs?
A: Backward compatibility ensures existing clients continue working when APIs change. Additive changes are generally safe: adding new optional fields, new endpoints, new query parameters, or new response fields. Breaking changes to avoid include removing fields, renaming fields, changing field types, changing required/optional status, altering response structures, or modifying error formats. Use feature flags and gradual rollouts to test changes with subsets of traffic. Implement request/response versioning so new clients can use new formats while old clients continue working. Provide clear deprecation notices through Sunset and Deprecation headers (RFC 8594) giving clients time to migrate. Create migration guides documenting required client changes. Consider using expand parameters to allow clients to opt into additional data, making additions backward compatible. Monitor API usage to understand which endpoints and fields are actually used before making changes.

Q: How do webhooks complement REST APIs, and what are best practices for implementing them?
A: Webhooks provide push-based notifications when events occur, complementing pull-based REST APIs and eliminating the need for clients to poll for changes. When implementing webhooks, require HTTPS endpoints and verify SSL certificates to ensure secure delivery. Include a signature header (using HMAC-SHA256 with a shared secret) so receivers can verify requests originated from your service. Implement retry logic with exponential backoff for failed deliveries, typically retrying for 24-72 hours before marking the webhook as failed. Include a unique event ID to enable idempotent processing by receivers. Provide a webhook event catalog documenting all event types, payloads, and when they fire. Allow subscribers to filter which events they receive to reduce unnecessary traffic. Include timestamps and event type in payloads for routing and debugging. Offer a way to test webhooks without triggering real events, and provide delivery logs so subscribers can debug integration issues.

Q: What role do API gateways play in modern API architecture?
A: API gateways serve as the single entry point for all API traffic, providing centralized management of cross-cutting concerns. Key capabilities include authentication and authorization, enforcing security policies before requests reach backend services. Rate limiting and throttling protect services from overload and ensure fair usage. Request/response transformation allows adapting between different formats or API versions. Load balancing distributes traffic across service instances for high availability. Caching reduces backend load and improves response times for frequently accessed data. Analytics and monitoring provide visibility into API usage, performance, and errors. Popular API gateway solutions include Kong, AWS API Gateway, Azure API Management, and Apigee. Gateways simplify microservices architectures by abstracting service discovery and providing a stable external interface while internal services evolve. They also enable canary deployments and A/B testing by routing traffic percentages to different service versions.
