Q: What is horizontal scaling and how does it differ from vertical scaling?
A: Horizontal scaling (scaling out) involves adding more machines to a system to distribute the load, while vertical scaling (scaling up) means adding more resources (CPU, RAM, storage) to an existing machine. Horizontal scaling is generally preferred for large-scale systems because it provides better fault tolerance - if one server fails, others can continue serving requests. It also offers theoretically unlimited scaling capacity, whereas vertical scaling has physical hardware limits. However, horizontal scaling introduces complexity in terms of data consistency, load distribution, and inter-service communication. Modern cloud architectures typically favor horizontal scaling due to its cost-effectiveness and resilience benefits.

Q: How does a load balancer distribute traffic and what algorithms are commonly used?
A: A load balancer acts as a reverse proxy that distributes incoming network traffic across multiple backend servers to ensure no single server becomes overwhelmed. Common algorithms include Round Robin (requests distributed sequentially), Weighted Round Robin (servers with higher capacity receive more traffic), Least Connections (routes to the server with fewest active connections), and IP Hash (routes based on client IP for session persistence). More sophisticated approaches include Least Response Time (routes to fastest responding server) and Resource-Based (considers actual server CPU/memory utilization). Load balancers can operate at Layer 4 (TCP/UDP) for simple routing or Layer 7 (HTTP) for content-aware routing decisions. Health checks continuously monitor backend servers and automatically remove unhealthy instances from the pool.

Q: What is the CAP theorem and why is it important in distributed systems?
A: The CAP theorem states that a distributed system can only guarantee two out of three properties simultaneously: Consistency (all nodes see the same data at the same time), Availability (every request receives a response), and Partition Tolerance (the system continues operating despite network failures between nodes). Since network partitions are inevitable in distributed systems, architects must choose between consistency and availability during failures. CP systems (like ZooKeeper) prioritize consistency and may become unavailable during partitions, while AP systems (like Cassandra) prioritize availability and may serve stale data. Understanding CAP helps architects make informed trade-offs based on business requirements. Modern systems often employ tunable consistency, allowing different operations to have different consistency guarantees.

Q: What are the different caching strategies and when should each be used?
A: Cache-Aside (Lazy Loading) loads data into cache only when requested - ideal for read-heavy workloads with unpredictable access patterns. Write-Through writes data to both cache and database simultaneously, ensuring consistency but adding write latency. Write-Behind (Write-Back) writes to cache immediately and asynchronously updates the database, providing low latency but risking data loss. Read-Through has the cache itself responsible for loading from the database on cache misses, simplifying application code. Refresh-Ahead proactively refreshes frequently accessed data before expiration, reducing cache miss latency for hot data. The choice depends on read/write ratios, consistency requirements, and tolerance for stale data. Multi-tier caching (browser, CDN, application, database) is common in production systems.

Q: How do message queues improve system architecture and what patterns do they enable?
A: Message queues decouple producers from consumers, allowing them to operate independently and at different speeds, which improves system resilience and scalability. They enable asynchronous processing, allowing the system to accept work faster than it can process it by buffering messages during traffic spikes. Common patterns include Point-to-Point (one consumer processes each message), Publish-Subscribe (multiple consumers receive copies), and Fan-Out (one message triggers multiple downstream processes). Message queues provide guaranteed delivery through acknowledgments and persistence, ensuring messages aren't lost even if consumers fail. They enable event-driven architectures where services react to events rather than polling for changes. Popular implementations include RabbitMQ, Apache Kafka, Amazon SQS, and Redis Streams, each optimized for different use cases.

Q: What is eventual consistency and how do systems achieve it?
A: Eventual consistency is a consistency model where the system guarantees that if no new updates are made, all replicas will eventually converge to the same value. This model trades immediate consistency for higher availability and lower latency in distributed systems. Systems achieve eventual consistency through various mechanisms: vector clocks track causality between updates, conflict-free replicated data types (CRDTs) allow automatic conflict resolution, and last-write-wins policies use timestamps to resolve conflicts. Read-repair corrects inconsistencies when stale data is detected during reads, while anti-entropy protocols (like Merkle trees) periodically synchronize replicas in the background. The convergence time depends on network conditions, replication lag, and the specific consistency protocol used. Applications must be designed to tolerate temporary inconsistencies, often using techniques like compensating transactions or idempotent operations.

Q: What are the key principles of microservices architecture?
A: Microservices architecture decomposes applications into small, independently deployable services that communicate over well-defined APIs. Each service should follow the Single Responsibility Principle, focusing on one business capability and owning its data store (database per service). Services should be loosely coupled, meaning changes to one service don't require changes to others, enabled through contracts and API versioning. Teams can choose the best technology stack for each service, enabling polyglot persistence and programming. Deployment independence allows services to be updated, scaled, and rolled back without affecting the entire system. This architecture requires robust DevOps practices including containerization, service discovery, API gateways, and distributed tracing. The trade-off is increased operational complexity, network latency, and the challenges of distributed transactions.

Q: How does consistent hashing work and why is it used in distributed systems?
A: Consistent hashing maps both data keys and server nodes onto a circular hash ring, where each key is assigned to the first node encountered moving clockwise from its position. When a node is added or removed, only keys mapped to that node need to be redistributed, minimizing data movement compared to traditional modulo-based hashing. Virtual nodes (multiple positions per physical node) improve load distribution and handle heterogeneous server capacities. This technique is essential for distributed caches (Memcached), databases (Cassandra, DynamoDB), and content delivery networks where servers frequently join and leave. The algorithm provides predictable key distribution and makes the system resilient to node failures. Consistent hashing with replication stores data on multiple consecutive nodes for fault tolerance. The approach enables horizontal scaling with minimal disruption to existing data placement.

Q: What is the Circuit Breaker pattern and how does it prevent cascading failures?
A: The Circuit Breaker pattern prevents a failing service from causing system-wide failures by wrapping calls to remote services and monitoring for failures. It operates in three states: Closed (requests pass through normally), Open (requests fail immediately without attempting the call), and Half-Open (limited requests test if the service has recovered). When failures exceed a threshold in the Closed state, the circuit trips to Open, giving the failing service time to recover without being overwhelmed. After a timeout, the circuit moves to Half-Open and allows test requests through. If these succeed, it returns to Closed; if they fail, it returns to Open. This pattern protects system resources, provides fail-fast behavior, and enables graceful degradation through fallback responses. Libraries like Hystrix, Resilience4j, and Polly implement this pattern with additional features like bulkheads and rate limiting.

Q: What strategies exist for database sharding and what are their trade-offs?
A: Range-based sharding partitions data by value ranges (e.g., users A-M on shard 1, N-Z on shard 2), which is simple but can create hotspots if data isn't uniformly distributed. Hash-based sharding applies a hash function to the shard key for even distribution but makes range queries across shards expensive. Directory-based sharding uses a lookup service to map keys to shards, offering flexibility but adding a single point of failure. Geographic sharding places data near its users for lower latency but complicates global queries. All sharding strategies face challenges with cross-shard queries, distributed transactions, and rebalancing data when adding shards. The choice of shard key is critical - it should provide even distribution, support common query patterns, and minimize cross-shard operations. Many systems combine sharding with replication for both scalability and high availability.

Q: How do distributed systems handle data replication and what are the consistency trade-offs?
A: Synchronous replication waits for all replicas to acknowledge writes before confirming to the client, ensuring strong consistency but increasing latency and reducing availability if any replica fails. Asynchronous replication acknowledges writes after the primary accepts them, offering lower latency but risking data loss if the primary fails before replication completes. Semi-synchronous replication waits for at least one replica to acknowledge, balancing durability and performance. Chain replication orders replicas in a chain where writes flow through all nodes, providing strong consistency with good read throughput. Quorum-based replication (used in systems like Cassandra) requires W writes and R reads where W+R > N (total replicas) to ensure overlap and consistency. Leader-follower (master-slave) replication directs all writes to a leader while followers serve reads, simplifying consistency but creating a bottleneck. Multi-leader replication allows writes at multiple nodes but requires conflict resolution strategies.

Q: What is service discovery and why is it essential in microservices?
A: Service discovery enables services to find and communicate with each other in dynamic environments where instances are constantly created, destroyed, and moved. Client-side discovery has clients query a service registry (like Consul or etcd) to find available instances and then load balance requests themselves. Server-side discovery routes requests through a load balancer or API gateway that queries the registry, simplifying client logic but adding network hops. Services register themselves upon startup and deregister on shutdown, with health checks removing unhealthy instances. DNS-based discovery is simple but suffers from caching issues and limited load balancing. Container orchestrators like Kubernetes provide built-in service discovery through internal DNS and virtual IPs. Effective service discovery must handle network partitions, stale registrations, and provide fast failover to maintain system availability.

Q: What are idempotency and exactly-once semantics, and why do they matter in distributed systems?
A: Idempotency means an operation can be applied multiple times without changing the result beyond the initial application, which is crucial when network failures cause message retries. Without idempotent operations, retried requests could cause duplicate charges, double inventory decrements, or data corruption. Systems achieve idempotency through unique request identifiers that allow servers to detect and ignore duplicate requests. Exactly-once semantics guarantee each message is processed once despite failures, which is extremely difficult to achieve in distributed systems due to the Two Generals Problem. Many systems settle for at-least-once delivery combined with idempotent handlers, effectively achieving exactly-once processing semantics. Implementations often use idempotency keys stored in databases with appropriate TTLs, request deduplication at the message queue level, or optimistic locking with version numbers. Designing for idempotency from the start is easier than retrofitting it into existing systems.

Q: How do rate limiting and throttling protect distributed systems?
A: Rate limiting restricts the number of requests a client can make within a time window, protecting services from abuse, DDoS attacks, and accidental traffic spikes. Token bucket algorithm allows bursts up to a bucket size while maintaining an average rate, suitable for APIs with variable traffic patterns. Leaky bucket processes requests at a constant rate, queuing excess requests, which smooths traffic but increases latency during bursts. Fixed window counting is simple but allows double the limit at window boundaries. Sliding window provides more accurate limiting by considering both current and previous window activity. Distributed rate limiting requires shared state across instances, often using Redis with atomic operations. Rate limiters should return appropriate HTTP status codes (429 Too Many Requests) with Retry-After headers and provide different limits for different API tiers or client types.

Q: What is the Saga pattern and how does it handle distributed transactions?
A: The Saga pattern manages data consistency across microservices by breaking a distributed transaction into a sequence of local transactions, each updating a single service and publishing events to trigger the next step. Unlike traditional ACID transactions, sagas rely on eventual consistency and compensating transactions to undo changes if a step fails. Choreography-based sagas have services listen for events and decide independently whether to act, which is decentralized but can become difficult to understand and debug. Orchestration-based sagas use a central coordinator that explicitly manages the transaction sequence and handles compensation, providing better visibility but creating a single point of control. Compensating transactions must be carefully designed to be idempotent and semantically undo business operations, which isn't always straightforward (e.g., sending a cancellation email after mistakenly sending a confirmation). The saga pattern accepts temporary inconsistency in exchange for availability and requires the application to handle the complexity of partial failures gracefully.
