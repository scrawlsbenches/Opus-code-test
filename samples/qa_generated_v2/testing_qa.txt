Q: What is unit testing and why is it considered the foundation of a testing strategy?
A: Unit testing is the practice of testing individual components or functions in isolation from the rest of the application. These tests verify that a single unit of code, typically a function or method, behaves correctly given specific inputs. Unit tests are considered foundational because they provide fast feedback, are cheap to write and maintain, and catch bugs at the earliest possible stage of development. When a unit test fails, it immediately pinpoints the exact location of the problem, making debugging straightforward. A comprehensive unit test suite also serves as living documentation, demonstrating how components are expected to behave.

Q: How does integration testing differ from unit testing, and when should you use each?
A: Integration testing verifies that multiple components work correctly together, whereas unit testing focuses on individual components in isolation. Unit tests use mocks and stubs to replace dependencies, while integration tests use real implementations to test actual interactions between modules, databases, APIs, or services. You should use unit tests for validating business logic and edge cases within individual functions, and integration tests for verifying that components communicate correctly across boundaries. A balanced testing strategy employs both: unit tests provide fast, granular feedback during development, while integration tests catch issues that only emerge when components interact.

Q: What is Test-Driven Development (TDD) and what are its three main steps?
A: Test-Driven Development is a software development methodology where tests are written before the production code. The three main steps, often called Red-Green-Refactor, are: first, write a failing test that defines the desired behavior (Red); second, write the minimum amount of code necessary to make the test pass (Green); third, refactor the code to improve its design while keeping all tests passing (Refactor). TDD encourages developers to think about requirements and edge cases upfront, resulting in better-designed, more testable code. It also ensures comprehensive test coverage since no production code is written without a corresponding test. Many practitioners find that TDD leads to simpler solutions because you only write code that is actually needed.

Q: What is Behavior-Driven Development (BDD) and how does it relate to TDD?
A: Behavior-Driven Development is an extension of TDD that emphasizes collaboration between developers, testers, and business stakeholders through a shared language. BDD uses natural language specifications, typically in Given-When-Then format, to describe the expected behavior of a system from the user's perspective. For example: "Given a user is logged in, When they add an item to cart, Then the cart count should increase by one." This approach bridges the gap between technical and non-technical team members, ensuring everyone understands what the software should do. BDD frameworks like Cucumber, Behave, or SpecFlow allow these specifications to be executed as automated tests. While TDD focuses on technical correctness, BDD ensures the software delivers actual business value.

Q: What is mocking in testing and when should you use mocks versus real implementations?
A: Mocking is a technique where you replace real dependencies with controlled fake objects that simulate the behavior of those dependencies. Mocks allow you to isolate the unit under test, control the test environment precisely, and verify interactions between components. You should use mocks when testing code that depends on external services, databases, file systems, or network calls, as these dependencies make tests slow, flaky, or difficult to set up. However, over-mocking can lead to tests that pass but don't reflect real behavior. A good rule is to mock at architectural boundaries but use real implementations for internal collaborators. Integration tests should use fewer mocks to verify that real components work together correctly.

Q: What is test coverage and why can high coverage be misleading?
A: Test coverage is a metric that measures what percentage of your code is executed during test runs. Common coverage types include line coverage, branch coverage, and path coverage. While coverage helps identify untested code paths, high coverage can be misleading because it only measures whether code was executed, not whether the tests actually verify correct behavior. A test suite could achieve 100% coverage while having no meaningful assertions. Coverage also doesn't account for edge cases, error handling, or the quality of test design. The goal should be meaningful coverage of critical business logic and edge cases rather than chasing a coverage number. Use coverage as a tool for identifying gaps, not as a target to game.

Q: What is property-based testing and how does it differ from example-based testing?
A: Property-based testing is an approach where you define properties or invariants that should hold true for all inputs, and the testing framework automatically generates hundreds or thousands of random test cases. Unlike example-based testing where you write specific input-output pairs, property-based testing describes general rules about your code's behavior. For example, instead of testing that sorting [3,1,2] returns [1,2,3], you might test properties like "the output has the same length as the input" and "each element in the output is less than or equal to the next." Libraries like QuickCheck, Hypothesis, and fast-check implement this approach. Property-based testing excels at finding edge cases you wouldn't think to test manually and often uncovers subtle bugs that example-based tests miss.

Q: What is end-to-end testing and what are its advantages and disadvantages?
A: End-to-end (E2E) testing validates the entire application flow from start to finish, simulating real user scenarios through the complete system stack. These tests interact with the application as a user would, clicking buttons, filling forms, and navigating pages, verifying that all components work together correctly in a production-like environment. The main advantage is confidence that the system works as users expect, catching integration issues that lower-level tests might miss. However, E2E tests are slow to execute, expensive to maintain, and often flaky due to timing issues, network variability, or environmental differences. The testing pyramid principle suggests having fewer E2E tests than integration tests, and fewer integration tests than unit tests. Reserve E2E tests for critical user journeys that provide the most business value.

Q: What is test automation and what factors should guide the decision to automate a test?
A: Test automation is the practice of using software tools to execute tests, compare actual outcomes with expected outcomes, and report results without manual intervention. Factors guiding automation decisions include test frequency, test stability, execution time savings, and the complexity of manual execution. Tests that run frequently, such as regression tests, are prime automation candidates because the upfront investment pays off over time. Stable functionality with clear pass/fail criteria automates well, while exploratory or frequently changing features may not. Consider the cost-benefit ratio: if a manual test takes 10 minutes and runs daily, automating it saves significant time. However, some tests requiring human judgment, like usability testing, are better performed manually. A balanced approach automates repetitive, deterministic tests while preserving manual testing for exploratory and creative scenarios.

Q: What are test fixtures and why are they important for test maintainability?
A: Test fixtures are the preconditions and setup needed to run tests, including test data, database states, configuration, and mock objects. Well-designed fixtures isolate setup logic, making tests more readable and maintainable by separating the "arrange" phase from "act" and "assert." Shared fixtures reduce code duplication when multiple tests need similar setups, but they must be designed carefully to avoid unintended coupling between tests. Each test should ideally set up its own isolated state to prevent one test's modifications from affecting another. Fixture factories and builders help create test data with sensible defaults while allowing customization for specific scenarios. Good fixture design is crucial for long-term test suite health; poorly managed fixtures lead to brittle tests that break when unrelated code changes.

Q: What is the test pyramid and why is it recommended?
A: The test pyramid is a visual metaphor suggesting that a well-structured test suite should have many unit tests at the base, fewer integration tests in the middle, and even fewer end-to-end tests at the top. This structure is recommended because unit tests are fast, reliable, and cheap to maintain, providing rapid feedback during development. Integration tests verify component interactions but are slower and more complex. E2E tests provide the highest confidence but are the slowest, most brittle, and most expensive to maintain. By having more tests at lower levels, you get faster feedback loops and more stable builds. The pyramid also encourages pushing testing down: if you can verify behavior with a unit test, prefer that over an integration test. Anti-patterns like the ice cream cone (many manual and E2E tests, few unit tests) lead to slow, unreliable test suites.

Q: What is mutation testing and how does it assess test suite quality?
A: Mutation testing is a technique that evaluates the effectiveness of your test suite by introducing small changes (mutations) to your production code and checking if your tests detect them. Mutations include changes like replacing arithmetic operators, modifying boolean conditions, or changing return values. If your tests still pass after a mutation is introduced, it indicates a weakness in your test suite called a "surviving mutant." A high mutation score means your tests catch most introduced defects, suggesting good test quality. Mutation testing goes beyond coverage by verifying that tests actually check correct behavior rather than just executing code paths. Tools like PIT for Java, mutmut for Python, and Stryker for JavaScript automate this process. While computationally expensive, mutation testing provides valuable insights for improving test effectiveness.

Q: What is test isolation and why is it critical for reliable test suites?
A: Test isolation means each test runs independently without depending on or affecting other tests. Isolated tests can run in any order, in parallel, and produce consistent results regardless of what other tests do. Lack of isolation leads to flaky tests that pass or fail depending on execution order, making it impossible to trust test results. Common isolation violations include shared mutable state, database records left by previous tests, and global variables. Achieving isolation requires proper setup and teardown, using fresh instances of dependencies, and avoiding shared state between tests. Database tests should use transactions that roll back or isolated test databases. Test frameworks provide hooks like beforeEach and afterEach to manage setup and cleanup. Well-isolated tests are easier to debug because failures point to specific problems rather than mysterious interactions.

Q: What are test doubles and what are the differences between mocks, stubs, fakes, and spies?
A: Test doubles are objects that stand in for real dependencies during testing, and they come in several varieties with distinct purposes. Stubs provide canned answers to calls made during tests without recording information about those calls. Mocks are pre-programmed with expectations about which calls they should receive and can fail the test if unexpected calls occur. Fakes are working implementations with shortcuts that make them unsuitable for production, like an in-memory database. Spies are partial mocks that record information about calls while also calling through to the real implementation. Choosing the right test double depends on your testing goal: use stubs when you need controlled return values, mocks when verifying interactions is important, fakes when you need realistic behavior without production overhead, and spies when you want to observe real behavior. Understanding these distinctions helps write more expressive and appropriate tests.

Q: What is continuous testing and how does it fit into CI/CD pipelines?
A: Continuous testing is the practice of executing automated tests throughout the software delivery pipeline, providing immediate feedback on code quality at every stage. In CI/CD pipelines, tests run automatically whenever code is committed, merged, or deployed. Fast unit tests typically run first to catch obvious errors quickly, followed by integration tests, and finally end-to-end tests before deployment. This layered approach balances speed with thoroughness: failures are caught early when they're cheap to fix. Continuous testing also enables practices like test-driven deployments, where code only progresses to the next environment if tests pass. Key considerations include test execution speed, parallelization strategies, and intelligent test selection to run only tests affected by recent changes. Effective continuous testing transforms quality assurance from a phase into an ongoing activity embedded throughout development.
