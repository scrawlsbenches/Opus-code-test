Q: What are the core principles of REST API design?
A: REST (Representational State Transfer) is built on six fundamental principles: client-server separation, statelessness, cacheability, uniform interface, layered system, and optional code-on-demand. The uniform interface is particularly crucial, requiring resource identification through URIs, manipulation through representations, self-descriptive messages, and hypermedia as the engine of application state (HATEOAS). Statelessness means each request must contain all information needed to process it, with no server-side session state between requests. These principles ensure scalability, reliability, and loose coupling between client and server components.

Q: How does GraphQL differ from REST, and when should you choose one over the other?
A: GraphQL provides a query language that allows clients to request exactly the data they need in a single request, solving REST's over-fetching and under-fetching problems. While REST uses multiple endpoints with fixed data structures, GraphQL exposes a single endpoint with a flexible schema that clients query against. Choose GraphQL when you have complex data requirements, multiple client types with different needs, or when minimizing network requests is critical. REST remains preferable for simpler APIs, when HTTP caching is important, when you need predictable request patterns, or when your team lacks GraphQL expertise. GraphQL also introduces complexity in areas like caching, rate limiting, and query cost analysis that REST handles more naturally.

Q: What authentication mechanisms are commonly used in web APIs?
A: The most common API authentication mechanisms include API keys, OAuth 2.0, JWT (JSON Web Tokens), and Basic Authentication. API keys are simple but offer limited security and should only be used for non-sensitive operations or combined with other methods. OAuth 2.0 is the industry standard for delegated authorization, allowing third-party applications to access resources without exposing credentials, with flows like Authorization Code, Client Credentials, and PKCE for different scenarios. JWTs are self-contained tokens that encode user claims and are cryptographically signed, enabling stateless authentication across distributed systems. Modern APIs typically combine these approaches, using OAuth for user authentication and JWTs as the token format for subsequent API calls.

Q: Why is rate limiting important and how should it be implemented?
A: Rate limiting protects APIs from abuse, ensures fair resource allocation among clients, and maintains service availability during traffic spikes or attacks. Common algorithms include fixed window (simple but allows bursts at window boundaries), sliding window (smoother but more complex), token bucket (allows controlled bursting), and leaky bucket (ensures constant output rate). Implementation should include proper HTTP headers like X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset to inform clients of their quota status. When limits are exceeded, return HTTP 429 Too Many Requests with a Retry-After header. Consider implementing tiered rate limits based on authentication level, endpoint sensitivity, and customer plans, and always rate limit by multiple dimensions such as IP address, API key, and user ID.

Q: What are the best practices for API versioning?
A: API versioning strategies include URI path versioning (/v1/users), query parameter versioning (?version=1), custom header versioning (X-API-Version: 1), and content negotiation via Accept headers. URI versioning is the most explicit and discoverable approach, making it popular despite being less RESTful. Header-based versioning keeps URLs clean but is less visible and harder to test in browsers. Semantic versioning principles should guide when to increment versions: major versions for breaking changes, minor for backward-compatible additions. Best practices include maintaining at least two versions simultaneously during transitions, providing clear deprecation timelines (typically 6-12 months), and documenting migration paths. Consider using API evolution techniques like tolerant readers and careful field additions to minimize the need for version increments.

Q: How should APIs handle and communicate errors to clients?
A: Effective API error handling requires consistent, informative responses that help developers diagnose and fix issues quickly. Use appropriate HTTP status codes: 4xx for client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity) and 5xx for server errors (500 Internal Server Error, 503 Service Unavailable). Response bodies should follow a consistent structure containing an error code, human-readable message, and optional details array for validation errors. Include correlation IDs in responses and logs to enable request tracing across distributed systems. Never expose internal implementation details, stack traces, or sensitive information in production error responses. Consider providing links to documentation or support resources in error responses to help developers resolve issues independently.

Q: What elements should be included in comprehensive API documentation?
A: Comprehensive API documentation should include authentication instructions, endpoint references with request/response examples, error code explanations, rate limiting details, and SDK or client library guides. Each endpoint needs a clear description, HTTP method, URL pattern, request parameters (path, query, header, body), response schemas for success and error cases, and realistic examples. Interactive documentation using tools like Swagger UI or Redoc allows developers to test endpoints directly. Include getting started guides, tutorials for common use cases, and a changelog tracking API evolution. Code samples in multiple programming languages significantly improve developer experience. Maintain documentation alongside code using OpenAPI specifications to ensure accuracy, and consider providing a sandbox environment for safe experimentation.

Q: What are the key considerations when designing microservices APIs?
A: Microservices API design must prioritize loose coupling, enabling services to evolve independently without cascading changes. Define clear service boundaries based on business domains following Domain-Driven Design principles, with each service owning its data and exposing it only through well-defined APIs. Choose appropriate communication patterns: synchronous REST or gRPC for request-response needs, asynchronous messaging for event-driven interactions and improved resilience. Implement circuit breakers, timeouts, and retry logic to handle partial failures gracefully. API gateways provide a unified entry point, handling cross-cutting concerns like authentication, rate limiting, and request routing. Design for eventual consistency and use saga patterns for distributed transactions. Service mesh technologies like Istio can manage service-to-service communication, providing observability, security, and traffic management capabilities.

Q: How can you protect APIs against common security vulnerabilities?
A: API security requires defense in depth across multiple layers. Always use HTTPS/TLS for data in transit and implement proper authentication and authorization for every endpoint. Validate and sanitize all input to prevent injection attacks, and use parameterized queries for database operations. Implement CORS (Cross-Origin Resource Sharing) policies appropriately, being restrictive rather than permissive with allowed origins. Protect against mass assignment by explicitly defining which fields can be updated. Rate limiting and request throttling prevent denial of service and brute force attacks. Use security headers like Content-Security-Policy, X-Content-Type-Options, and X-Frame-Options. Regularly audit dependencies for known vulnerabilities, conduct penetration testing, and maintain security monitoring for anomalous patterns. Consider implementing API-specific protections like request signing and timestamp validation to prevent replay attacks.

Q: What is HATEOAS and why is it considered important in REST API design?
A: HATEOAS (Hypermedia as the Engine of Application State) is a REST constraint where API responses include hyperlinks that guide clients to available actions and related resources. Instead of clients hardcoding endpoint URLs, they discover them dynamically through links in responses, similar to how web browsers follow links. This approach decouples clients from server URL structures, allowing the API to evolve its URL patterns without breaking clients. A response might include links like "self" for the current resource, "next" for pagination, or action-specific links like "approve" or "cancel" based on the current state. While theoretically elegant, HATEOAS is often partially implemented in practice due to added complexity. When implemented well, it creates more resilient integrations and self-documenting APIs that clients can navigate without extensive prior knowledge.

Q: How should pagination be implemented in APIs that return large datasets?
A: APIs returning large datasets should implement pagination to manage response sizes and improve performance. Offset-based pagination (using page and limit or skip and take parameters) is simple but performs poorly for large offsets and can show inconsistent results if data changes between requests. Cursor-based pagination uses an opaque cursor pointing to a specific record, providing stable results and better performance for large datasets, making it ideal for real-time feeds or infinite scrolling. Keyset pagination uses the last seen value of a sorted field, offering excellent performance but requiring a stable sort order. Include pagination metadata in responses: total count (when feasible), current page info, and links to first, previous, next, and last pages. Set reasonable default and maximum page sizes to prevent resource exhaustion, and document the pagination approach clearly for API consumers.

Q: What strategies help ensure backward compatibility when evolving APIs?
A: Maintaining backward compatibility requires discipline in how changes are made and communicated. Additive changes are generally safe: new optional fields, new endpoints, new optional query parameters, and new response fields that clients can ignore. Breaking changes to avoid include removing or renaming fields, changing field types, altering endpoint URLs, making optional parameters required, and changing error response formats. Use the tolerant reader pattern where servers accept and ignore unknown fields, and clients ignore unexpected response fields. Implement feature flags to roll out changes gradually and monitor for issues. Provide clear deprecation warnings in responses (Deprecation and Sunset headers) and documentation well before removing features. Contract testing with tools like Pact helps catch unintended breaking changes during development. When breaking changes are unavoidable, version the API and maintain the old version during a migration period.

Q: How do you design APIs for idempotency and safe retry behavior?
A: Idempotent APIs produce the same result regardless of how many times a request is made, which is crucial for reliability in distributed systems where network failures may cause duplicate requests. GET, PUT, and DELETE operations are naturally idempotent by HTTP semantics. POST operations, typically used for creation, require explicit idempotency handling through idempotency keys: clients generate a unique key for each logical operation and include it in request headers. The server stores results associated with each key and returns cached responses for duplicate requests. Implement idempotency with reasonable key expiration times (typically 24-48 hours) and handle edge cases like concurrent requests with the same key. Document idempotency behavior for each endpoint and provide client libraries that automatically generate and manage idempotency keys, especially for payment or critical business operations.

Q: What role do API gateways play in modern architectures?
A: API gateways serve as a single entry point for all API traffic, centralizing cross-cutting concerns and simplifying client integration. Key responsibilities include authentication and authorization enforcement, request routing to appropriate backend services, rate limiting and throttling, request/response transformation, protocol translation (REST to gRPC, for example), SSL termination, and request logging and monitoring. Gateways enable backend services to focus on business logic without duplicating infrastructure concerns. They facilitate API composition, aggregating multiple service calls into single client requests to reduce latency. Modern gateways like Kong, AWS API Gateway, or Azure API Management provide developer portals, API analytics, and monetization features. However, gateways can become bottlenecks or single points of failure, so deploy them with proper redundancy and scaling. Be cautious about adding too much business logic to gateways, which should remain focused on infrastructure concerns.

Q: How should APIs handle partial responses and field selection?
A: Field selection allows clients to request only the data fields they need, reducing payload sizes and improving performance. Implement using query parameters like fields=id,name,email or through GraphQL's native field selection. Sparse fieldsets in JSON:API use include and fields parameters for standardized partial responses across related resources. This technique is particularly valuable for mobile clients with bandwidth constraints or when responses contain expensive-to-compute fields. Consider implementing field expansion for nested resources (fields=author.name,author.email) to provide flexibility without multiple round trips. Document available fields clearly and handle invalid field requests gracefully with helpful error messages. Cache partial responses carefully, as different field combinations create different cache keys. For complex selection needs, GraphQL provides a more natural solution than retrofitting field selection onto REST endpoints.
