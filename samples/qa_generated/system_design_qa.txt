Q: What is horizontal scaling and when should you use it instead of vertical scaling?
A: Horizontal scaling (scaling out) involves adding more machines to your resource pool, while vertical scaling (scaling up) means adding more power to an existing machine. Horizontal scaling is preferred when you need to handle increasing loads beyond what a single machine can provide, when you require high availability and fault tolerance, or when your application architecture supports stateless services. It distributes the load across multiple servers, eliminating single points of failure. However, it introduces complexity in data consistency and session management. Use horizontal scaling for web applications, microservices, and systems where availability is critical, while vertical scaling may suffice for databases or applications with limited concurrency requirements.

Q: How does a load balancer distribute traffic, and what are the common algorithms used?
A: A load balancer acts as a traffic cop sitting in front of your servers, distributing incoming requests across multiple backend servers to ensure no single server becomes overwhelmed. Common algorithms include Round Robin, which cycles through servers sequentially; Weighted Round Robin, where servers with more capacity receive proportionally more requests; Least Connections, which routes traffic to the server with the fewest active connections; and IP Hash, which uses the client IP to consistently route requests to the same server. More sophisticated approaches include Least Response Time, which considers both connection count and server response latency. The choice of algorithm depends on whether your servers are homogeneous, whether session persistence matters, and the nature of your workload patterns.

Q: What are the key differences between write-through, write-back, and write-around caching strategies?
A: Write-through caching writes data to both the cache and the underlying storage simultaneously, ensuring consistency but introducing latency on every write operation. Write-back (or write-behind) caching writes data only to the cache initially, then asynchronously flushes to persistent storage, offering better write performance but risking data loss if the cache fails before persistence. Write-around caching writes directly to storage, bypassing the cache entirely, which prevents cache pollution from write-heavy workloads but may cause cache misses on subsequent reads of newly written data. Choose write-through when data integrity is paramount, write-back when write performance is critical and some data loss is acceptable, and write-around when your application has distinct read and write patterns with infrequent re-reads of written data.

Q: What is the CAP theorem and what are its practical implications for distributed system design?
A: The CAP theorem states that a distributed system can only provide two of three guarantees simultaneously: Consistency (all nodes see the same data at the same time), Availability (every request receives a response), and Partition tolerance (the system continues operating despite network partitions). Since network partitions are inevitable in distributed systems, the practical choice is between CP (consistent but potentially unavailable during partitions) and AP (available but potentially inconsistent). Traditional relational databases often favor CP, while systems like Cassandra and DynamoDB favor AP with eventual consistency. Understanding CAP helps architects make informed tradeoffs: banking systems might prioritize consistency, while social media feeds can tolerate eventual consistency for better availability.

Q: How do message queues improve system architecture, and when should you use them?
A: Message queues decouple producers and consumers, enabling asynchronous communication where the sender does not need to wait for the receiver to process the message. This decoupling improves system resilience since failures in one component do not cascade to others, enables independent scaling of producers and consumers, and provides natural load leveling by buffering traffic spikes. Use message queues for background job processing, event-driven architectures, inter-service communication in microservices, and any scenario where immediate response is not required. Popular implementations include RabbitMQ for complex routing patterns, Apache Kafka for high-throughput event streaming, and Amazon SQS for managed simplicity. The tradeoff is added complexity, potential message ordering challenges, and the need to handle duplicate messages in at-least-once delivery systems.

Q: What are the key considerations when deciding between microservices and monolithic architecture?
A: Monolithic architectures package all functionality into a single deployable unit, offering simplicity in development, testing, and deployment for smaller teams and applications. Microservices decompose the system into independently deployable services, each owning its data and business logic. Choose microservices when you have multiple teams that need to deploy independently, when different components have vastly different scaling requirements, or when you need technology diversity across services. However, microservices introduce distributed system complexity including network latency, data consistency challenges, and operational overhead for service discovery, monitoring, and debugging. Start with a well-structured monolith and extract microservices when clear bounded contexts emerge and the organizational structure supports independent service ownership.

Q: How does consistent hashing work and why is it important for distributed caching?
A: Consistent hashing maps both data keys and server nodes onto a circular hash space (hash ring), assigning each key to the nearest server node clockwise on the ring. When a server is added or removed, only keys that map between the affected server and its predecessor need to be redistributed, rather than reshuffling the entire dataset. This property is critical for distributed caches because it minimizes cache invalidation during scaling events: adding a server with N nodes only invalidates approximately 1/N of the keys, compared to traditional modulo hashing which would invalidate nearly all cached data. Virtual nodes (multiple hash positions per physical server) improve load distribution across heterogeneous servers. Systems like Memcached, Cassandra, and Amazon DynamoDB use consistent hashing to achieve predictable data distribution and minimal disruption during topology changes.

Q: What is the circuit breaker pattern and how does it prevent cascading failures?
A: The circuit breaker pattern prevents a failing service from causing cascading failures across a distributed system by monitoring failures and temporarily blocking requests when a threshold is exceeded. It operates in three states: Closed (normal operation, requests pass through), Open (requests fail immediately without attempting the downstream call), and Half-Open (limited requests are allowed to test if the service has recovered). When failures exceed the threshold, the circuit opens, returning fast failures instead of waiting for timeouts, which preserves thread pools and prevents resource exhaustion. After a timeout period, it transitions to half-open to probe recovery. This pattern is essential in microservices architectures where one slow or failing service could consume resources across multiple dependent services. Libraries like Netflix Hystrix, Resilience4j, and Polly provide circuit breaker implementations.

Q: What are the differences between eventual consistency and strong consistency, and how do you choose between them?
A: Strong consistency guarantees that after a write completes, all subsequent reads will return that value, providing a simple programming model but requiring coordination that impacts latency and availability. Eventual consistency guarantees only that if no new updates are made, all replicas will eventually converge to the same value, allowing higher availability and lower latency but requiring applications to handle temporary inconsistencies. Choose strong consistency for financial transactions, inventory management, or any domain where reading stale data causes business problems. Choose eventual consistency for user-facing features where brief inconsistency is acceptable, such as social media timelines, product reviews, or analytics dashboards. Many systems offer tunable consistency, allowing you to make per-operation tradeoffs between consistency, latency, and availability based on specific requirements.

Q: How do you design for fault tolerance in distributed systems?
A: Fault tolerance requires assuming failures will occur and designing systems to continue operating despite them. Key strategies include redundancy at every layer (multiple servers, availability zones, and regions), automatic failover with health checks and leader election, graceful degradation that maintains core functionality when secondary features fail, and bulkhead patterns that isolate failures to prevent system-wide outages. Implement retry logic with exponential backoff for transient failures, timeouts to prevent indefinite blocking, and circuit breakers to fail fast when dependencies are unhealthy. Design for idempotency so that retried operations produce the same result, and maintain operational visibility through comprehensive logging, distributed tracing, and alerting. Regularly test failure scenarios through chaos engineering practices to validate that your fault tolerance mechanisms work as expected under real conditions.

Q: What is database sharding and what are its challenges?
A: Database sharding horizontally partitions data across multiple database instances, with each shard containing a subset of the total data determined by a sharding key. This approach enables horizontal scaling beyond the limits of a single database server by distributing both storage and query load. However, sharding introduces significant challenges: cross-shard queries require scatter-gather operations with higher latency; joins across shards are expensive or impossible; maintaining referential integrity becomes the application's responsibility; and rebalancing data when adding shards or when hot spots emerge is operationally complex. Choosing an effective sharding key is critical because it affects query patterns, data distribution, and future scalability. Consider sharding only when vertical scaling and read replicas are insufficient, and evaluate whether a natively distributed database might provide similar scalability with less operational complexity.

Q: How does a content delivery network improve application performance and reliability?
A: A CDN distributes content across geographically dispersed edge servers, caching static assets closer to end users to reduce latency and improve load times. When a user requests content, the CDN routes them to the nearest edge location, serving cached content without hitting the origin server. This reduces bandwidth costs on your infrastructure, improves resilience against traffic spikes and DDoS attacks, and provides redundancy if your origin becomes unavailable. Modern CDNs also offer edge computing capabilities, SSL termination, and intelligent routing based on server health and network conditions. Configure appropriate cache headers and invalidation strategies to balance freshness with cache hit rates. For dynamic content, CDNs can still provide benefits through connection pooling, protocol optimization, and routing optimization even without caching.

Q: What is event sourcing and when is it appropriate to use?
A: Event sourcing persists the state of an entity as a sequence of immutable events rather than storing only the current state. Each state change is captured as an event, and the current state can be reconstructed by replaying all events from the beginning. This pattern provides a complete audit trail, enables temporal queries to see historical states, supports event-driven architectures naturally, and allows rebuilding read models or projections from the event log. Event sourcing is appropriate for domains requiring strong audit capabilities (financial systems, healthcare), systems where understanding the sequence of changes is important, or when building CQRS architectures with multiple read models. However, it adds complexity in event schema evolution, increases storage requirements, and can make simple queries more expensive. The pattern works best when combined with snapshots to optimize reconstruction time and careful consideration of event versioning strategies.

Q: What role does service discovery play in microservices architecture?
A: Service discovery enables services to find and communicate with each other in dynamic environments where service instances are constantly being created, destroyed, and moved across hosts. Client-side discovery has services query a registry directly and handle load balancing themselves, while server-side discovery routes requests through a load balancer that queries the registry. Popular implementations include Consul, which provides service mesh capabilities; etcd and ZooKeeper for distributed key-value storage; and Kubernetes DNS for container orchestration environments. Service discovery eliminates hard-coded endpoints, enables dynamic scaling, and supports deployment patterns like blue-green and canary releases. Health checking integration ensures traffic is only routed to healthy instances. Without effective service discovery, microservices architectures become fragile and difficult to scale or update independently.

Q: How do you implement rate limiting, and what algorithms are commonly used?
A: Rate limiting controls the number of requests a client can make within a time window, protecting services from abuse, ensuring fair resource allocation, and preventing cascade failures during traffic spikes. The token bucket algorithm allows bursts by accumulating tokens over time up to a maximum, with each request consuming a token. The leaky bucket algorithm smooths traffic by processing requests at a fixed rate, queuing excess requests. Fixed window counting divides time into windows and limits requests per window, though it can allow double the limit at window boundaries. Sliding window algorithms address this by considering a weighted combination of current and previous windows. Implement rate limiting at API gateways for external traffic and within services for fine-grained control. Return appropriate HTTP status codes (429 Too Many Requests) with headers indicating retry timing, and consider graceful degradation over hard failures for internal service communication.
