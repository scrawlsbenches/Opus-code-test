Q: What is the difference between a list and a tuple in Python, and when should you use each?
A: Lists and tuples are both sequence types in Python, but they differ fundamentally in mutability. Lists are mutable, meaning you can add, remove, or modify elements after creation, while tuples are immutable and cannot be changed once created. Use lists when you need a collection that will change over time, such as a shopping cart or a dynamic queue. Use tuples for fixed collections like coordinates (x, y), database records, or function return values with multiple components. Tuples also have a slight performance advantage and can be used as dictionary keys since they are hashable, whereas lists cannot.

Q: How does Python's garbage collection work, and what is reference counting?
A: Python uses a combination of reference counting and a cyclic garbage collector for memory management. Reference counting tracks how many references point to each object; when the count drops to zero, the memory is immediately freed. However, reference counting alone cannot handle circular references where objects reference each other. Python's cyclic garbage collector periodically scans for these circular reference groups and frees them when they become unreachable. You can interact with garbage collection using the gc module, though manual intervention is rarely needed. Understanding this system helps when debugging memory leaks or optimizing memory-intensive applications.

Q: What are Python decorators and how do they work under the hood?
A: Decorators are a powerful Python feature that allows you to modify or enhance functions and classes without changing their source code. Under the hood, a decorator is simply a function that takes another function as an argument and returns a new function (or the same function modified). When you use the @decorator syntax, Python automatically passes your function to the decorator and replaces it with the returned value. Common use cases include logging, timing, authentication, caching (like @functools.lru_cache), and enforcing access controls. Decorators can be stacked, and they can accept arguments themselves when implemented as decorator factories using nested functions or classes.

Q: What is the Global Interpreter Lock (GIL) and how does it affect Python performance?
A: The Global Interpreter Lock (GIL) is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on multi-core processors. This means CPU-bound Python code cannot achieve true parallelism using threads alone. The GIL exists to protect CPython's memory management, which uses reference counting that is not thread-safe. For CPU-bound tasks requiring parallelism, use the multiprocessing module to spawn separate Python processes, each with its own GIL. For I/O-bound tasks like network requests or file operations, threading still works well because threads release the GIL while waiting for I/O. Alternative Python implementations like Jython and IronPython do not have a GIL.

Q: What are context managers and why should you use them for resource management?
A: Context managers provide a clean, reliable way to manage resources that need setup and teardown, such as file handles, database connections, or locks. Using the with statement ensures that cleanup code runs even if exceptions occur, preventing resource leaks. You can create custom context managers either by implementing __enter__ and __exit__ methods in a class, or more simply using the @contextlib.contextmanager decorator with a generator function. The pattern is especially important for scarce resources where forgetting to close them can cause system-wide problems. Always prefer context managers over try/finally blocks when managing resources, as they make the code more readable and less error-prone.

Q: How do you properly handle exceptions in Python, and what are common anti-patterns to avoid?
A: Proper exception handling involves catching specific exceptions rather than using bare except clauses, which can mask bugs and catch system-exiting exceptions like KeyboardInterrupt. Always catch the most specific exception type possible and handle different error conditions appropriately. Avoid using exceptions for normal control flow, as they are more expensive than conditional checks. Never silently swallow exceptions without logging or re-raising them, as this makes debugging nearly impossible. Use the else clause in try blocks for code that should run only when no exception occurred, and the finally clause for cleanup that must always run. Consider creating custom exception classes for your application's domain-specific errors to provide clearer error handling.

Q: What is the difference between __str__ and __repr__ in Python classes?
A: Both __str__ and __repr__ are special methods for creating string representations of objects, but they serve different purposes. __repr__ should return an unambiguous string representation that ideally could be used to recreate the object, primarily aimed at developers for debugging. __str__ should return a human-readable, user-friendly representation meant for end-user display. When you use print() or str(), Python calls __str__, but if __str__ is not defined, it falls back to __repr__. In the interactive interpreter and debugger, __repr__ is used. A good practice is to always implement __repr__ and only add __str__ if you need a different user-facing representation. For example, repr(datetime.now()) shows the full constructor call, while str(datetime.now()) shows a clean formatted date.

Q: How do you write effective unit tests in Python using pytest?
A: Effective unit tests follow the Arrange-Act-Assert pattern: set up test data, perform the action being tested, and verify the results. Keep tests isolated and independent so they can run in any order without affecting each other. Use pytest fixtures for shared setup code, and parametrize tests to cover multiple input cases without duplicating code. Mock external dependencies like databases and APIs using unittest.mock or pytest-mock to ensure tests are fast and deterministic. Name tests descriptively to document what behavior they verify, using patterns like test_function_does_something_when_condition. Aim for meaningful coverage rather than 100% line coverage; focus on testing critical paths, edge cases, and error handling. Run tests frequently during development to catch regressions early.

Q: What is the difference between shallow copy and deep copy in Python?
A: Shallow copy creates a new object but inserts references to the same nested objects from the original. Deep copy creates a new object and recursively copies all nested objects, creating completely independent copies. For simple objects without nested structures, both behave the same. The difference matters when you have lists containing lists, dictionaries with mutable values, or objects with object attributes. Use copy.copy() for shallow copies and copy.deepcopy() for deep copies from the copy module. Slicing (list[:]) and list(), dict(), etc., create shallow copies. Deep copying is more expensive in memory and time but necessary when you need to modify nested structures independently. Be aware that deep copy can fail on objects containing uncopyable elements like file handles or database connections.

Q: How do generators work in Python, and when should you use them instead of lists?
A: Generators are functions that yield values one at a time instead of returning a complete list, using the yield keyword instead of return. They implement the iterator protocol lazily, computing each value only when requested, which saves memory when working with large datasets. When you call a generator function, it returns a generator object without executing the function body; execution happens incrementally as you iterate. Use generators when processing large files line by line, implementing infinite sequences, or when you only need to iterate through data once. Generator expressions (similar to list comprehensions but with parentheses) provide a concise syntax for simple generators. The key advantage is O(1) memory usage regardless of sequence length, compared to O(n) for lists.

Q: What are the SOLID principles and how do they apply to Python development?
A: SOLID is an acronym for five object-oriented design principles that lead to maintainable, flexible code. Single Responsibility Principle states that a class should have only one reason to change, keeping classes focused and cohesive. Open/Closed Principle means classes should be open for extension but closed for modification, achieved through inheritance and composition. Liskov Substitution Principle requires that subclasses must be substitutable for their base classes without altering program correctness. Interface Segregation Principle advises creating specific interfaces rather than forcing clients to depend on methods they don't use, though Python's duck typing makes this less rigid. Dependency Inversion Principle suggests depending on abstractions rather than concrete implementations, using dependency injection to decouple components. While Python's dynamic nature makes some principles less strict, following SOLID leads to more testable, reusable code.

Q: How do you debug Python applications effectively beyond using print statements?
A: The built-in pdb debugger lets you set breakpoints, step through code, inspect variables, and evaluate expressions interactively using breakpoint() or import pdb; pdb.set_trace(). IDEs like PyCharm and VS Code provide graphical debuggers with breakpoints, variable watches, and call stack navigation that are more user-friendly. For post-mortem debugging of crashed programs, use python -m pdb script.py or pdb.pm() to examine the state at the crash point. Logging with the logging module provides different severity levels and can be configured to output to files, making it superior to print for production code. The traceback module helps format exception information, and sys.exc_info() provides programmatic access to exception details. For performance issues, use cProfile or the timeit module to identify bottlenecks before optimizing.

Q: What is duck typing in Python, and how does it relate to interfaces and abstract base classes?
A: Duck typing is Python's approach to type checking based on behavior rather than explicit type declarations: "if it walks like a duck and quacks like a duck, it's a duck." This means you can pass any object to a function as long as it has the required methods or attributes, regardless of its actual class. While this provides flexibility, it can lead to runtime errors if objects lack expected behavior. Abstract Base Classes (ABCs) from the abc module provide a middle ground, defining interfaces that classes must implement without dictating the implementation details. ABCs use @abstractmethod to declare methods that subclasses must override, raising TypeError if they don't. You can also register virtual subclasses to maintain duck typing flexibility while adding optional type checking. Many built-in types are defined through ABCs in collections.abc, like Iterable, Sequence, and Mapping.

Q: What are common Python performance optimization techniques?
A: Start by profiling with cProfile or line_profiler to identify actual bottlenecks rather than guessing, as premature optimization wastes time and reduces readability. Use built-in functions and data structures, which are implemented in C and highly optimized; for example, sum() is faster than manual loops, and sets provide O(1) membership testing. List comprehensions and generator expressions are faster than equivalent for loops with append. For numerical computing, use NumPy arrays instead of Python lists for vectorized operations that are orders of magnitude faster. Memoization with @functools.lru_cache automatically caches function results for expensive repeated calculations. Avoid global variable lookups in tight loops by assigning them to local variables. Consider using __slots__ in classes to reduce memory usage and slightly improve attribute access speed. For truly performance-critical code, consider Cython or writing C extensions.

Q: How do you manage dependencies and virtual environments in Python projects?
A: Virtual environments isolate project dependencies, preventing conflicts between projects that require different package versions. Create them with python -m venv venv_name or virtualenv, and activate with source venv/bin/activate on Unix or venv\Scripts\activate on Windows. Track dependencies in requirements.txt using pip freeze, or preferably use pip-tools to separate direct dependencies from their transitive dependencies. For more robust dependency management, tools like Poetry or Pipenv provide lock files for reproducible builds, dependency resolution, and combined virtual environment management. Always pin exact versions in production requirements to avoid unexpected breaking changes. Consider using pyproject.toml as the modern standard for project metadata and build configuration. Docker can provide even stronger isolation for deployment, ensuring consistent environments across development and production.
