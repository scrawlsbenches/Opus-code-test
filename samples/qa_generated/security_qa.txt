Q: What is SQL injection and how can developers prevent it?
A: SQL injection is a code injection technique where attackers insert malicious SQL statements into application queries through user input fields. This vulnerability occurs when user-supplied data is concatenated directly into SQL queries without proper sanitization. Attackers can exploit this to bypass authentication, extract sensitive data, modify database contents, or even execute administrative operations. Prevention strategies include using parameterized queries (prepared statements), employing stored procedures, implementing input validation with allowlists, applying the principle of least privilege to database accounts, and using ORM frameworks that handle query construction safely. Modern web frameworks provide built-in protection, but developers must still be vigilant when writing raw SQL queries.

Q: What are the OWASP Top 10 vulnerabilities and why are they important?
A: The OWASP Top 10 is a regularly updated list of the most critical web application security risks, maintained by the Open Web Application Security Project. The current categories include Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable and Outdated Components, Identification and Authentication Failures, Software and Data Integrity Failures, Security Logging and Monitoring Failures, and Server-Side Request Forgery. This list is important because it represents a consensus among security experts about the most prevalent and dangerous vulnerabilities affecting web applications. Organizations use the OWASP Top 10 as a baseline for security testing, developer training, and compliance requirements. Understanding these vulnerabilities helps development teams prioritize security efforts and allocate resources effectively.

Q: How does Cross-Site Scripting (XSS) work and what are its different types?
A: Cross-Site Scripting occurs when an attacker injects malicious scripts into web pages viewed by other users, exploiting the trust a user has for a particular website. There are three main types: Stored XSS persists on the target server in databases or message forums, affecting all users who view the compromised content. Reflected XSS occurs when malicious scripts are reflected off a web server through error messages, search results, or other responses that include user input. DOM-based XSS happens when the vulnerability exists in client-side code rather than server-side, manipulating the Document Object Model directly. Prevention measures include encoding output data, validating and sanitizing input, implementing Content Security Policy headers, using HTTPOnly cookies to protect session data, and employing modern frameworks that automatically escape output.

Q: What is Cross-Site Request Forgery (CSRF) and how do anti-CSRF tokens work?
A: Cross-Site Request Forgery is an attack that forces authenticated users to execute unwanted actions on a web application where they are currently authenticated. The attacker tricks the victim into submitting a malicious request, leveraging the user's existing session with the target site. For example, a hidden form on a malicious website could transfer funds from a victim's bank account if they happen to be logged into that bank. Anti-CSRF tokens work by including a unique, unpredictable value in each form or request that the server verifies before processing. These tokens are tied to the user's session and change with each request or session, making it impossible for attackers to forge valid requests. Additional defenses include checking the Referer header, using SameSite cookie attributes, and requiring re-authentication for sensitive operations.

Q: What is the principle of least privilege and how does it apply to secure coding?
A: The principle of least privilege states that every program, user, and system component should operate using the minimum set of privileges necessary to complete its intended function. In secure coding, this means applications should request only the permissions they need, database connections should use accounts with restricted access, API keys should have limited scopes, and file system operations should be confined to specific directories. This principle reduces the attack surface by limiting what an attacker can accomplish even if they successfully exploit a vulnerability. Implementation includes creating separate database users for read and write operations, running services under dedicated non-root accounts, using capability-based security models, and regularly auditing permissions to remove unnecessary access rights.

Q: How should passwords be securely stored in a database?
A: Passwords should never be stored in plaintext or using reversible encryption. Instead, they should be hashed using a modern, slow hashing algorithm specifically designed for passwords, such as Argon2, bcrypt, or scrypt. These algorithms are intentionally computationally expensive to make brute-force attacks impractical. Each password should be hashed with a unique, randomly generated salt to prevent rainbow table attacks and ensure identical passwords produce different hashes. The salt should be stored alongside the hash. Additional security measures include setting minimum password complexity requirements, implementing rate limiting on login attempts, supporting multi-factor authentication, and using pepper (a secret key added to passwords before hashing) stored separately from the database. Regular security audits should verify that password storage meets current best practices.

Q: What is a penetration test and what are the main phases involved?
A: A penetration test is an authorized simulated cyberattack performed to evaluate the security of a system by attempting to exploit vulnerabilities just as a malicious attacker would. The main phases include reconnaissance (gathering information about the target through passive and active methods), scanning (identifying live hosts, open ports, and running services), vulnerability assessment (identifying potential weaknesses using automated tools and manual techniques), exploitation (attempting to compromise systems using discovered vulnerabilities), post-exploitation (determining the value of compromised systems and maintaining access), and reporting (documenting findings, risk levels, and remediation recommendations). Penetration tests can be black-box (no prior knowledge), white-box (full system knowledge), or gray-box (partial knowledge). Regular penetration testing helps organizations identify security gaps before malicious actors can exploit them.

Q: What is encryption and what is the difference between symmetric and asymmetric encryption?
A: Encryption is the process of converting plaintext data into ciphertext using an algorithm and key, making the data unreadable to unauthorized parties. Symmetric encryption uses the same key for both encryption and decryption, making it fast and efficient for large amounts of data, with algorithms like AES being widely used. The main challenge is securely sharing the key between parties. Asymmetric encryption uses a mathematically related key pair: a public key for encryption and a private key for decryption. This solves the key distribution problem since the public key can be shared openly, but it is computationally more expensive. Common asymmetric algorithms include RSA and elliptic curve cryptography. In practice, hybrid systems combine both: asymmetric encryption securely exchanges a symmetric session key, which then encrypts the actual data.

Q: What is input validation and why is it critical for application security?
A: Input validation is the process of verifying that user-supplied data meets expected criteria before the application processes it. This practice is critical because most attacks exploit applications that trust user input implicitly. Validation should occur on both client-side (for user experience) and server-side (for security, as client-side validation can be bypassed). Effective validation includes checking data type, length, format, and range; using allowlists rather than blocklists when possible; encoding or escaping special characters based on context; and rejecting invalid input rather than attempting to sanitize it. Input validation prevents injection attacks, buffer overflows, and many other vulnerability classes. It should be applied consistently across all entry points including form fields, URL parameters, HTTP headers, cookies, and API endpoints.

Q: What are security headers and which ones should every web application implement?
A: Security headers are HTTP response headers that instruct browsers to enable specific security features, adding layers of protection against common attacks. Essential headers include Content-Security-Policy (CSP), which prevents XSS by specifying allowed sources for scripts, styles, and other resources. X-Content-Type-Options with the nosniff value prevents MIME type sniffing attacks. X-Frame-Options or the frame-ancestors CSP directive protects against clickjacking by controlling whether the page can be embedded in frames. Strict-Transport-Security (HSTS) enforces HTTPS connections and prevents protocol downgrade attacks. X-XSS-Protection enables browser-based XSS filtering (though modern CSP is preferred). Referrer-Policy controls how much referrer information is included with requests. These headers provide defense-in-depth and should be configured based on the application's specific requirements and functionality.

Q: What is a security audit and how does it differ from a penetration test?
A: A security audit is a comprehensive, systematic evaluation of an organization's information systems, policies, and procedures against established standards or regulatory requirements. It examines documentation, configurations, access controls, and operational practices through interviews, observations, and technical reviews. Security audits are typically broader in scope than penetration tests, covering governance, risk management, compliance, physical security, and personnel policies in addition to technical controls. While penetration tests focus on actively exploiting vulnerabilities to demonstrate impact, audits assess whether proper security controls exist and are functioning as intended. Audits often result in compliance certifications and are conducted by internal teams or third-party auditors. Organizations typically need both: audits ensure security frameworks and processes are in place, while penetration tests validate that technical defenses actually work against real-world attack techniques.

Q: What is secure session management and what are common session-related vulnerabilities?
A: Secure session management involves properly creating, maintaining, and destroying user sessions to prevent unauthorized access. Sessions should use strong, randomly generated identifiers that are sufficiently long to resist brute-force attacks. Common vulnerabilities include session fixation (attacker sets a known session ID before authentication), session hijacking (stealing valid session tokens through XSS or network interception), insufficient session expiration (sessions remaining valid too long), and insecure session storage. Best practices include regenerating session IDs after authentication and privilege changes, setting appropriate timeout values for both idle and absolute session duration, transmitting session tokens only over HTTPS, using HTTPOnly and Secure cookie flags, implementing proper logout functionality that invalidates sessions server-side, and binding sessions to additional attributes like IP address or user agent fingerprint where appropriate.

Q: What is the Secure Development Lifecycle (SDL) and what are its key phases?
A: The Secure Development Lifecycle is a software development process that integrates security practices at every stage rather than treating security as an afterthought. Key phases include security training for development teams, requirements gathering that includes security requirements and abuse cases, secure design incorporating threat modeling and attack surface analysis, secure implementation following coding standards and using approved libraries, security testing including static analysis, dynamic testing, and code review, and secure deployment with hardened configurations and incident response planning. Post-release activities include vulnerability management, patch deployment, and continuous monitoring. The SDL reduces vulnerabilities by addressing security early when fixes are less expensive, creates documentation for compliance requirements, and establishes consistent security practices across projects. Popular frameworks include Microsoft SDL, OWASP SAMM, and BSIMM.

Q: What is threat modeling and how is it performed?
A: Threat modeling is a structured approach to identifying, quantifying, and addressing security threats to an application or system during the design phase. The process typically involves defining security objectives and the scope of analysis, creating a visual representation of the system architecture including data flows and trust boundaries, identifying potential threats using frameworks like STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), rating threats based on likelihood and impact using methods like DREAD, and determining appropriate countermeasures or accepting residual risk. Threat modeling should be iterative, updated when the system design changes significantly, and involve stakeholders from development, security, and operations. By identifying threats early in development, teams can implement security controls proactively rather than reactively patching vulnerabilities after deployment.

Q: What are the best practices for API security?
A: API security requires multiple layers of protection since APIs expose application logic and sensitive data directly. Authentication should use robust mechanisms like OAuth 2.0 with JWT tokens rather than API keys alone, and all endpoints should verify user identity. Authorization must enforce access controls at each endpoint, validating that authenticated users have permission for requested operations. Input validation should be strict, with schemas defining expected request formats. Rate limiting and throttling prevent abuse and denial-of-service attacks. Transport security requires TLS for all communications, with proper certificate validation. APIs should return minimal error information to avoid leaking implementation details. Logging should capture security-relevant events without exposing sensitive data. Versioning helps manage security updates, and deprecated versions should be sunset promptly. Regular security testing, including automated scanning and manual review, should verify that security controls function correctly across all API endpoints.
