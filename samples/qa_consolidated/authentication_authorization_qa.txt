Q: What is OAuth 2.0 and how does it differ from simple password-based authentication?
A: OAuth 2.0 is an authorization framework that enables third-party applications to obtain limited access to user accounts without exposing user credentials. Unlike password-based authentication where credentials are shared directly with each application, OAuth 2.0 uses access tokens issued by an authorization server. This delegation model allows users to grant specific permissions to applications while maintaining control over their credentials. The framework supports multiple grant types including authorization code, client credentials, and refresh tokens for different use cases.

Q: How does OpenID Connect extend OAuth 2.0 for authentication purposes?
A: OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0 that adds standardized authentication capabilities. While OAuth 2.0 only handles authorization (what you can access), OIDC adds authentication (who you are) by introducing the ID token, a JSON Web Token containing user identity claims. OIDC defines standard scopes like openid, profile, and email, along with a UserInfo endpoint for retrieving additional user attributes. This combination provides a complete solution for both verifying user identity and obtaining authorization for resource access.

Q: What are the three parts of a JSON Web Token (JWT) and what purpose does each serve?
A: A JWT consists of three Base64URL-encoded parts separated by dots: the header, payload, and signature. The header specifies the token type and the cryptographic algorithm used for signing, such as HS256 or RS256. The payload contains the claims, which are statements about the user and additional metadata like expiration time, issuer, and audience. The signature is created by signing the encoded header and payload with a secret key, ensuring the token's integrity and authenticity cannot be tampered with without detection.

Q: What are the key differences between session-based authentication and token-based authentication?
A: Session-based authentication stores user state on the server, creating a session ID that is sent to the client as a cookie and referenced on subsequent requests. Token-based authentication is stateless, with the server issuing a self-contained token that the client stores and sends with each request, requiring no server-side session storage. Session-based approaches are simpler to implement and allow easy session invalidation, while token-based systems scale better horizontally since any server can validate the token. Token-based authentication is preferred for APIs and microservices, while sessions remain common for traditional web applications.

Q: When should API keys be used for authentication, and what are their limitations?
A: API keys are best suited for server-to-server communication, rate limiting, and identifying calling applications rather than authenticating individual users. They provide a simple mechanism for tracking API usage and enforcing quotas without the complexity of OAuth flows. However, API keys have significant limitations: they typically don't expire, cannot be easily scoped to specific permissions, and if compromised, require regeneration which affects all integrations using that key. API keys should never be used in client-side code or mobile apps where they can be extracted, and should always be transmitted over HTTPS.

Q: How does Role-Based Access Control (RBAC) differ from Attribute-Based Access Control (ABAC)?
A: RBAC assigns permissions to roles, and users are granted roles that determine their access rights, making it straightforward to manage and audit but relatively inflexible for complex scenarios. ABAC evaluates access decisions based on attributes of the user, resource, action, and environment, enabling fine-grained policies like "managers can approve expenses under $10,000 during business hours." RBAC is easier to implement and understand, working well for organizations with clear hierarchical structures and static permission requirements. ABAC provides greater flexibility and can express complex business rules but requires more sophisticated policy engines and can be harder to audit and troubleshoot.

Q: What is Single Sign-On (SSO) and what protocols commonly implement it?
A: Single Sign-On allows users to authenticate once and gain access to multiple related but independent applications without re-entering credentials. SSO improves user experience by reducing password fatigue and login friction while centralizing authentication management for security teams. Common protocols implementing SSO include SAML 2.0 for enterprise environments, OpenID Connect for modern web and mobile applications, and Kerberos for Windows domain environments. The identity provider (IdP) handles authentication and issues tokens or assertions that service providers (SPs) accept, creating a trust relationship that enables seamless access across applications.

Q: What are the different factors in Multi-Factor Authentication (MFA) and why is it more secure?
A: MFA requires users to provide two or more verification factors from different categories: something you know (passwords, PINs), something you have (phones, hardware tokens), and something you are (biometrics like fingerprints or facial recognition). This layered approach significantly increases security because compromising one factor doesn't grant access; an attacker would need to compromise multiple independent factors simultaneously. Time-based One-Time Passwords (TOTP), SMS codes, push notifications, and hardware security keys like YubiKeys are common second factors. MFA is particularly critical for protecting sensitive accounts and has become a baseline security requirement for most organizations.

Q: How does SAML work for enterprise single sign-on, and what are its main components?
A: SAML (Security Assertion Markup Language) is an XML-based standard for exchanging authentication and authorization data between an identity provider and service providers. The flow typically begins when a user accesses a service provider, which redirects them to the identity provider for authentication. After successful authentication, the IdP generates a SAML assertion containing user attributes and digitally signs it before redirecting the user back to the SP. The service provider validates the signature, extracts user information from the assertion, and establishes a local session. SAML's XML-based assertions and reliance on browser redirects make it well-suited for enterprise web applications but less ideal for mobile or API scenarios.

Q: Why is bcrypt preferred over simple hashing algorithms like MD5 or SHA-256 for password storage?
A: Bcrypt is specifically designed for password hashing with built-in features that make brute-force attacks computationally expensive. Unlike MD5 or SHA-256 which are designed to be fast, bcrypt incorporates a configurable work factor that determines the computational cost, allowing security teams to increase difficulty as hardware improves. Bcrypt also automatically handles salt generation and storage, preventing rainbow table attacks and ensuring identical passwords produce different hashes. The algorithm's intentional slowness means even with powerful hardware, attackers can only test a limited number of password guesses per second, making it impractical to crack strong passwords.

Q: How does Argon2 improve upon bcrypt for modern password hashing requirements?
A: Argon2, winner of the Password Hashing Competition in 2015, addresses limitations of bcrypt by being resistant to both GPU and ASIC-based attacks through its memory-hard design. The algorithm requires a configurable amount of memory during computation, making parallel attacks on specialized hardware prohibitively expensive since memory is harder to scale than raw computation. Argon2 comes in three variants: Argon2d optimized against GPU attacks, Argon2i optimized against side-channel attacks, and Argon2id combining both protections for general use. Its tunable parameters for time cost, memory cost, and parallelism allow security teams to balance security requirements against user experience on their specific hardware.

Q: What is the purpose of refresh tokens in OAuth 2.0, and how should they be handled securely?
A: Refresh tokens allow applications to obtain new access tokens without requiring users to re-authenticate, enabling short-lived access tokens while maintaining long user sessions. When an access token expires, the application sends the refresh token to the authorization server to receive a new access token, potentially with a new refresh token as well (refresh token rotation). Refresh tokens should be stored securely, never in browser localStorage or sessionStorage where JavaScript can access them; HTTP-only cookies or secure server-side storage are preferred. Implementing refresh token rotation and absolute expiration times limits the damage if a refresh token is compromised, and applications should handle token revocation gracefully.

Q: What is PKCE and why is it essential for public clients like mobile and single-page applications?
A: PKCE (Proof Key for Code Exchange) is an extension to the OAuth 2.0 authorization code flow that protects against authorization code interception attacks. Public clients cannot securely store client secrets, making them vulnerable to attackers who intercept the authorization code during the redirect back from the authorization server. PKCE works by having the client generate a random code verifier and its transformed code challenge sent with the authorization request. When exchanging the authorization code for tokens, the client sends the original code verifier, which the server validates against the stored challenge. This ensures that only the client that initiated the flow can complete it, even if the authorization code is intercepted.

Q: What security considerations should guide the choice of JWT signing algorithms?
A: The choice between symmetric (HS256) and asymmetric (RS256, ES256) algorithms depends on the trust model and architecture of the system. Symmetric algorithms use a shared secret, requiring both token issuer and validator to possess the same key, suitable for single-service scenarios but problematic when multiple services need to validate tokens. Asymmetric algorithms use public/private key pairs where only the issuer holds the private key for signing, while any service can validate using the public key. The "none" algorithm should always be explicitly rejected to prevent signature bypass attacks, and systems should validate the "alg" header against an allowlist rather than trusting the token's declared algorithm.

Q: How can token revocation be implemented effectively in stateless JWT-based systems?
A: While JWTs are designed to be stateless and self-validating, real-world systems often need to revoke tokens before expiration for security events like password changes or logout. Common approaches include maintaining a token blacklist or blocklist that is checked during validation, though this reintroduces state and can impact performance. Using short-lived access tokens (5-15 minutes) combined with refresh tokens reduces the window of vulnerability since compromised access tokens quickly expire. Token versioning or "jti" (JWT ID) claims combined with a revocation list, or storing a "valid_after" timestamp per user that invalidates all tokens issued before a certain time, provide practical compromise solutions for balancing security with stateless architecture benefits.
