Q: What is cache invalidation and why is it considered one of the hardest problems in computer science?
A: Cache invalidation is the process of removing or updating stale data from a cache when the underlying source data changes. It is notoriously difficult because determining exactly when cached data becomes stale requires coordination between the cache and data source, and incorrect invalidation can lead to users seeing outdated information or, conversely, unnecessary cache misses that defeat the purpose of caching. The challenge grows exponentially in distributed systems where multiple cache nodes must be kept consistent, and timing issues can cause race conditions where invalidation messages arrive out of order.

Q: How does write-through caching work and what are its primary advantages and disadvantages?
A: Write-through caching writes data to both the cache and the underlying storage simultaneously on every write operation. The primary advantage is strong data consistency since the cache and storage are always synchronized, making it ideal for applications where data integrity is critical. However, the main disadvantage is increased write latency because every write must wait for the slower storage operation to complete, which can significantly impact performance in write-heavy workloads.

Q: What distinguishes write-back caching from write-through, and when should each be used?
A: Write-back caching initially writes data only to the cache and defers the write to underlying storage until later, typically when the cache line is evicted or during periodic flushes. This approach offers significantly better write performance since applications do not wait for slow storage operations, making it ideal for write-intensive workloads. However, write-back introduces a risk of data loss if the system crashes before dirty cache entries are persisted, so it should be avoided when data durability is paramount and preferred when performance is prioritized over absolute consistency.

Q: What is write-around caching and in what scenarios does it provide benefits?
A: Write-around caching writes data directly to the underlying storage while bypassing the cache entirely, with the cache only being populated on subsequent reads. This strategy is beneficial when written data is unlikely to be read soon after writing, as it prevents cache pollution with data that may never be accessed again. It works particularly well for logging systems, bulk data imports, or backup operations where caching recently written data would waste valuable cache space and potentially evict more frequently accessed data.

Q: How do TTL (Time-To-Live) strategies work in caching and what factors influence optimal TTL selection?
A: TTL strategies automatically expire cached data after a predetermined time period, forcing a refresh from the source on the next access. Optimal TTL selection depends on how frequently the underlying data changes, the cost of serving stale data, and the load that cache misses place on the origin system. Short TTLs provide fresher data but increase origin load, while longer TTLs improve cache hit rates but risk serving outdated information. Many systems use adaptive TTL approaches that adjust expiration times based on observed data change patterns or access frequency.

Q: What is the LRU (Least Recently Used) cache eviction policy and how does it determine which items to remove?
A: LRU eviction removes the cache entry that has not been accessed for the longest period of time when the cache reaches capacity and needs to make room for new entries. The algorithm maintains access timestamps or ordering for all cached items, typically implemented using a combination of a hash map for O(1) lookups and a doubly-linked list for O(1) reordering. LRU works well for workloads with temporal locality where recently accessed items are likely to be accessed again, but it can perform poorly when access patterns include periodic scans of large datasets.

Q: How does LFU (Least Frequently Used) eviction differ from LRU, and what are its strengths and weaknesses?
A: LFU eviction removes the cache entry with the lowest access count rather than the oldest access time, preserving items that have been accessed many times over a longer period. This approach excels when some items are consistently popular and should remain cached even if not accessed in the immediate past, making it suitable for content delivery or product catalogs with stable popularity distributions. However, LFU can struggle with changing access patterns since previously popular items accumulate high counts that prevent eviction even when they are no longer relevant, leading many implementations to use frequency decay or hybrid LRU-LFU approaches.

Q: What is distributed caching and what challenges does it introduce compared to single-node caching?
A: Distributed caching spreads cached data across multiple nodes to increase capacity, improve availability, and enable horizontal scaling beyond what a single server can handle. This architecture introduces challenges including determining which node holds a particular cache entry (typically solved with consistent hashing), maintaining consistency when the same data could be cached on multiple nodes, and handling node failures without losing cached data or creating hotspots. Network latency between nodes also becomes a factor, and cache invalidation becomes more complex as updates must propagate to all nodes that might hold copies of the affected data.

Q: What is a cache stampede and what techniques can prevent it?
A: A cache stampede occurs when a popular cache entry expires and multiple concurrent requests simultaneously attempt to regenerate the cached value, potentially overwhelming the backend system with duplicate expensive computations or database queries. Prevention techniques include cache locking where only one request regenerates the value while others wait, probabilistic early expiration where entries are refreshed before actual expiration with some randomness to spread regeneration load, and stale-while-revalidate patterns where the old value is served while a single background process updates the cache. Some systems also use request coalescing to deduplicate simultaneous requests for the same uncached key.

Q: What is cache warming and when is it beneficial to implement?
A: Cache warming is the process of proactively populating a cache with anticipated data before actual user requests arrive, rather than waiting for cache misses to trigger data loading. This technique is particularly valuable after system restarts, deployments, or cache server additions where an empty cache would cause a sudden spike in backend load as users encounter cache misses. Effective cache warming strategies analyze access logs to identify frequently requested data, use predictive models based on time-of-day patterns, or pre-populate with data that is known to be needed based on application logic such as loading product information before a scheduled sale begins.

Q: How does CDN (Content Delivery Network) caching differ from application-level caching?
A: CDN caching operates at the network edge, storing content on geographically distributed servers close to end users to reduce latency and offload traffic from origin servers. Unlike application-level caching which typically handles dynamic data with complex invalidation logic, CDN caching focuses primarily on static assets like images, CSS, and JavaScript files, though modern CDNs increasingly support dynamic content caching with varying TTLs. CDN cache behavior is controlled through HTTP headers like Cache-Control and varies headers, and invalidation usually requires explicit purge requests through CDN APIs since the CDN cannot automatically detect origin changes.

Q: What HTTP headers control browser caching behavior and how do they interact?
A: The primary browser caching headers are Cache-Control, which specifies directives like max-age, no-cache, and private/public; ETag, which provides a validator for conditional requests; and Last-Modified, which indicates when the resource last changed. Cache-Control max-age tells browsers how long to use a cached response without revalidation, while no-cache requires revalidation on every use but still allows storing. When cached content expires or no-cache is specified, browsers send conditional requests using If-None-Match (with ETag) or If-Modified-Since (with Last-Modified), allowing servers to respond with 304 Not Modified to avoid transferring unchanged content.

Q: What are the key differences between Redis and Memcached for caching use cases?
A: Redis offers richer data structures including lists, sets, sorted sets, and hashes, plus features like persistence, replication, and Lua scripting, making it suitable for complex caching scenarios and as a primary data store. Memcached provides a simpler key-value model optimized purely for caching with excellent multi-threaded performance and predictable memory usage through its slab allocation system. Redis is typically chosen when cache data needs persistence, complex operations, or pub/sub messaging, while Memcached excels in simpler high-throughput caching scenarios where its lighter weight and multi-core utilization provide performance advantages.

Q: How can cache hit rate be monitored and what metrics indicate caching effectiveness?
A: Cache hit rate, calculated as hits divided by total requests, is the primary metric for cache effectiveness, with higher rates indicating better performance and reduced backend load. Additional important metrics include cache latency for hits versus misses, eviction rates which indicate if the cache is sized appropriately, and memory utilization to track capacity usage. Effective monitoring also tracks miss rates by key patterns to identify candidates for longer TTLs or prefetching, and monitors backend load during cache failures to understand dependency risks. A sudden drop in hit rate often signals issues like changed access patterns, cache server problems, or deployment-related cache clearing.

Q: What strategies help maintain cache consistency in microservices architectures?
A: In microservices architectures, cache consistency can be maintained through event-driven invalidation where services publish data change events that trigger cache updates across consuming services. Another approach uses the cache-aside pattern where each service manages its own cache with explicit invalidation logic when receiving relevant events. Some systems implement distributed cache invalidation through message queues or dedicated invalidation services that coordinate cache clearing across service boundaries. The key is accepting that perfect consistency is often impossible and designing for eventual consistency with appropriate TTLs and monitoring to detect and recover from inconsistencies.
