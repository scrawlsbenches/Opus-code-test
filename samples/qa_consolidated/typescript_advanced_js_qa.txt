TypeScript and Advanced JavaScript Q&A

Q: How does TypeScript's type inference work, and when should you rely on it versus explicit type annotations?
A: TypeScript's type inference automatically deduces types based on variable initialization, return statements, and contextual typing from surrounding code. The compiler analyzes the right-hand side of assignments and function return paths to determine the most specific type possible. You should rely on inference for simple cases like primitive initializations and obvious return types, but use explicit annotations for function parameters, complex object shapes, public API boundaries, and when the inferred type is broader than intended. Explicit types also improve code documentation and catch errors earlier at assignment rather than at usage.

Q: What are generics in TypeScript, and how do they enable writing reusable, type-safe code?
A: Generics are type parameters that allow you to create components that work with multiple types while maintaining type safety throughout operations. They act as placeholders that get replaced with actual types when the generic function, class, or interface is used, enabling the compiler to track and enforce type relationships. For example, a generic function like `function identity<T>(arg: T): T` preserves the input type in its return type, unlike using `any` which loses type information. Generics support constraints via `extends`, default types, and multiple type parameters, making them essential for building flexible libraries and data structures like typed arrays, maps, and promise chains.

Q: How do union and intersection types differ, and what are practical use cases for each?
A: Union types (A | B) represent values that can be one of several types, requiring you to narrow the type before accessing type-specific properties, while intersection types (A & B) combine multiple types into one that has all properties from each constituent type. Unions are ideal for function parameters that accept multiple input types, discriminated unions for state management, and representing nullable values without strict null checks. Intersections excel at composing object types through mixins, adding properties to existing types, and combining interfaces for objects that must satisfy multiple contracts simultaneously. The key distinction is that unions expand possibilities (this OR that) while intersections constrain them (this AND that).

Q: What are mapped types in TypeScript, and how can you use them to transform existing types?
A: Mapped types iterate over the keys of a type to produce a new type with transformed properties, using the syntax `{ [K in keyof T]: NewType }`. They enable powerful transformations like making all properties optional (`Partial<T>`), readonly (`Readonly<T>`), or changing value types uniformly across an object type. You can combine mapped types with conditional types and template literal types for sophisticated transformations, such as prefixing all keys or filtering properties by type. Key modifiers like `+` and `-` with `readonly` and `?` allow adding or removing property modifiers, enabling transformations like `Required<T>` which removes optionality from all properties.

Q: How do conditional types work in TypeScript, and what problems do they solve?
A: Conditional types use the syntax `T extends U ? X : Y` to select types based on type relationships, enabling type-level programming similar to ternary expressions at runtime. They become particularly powerful with the `infer` keyword, which extracts types from complex structures like function parameters, return types, or array elements. Conditional types solve problems like extracting the element type from an array (`T extends Array<infer E> ? E : never`), unwrapping promises, and creating type-safe utility functions that adapt their return types based on input. They also distribute over union types when the checked type is a naked type parameter, allowing transformations to apply to each union member individually.

Q: What are TypeScript decorators, and how do they integrate with the class system?
A: Decorators are special declarations prefixed with `@` that attach metadata to classes, methods, properties, accessors, or parameters, executing at decoration time rather than runtime instantiation. They receive reflection information about their target and can modify or replace the decorated element, enabling patterns like dependency injection, validation, logging, and ORM mapping. Class decorators receive the constructor function, method decorators receive the prototype and property key, and property decorators enable metadata attachment for frameworks like Angular or TypeORM. With the TC39 Stage 3 decorator proposal now supported, TypeScript offers both legacy experimental decorators and the newer standard syntax with different semantics and capabilities.

Q: How do modules and namespaces differ in TypeScript, and when should each be used?
A: Modules are file-based units using ES6 import/export syntax that create isolated scopes, while namespaces (formerly internal modules) use the `namespace` keyword to organize code within a single scope that can span multiple files. Modules are the modern standard for organizing TypeScript code, benefiting from tree-shaking, lazy loading, and integration with bundlers like webpack and Rollup. Namespaces remain useful for organizing type declarations in ambient contexts (`.d.ts` files), global script code in non-module environments, and declaration merging scenarios. For new projects, modules should be the default choice as they align with ECMAScript standards and provide better tooling support for dead code elimination and code splitting.

Q: What does TypeScript's strict mode enable, and why is it recommended for new projects?
A: TypeScript's strict mode (`"strict": true` in tsconfig.json) activates a collection of rigorous type-checking options including `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `useUnknownInCatchVariables`, and `alwaysStrict`. These flags collectively catch common bugs like accessing potentially null values, implicit any types that bypass type checking, and incorrect function signature compatibility. Strict mode forces developers to handle edge cases explicitly, resulting in more robust code with fewer runtime errors. Starting a project with strict mode prevents the accumulation of technical debt that occurs when retrofitting strictness onto a permissive codebase with thousands of new errors to address.

Q: What are TypeScript's built-in utility types, and which ones are most commonly used?
A: TypeScript provides numerous utility types that transform existing types without manual type definitions, with `Partial<T>` making all properties optional, `Required<T>` making them mandatory, `Readonly<T>` preventing mutation, and `Pick<K>` and `Omit<K>` selecting or excluding specific properties. `Record<K, V>` creates object types with specified key and value types, useful for dictionaries and lookup tables. `ReturnType<T>` and `Parameters<T>` extract function return types and parameter tuples respectively, enabling type-safe higher-order functions. `NonNullable<T>` removes null and undefined from unions, `Extract<T, U>` and `Exclude<T, U>` filter union members, and `Awaited<T>` unwraps Promise types recursively for async code.

Q: What are type guards in TypeScript, and how do you create custom ones?
A: Type guards are expressions that perform runtime checks and narrow types within conditional blocks, allowing TypeScript to understand that a value is a more specific type after the check. Built-in type guards include `typeof` for primitives, `instanceof` for class instances, and `in` for property existence checks on objects. Custom type guards use the return type predicate syntax `parameterName is Type`, requiring a function that returns a boolean and performs the actual runtime validation. For example, `function isString(value: unknown): value is string { return typeof value === 'string'; }` creates a reusable guard that narrows `unknown` to `string`. Discriminated unions with a common literal property enable exhaustive pattern matching with type narrowing in switch statements.

Q: What are declaration files (.d.ts), and how do they enable TypeScript to work with JavaScript libraries?
A: Declaration files contain only type information without implementation code, describing the shape of JavaScript libraries so TypeScript can provide type checking and IntelliSense for code written in plain JavaScript. They use the `.d.ts` extension and include type declarations for variables, functions, classes, modules, and namespaces that exist at runtime but were not written in TypeScript. The DefinitelyTyped repository (@types packages on npm) provides community-maintained declarations for thousands of popular libraries like React, Lodash, and Node.js. You can generate declaration files automatically from TypeScript source using the `declaration` compiler option, or write them manually for JavaScript libraries using ambient declarations with the `declare` keyword for variables, functions, and modules.

Q: How does TypeScript handle the 'this' keyword, and what is the 'noImplicitThis' flag?
A: TypeScript tracks the type of `this` in functions and methods, with class methods automatically having `this` typed to the class instance, while standalone functions have `this` typed as `any` by default unless explicitly annotated. The `noImplicitThis` flag (included in strict mode) raises errors when `this` has an implicit `any` type, forcing explicit `this` parameter annotations in functions where context binding is unclear. You can declare a fake `this` parameter as the first parameter of a function (`function fn(this: SomeType, arg: string)`) to specify the expected `this` context without affecting runtime behavior. Arrow functions lexically capture `this` from their enclosing scope, making them useful for callbacks while avoiding binding issues, but they cannot have explicit `this` type annotations.

Q: What are template literal types in TypeScript, and how do they enable string manipulation at the type level?
A: Template literal types use the same syntax as JavaScript template literals but operate on string literal types, enabling type-level string manipulation and pattern matching with syntax like `type Greeting = \`Hello, ${string}\``. They can combine with union types to generate all possible combinations, useful for creating typed event names, CSS property keys, or API endpoint paths. Intrinsic string manipulation types including `Uppercase<T>`, `Lowercase<T>`, `Capitalize<T>`, and `Uncapitalize<T>` transform string literal types, enabling conventions like converting 'get' + 'Name' to 'getName'. Combined with mapped types and conditional types, template literal types enable advanced patterns like inferring parts of strings, validating string formats at compile time, and creating strongly-typed builders for query strings or route parameters.

Q: How does TypeScript's structural typing differ from nominal typing, and what are the implications?
A: TypeScript uses structural typing (also called duck typing) where type compatibility is determined by the shape of types rather than their declared names, meaning two types are compatible if they have the same structure regardless of whether they were declared separately. This differs from nominal typing (used in Java or C#) where types must be explicitly declared as compatible or share an inheritance relationship. Structural typing enables flexibility with object literals and makes TypeScript interoperable with JavaScript patterns, but it can cause issues when you want distinct types with identical structures, like UserId and OrderId both being strings. You can simulate nominal typing using branded types (intersecting with a unique symbol property) or the satisfies operator with opaque type patterns when semantic distinction between structurally identical types is important for domain modeling.

Q: What is the 'unknown' type in TypeScript, and how does it differ from 'any'?
A: The `unknown` type represents any value like `any`, but requires type narrowing before performing operations on it, making it the type-safe counterpart to `any` for handling values of uncertain type. While `any` disables type checking entirely and allows any operation, `unknown` forces you to verify the type through type guards, assertions, or control flow narrowing before accessing properties or calling methods. This makes `unknown` ideal for function parameters that accept arbitrary input, JSON parsing results, or catch clause variables where the value type is genuinely uncertain. Using `unknown` instead of `any` maintains type safety discipline by requiring explicit type verification, catching potential runtime errors at compile time and documenting the assumption that type checking is needed before use.
