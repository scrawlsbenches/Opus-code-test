Q: What are window functions in SQL and how do they differ from aggregate functions?
A: Window functions perform calculations across a set of rows that are related to the current row, without collapsing the result set like aggregate functions do. While aggregate functions like SUM() or COUNT() return a single value per group, window functions use the OVER() clause to define a "window" of rows and return a value for each row in the result set. Common window functions include ROW_NUMBER(), RANK(), DENSE_RANK(), LAG(), LEAD(), and running totals using SUM() OVER(). This makes them invaluable for tasks like calculating running totals, ranking results, and comparing values between adjacent rows.

Q: Explain the difference between RANK(), DENSE_RANK(), and ROW_NUMBER() window functions.
A: ROW_NUMBER() assigns a unique sequential integer to each row within a partition, with no gaps or duplicates regardless of ties. RANK() assigns the same rank to rows with identical values but leaves gaps in the sequence after ties (e.g., 1, 2, 2, 4). DENSE_RANK() also assigns the same rank to ties but does not leave gaps (e.g., 1, 2, 2, 3). The choice between them depends on your use case: ROW_NUMBER() for unique identifiers, RANK() when gaps after ties are meaningful, and DENSE_RANK() when you need consecutive ranking without gaps.

Q: What is a Common Table Expression (CTE) and when should you use one?
A: A Common Table Expression (CTE) is a temporary named result set defined within a WITH clause that can be referenced within the main query. CTEs improve query readability by breaking complex queries into logical building blocks, and they can be referenced multiple times in the same query unlike subqueries. They are particularly useful for hierarchical or recursive queries, simplifying complex joins, and making queries self-documenting. CTEs exist only for the duration of the query execution and are not stored as database objects, making them ideal for ad-hoc analysis and complex reporting.

Q: How do recursive CTEs work and what are common use cases?
A: Recursive CTEs consist of an anchor member (the base case) and a recursive member connected by UNION ALL, allowing the query to reference itself. The anchor member executes first and provides the starting rows, then the recursive member repeatedly executes, referencing the CTE itself, until no new rows are returned. Common use cases include traversing hierarchical data like organizational charts or bill of materials, generating sequences or date ranges, graph traversal problems, and calculating transitive closures. A termination condition is critical to prevent infinite loops, typically handled by the recursive member returning no rows.

Q: What are the differences between INNER JOIN, LEFT OUTER JOIN, RIGHT OUTER JOIN, and FULL OUTER JOIN?
A: INNER JOIN returns only rows where there is a match in both tables based on the join condition. LEFT OUTER JOIN returns all rows from the left table plus matched rows from the right table, with NULL values for unmatched right-side columns. RIGHT OUTER JOIN is the mirror image, returning all rows from the right table with NULLs for unmatched left-side columns. FULL OUTER JOIN returns all rows from both tables, with NULLs filling in where there is no match on either side. Understanding these differences is crucial for data analysis, as choosing the wrong join type can lead to missing data or incorrect row counts.

Q: What is a CROSS JOIN and when would you use it?
A: A CROSS JOIN produces a Cartesian product of two tables, combining every row from the first table with every row from the second table. If table A has 100 rows and table B has 50 rows, the result will have 5,000 rows. Use cases include generating all possible combinations for analysis (like all product-store combinations), creating test data, generating date or time dimension tables, and combining with filtering conditions for specific combinatorial queries. Because the result set grows multiplicatively, CROSS JOINs should be used cautiously with large tables to avoid performance issues and excessive memory consumption.

Q: Explain self-joins and provide a practical example of when to use them.
A: A self-join is when a table is joined to itself, typically using different aliases to distinguish between the two instances of the same table. This technique is essential for comparing rows within the same table or navigating hierarchical relationships stored in a single table. A classic example is an employee table with a manager_id column referencing another employee's id: SELECT e.name AS employee, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.id. Self-joins are also useful for finding duplicate records, comparing sequential records, and analyzing before/after states in audit tables.

Q: What is the difference between correlated and non-correlated subqueries?
A: A non-correlated subquery is independent and executes once before the outer query, returning a result that the outer query then uses. A correlated subquery references columns from the outer query and must be re-executed for each row processed by the outer query, making it dependent on the outer query's context. For example, finding employees who earn more than their department average requires a correlated subquery that recalculates the average for each employee's department. While correlated subqueries are more flexible, they can be less performant than non-correlated alternatives; often, joins or window functions can achieve the same result more efficiently.

Q: What are the ACID properties in database transactions?
A: ACID stands for Atomicity, Consistency, Isolation, and Durability, the four fundamental guarantees of reliable transaction processing. Atomicity ensures that all operations in a transaction either complete entirely or have no effect at all (all-or-nothing). Consistency guarantees that a transaction brings the database from one valid state to another, maintaining all defined rules and constraints. Isolation ensures that concurrent transactions execute as if they were running sequentially, preventing interference between transactions. Durability guarantees that once a transaction is committed, its changes persist even in the event of system failure.

Q: Explain the different transaction isolation levels and their trade-offs.
A: SQL defines four standard isolation levels: READ UNCOMMITTED (allows dirty reads), READ COMMITTED (prevents dirty reads but allows non-repeatable reads), REPEATABLE READ (prevents dirty and non-repeatable reads but allows phantom reads), and SERIALIZABLE (prevents all anomalies but with highest overhead). Higher isolation levels provide stronger consistency guarantees but reduce concurrency and throughput due to increased locking. READ COMMITTED is the default in most databases and balances safety with performance. The choice depends on application requirements: financial systems typically need SERIALIZABLE for accuracy, while high-throughput applications may accept READ COMMITTED with application-level handling of edge cases.

Q: What are stored procedures and what advantages do they offer?
A: Stored procedures are precompiled SQL code blocks stored in the database that can accept parameters, perform complex logic, and return results. They offer several advantages: improved performance through precompilation and reduced network traffic, enhanced security by encapsulating business logic and limiting direct table access, code reusability across multiple applications, and centralized maintenance since changes affect all callers automatically. Stored procedures can contain control flow statements, variables, error handling, and transaction management, making them suitable for complex business operations. However, they can reduce portability between database systems and may make debugging and version control more challenging than application code.

Q: What are database triggers and when should they be used?
A: Triggers are special stored procedures that automatically execute in response to specific events on a table, such as INSERT, UPDATE, or DELETE operations. They can fire BEFORE or AFTER the triggering event and have access to the old and new values of affected rows. Common use cases include maintaining audit logs, enforcing complex business rules that cannot be expressed as constraints, automatically updating derived data, and synchronizing related tables. However, triggers should be used sparingly because they can make debugging difficult, create hidden dependencies, impact performance, and lead to unexpected cascading effects. Alternative approaches like application-level logic or scheduled jobs are often more maintainable.

Q: What is the difference between a view and a materialized view?
A: A standard view is a virtual table defined by a stored query that executes each time the view is accessed, always reflecting current data from underlying tables. A materialized view physically stores the query results and must be refreshed periodically to reflect changes in the source data. Views are ideal for simplifying complex queries, implementing security layers, and providing consistent interfaces without storage overhead. Materialized views trade storage space and data freshness for significantly improved query performance, making them valuable for expensive aggregations, data warehousing, and reporting scenarios. The refresh strategy (on-demand, scheduled, or on-commit) depends on the acceptable staleness and system resources.

Q: How do you optimize a query that uses multiple subqueries?
A: Start by analyzing the execution plan to identify bottlenecks like full table scans, nested loops on large datasets, or repeated subquery execution. Consider converting correlated subqueries to JOINs, which often perform better as the optimizer can choose more efficient join algorithms. Replace multiple subqueries with CTEs for clarity and potential optimization opportunities, or use window functions to eliminate the need for self-referential subqueries. Ensure appropriate indexes exist on columns used in WHERE clauses and join conditions. For subqueries in SELECT lists that return scalar values, consider using LEFT JOINs with aggregation instead, as this allows the database to process all related data in a single pass.

Q: What strategies help prevent SQL injection in stored procedures and dynamic SQL?
A: Always use parameterized queries or prepared statements rather than concatenating user input into SQL strings. When dynamic SQL is unavoidable, use sp_executesql (SQL Server) or similar parameterized execution methods rather than EXEC with string concatenation. Validate and sanitize all inputs using whitelists for expected values, especially for identifiers that cannot be parameterized. Apply the principle of least privilege by granting stored procedures only necessary permissions and using EXECUTE AS to limit execution context. Implement proper error handling that does not expose database structure in error messages, and conduct regular code reviews and security testing to identify vulnerabilities.
