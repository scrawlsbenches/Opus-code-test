Q: What is the difference between a list and a tuple in Python, and when should you use each?
A: Lists and tuples are both sequence types in Python, but they differ fundamentally in mutability. Lists are mutable, meaning you can add, remove, or modify elements after creation, while tuples are immutable and cannot be changed once created. Use lists when you need a collection that will change over time, such as a shopping cart or a dynamic queue. Use tuples for fixed collections like coordinates (x, y), database records, or function return values with multiple components. Tuples also have a slight performance advantage and can be used as dictionary keys since they are hashable, whereas lists cannot.

Q: How does Python's garbage collection work, and what is reference counting?
A: Python uses a combination of reference counting and a cyclic garbage collector for memory management. Reference counting tracks how many references point to each object; when the count drops to zero, the memory is immediately freed. However, reference counting alone cannot handle circular references where objects reference each other. Python's cyclic garbage collector periodically scans for these circular reference groups and frees them when they become unreachable. You can interact with garbage collection using the gc module, though manual intervention is rarely needed. Understanding this system helps when debugging memory leaks or optimizing memory-intensive applications.

Q: What are Python decorators and how do they work under the hood?
A: Decorators are a powerful Python feature that allows you to modify or enhance functions and classes without changing their source code. Under the hood, a decorator is simply a function that takes another function as an argument and returns a new function (or the same function modified). When you use the @decorator syntax, Python automatically passes your function to the decorator and replaces it with the returned value. Common use cases include logging, timing, authentication, caching (like @functools.lru_cache), and enforcing access controls. Decorators can be stacked, and they can accept arguments themselves when implemented as decorator factories using nested functions or classes.

Q: What is the Global Interpreter Lock (GIL) and how does it affect Python performance?
A: The Global Interpreter Lock (GIL) is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on multi-core processors. This means CPU-bound Python code cannot achieve true parallelism using threads alone. The GIL exists to protect CPython's memory management, which uses reference counting that is not thread-safe. For CPU-bound tasks requiring parallelism, use the multiprocessing module to spawn separate Python processes, each with its own GIL. For I/O-bound tasks like network requests or file operations, threading still works well because threads release the GIL while waiting for I/O. Alternative Python implementations like Jython and IronPython do not have a GIL.

Q: What are context managers and why should you use them for resource management?
A: Context managers provide a clean, reliable way to manage resources that need setup and teardown, such as file handles, database connections, or locks. Using the with statement ensures that cleanup code runs even if exceptions occur, preventing resource leaks. You can create custom context managers either by implementing __enter__ and __exit__ methods in a class, or more simply using the @contextlib.contextmanager decorator with a generator function. The pattern is especially important for scarce resources where forgetting to close them can cause system-wide problems. Always prefer context managers over try/finally blocks when managing resources, as they make the code more readable and less error-prone.

Q: How do you properly handle exceptions in Python, and what are common anti-patterns to avoid?
A: Proper exception handling involves catching specific exceptions rather than using bare except clauses, which can mask bugs and catch system-exiting exceptions like KeyboardInterrupt. Always catch the most specific exception type possible and handle different error conditions appropriately. Avoid using exceptions for normal control flow, as they are more expensive than conditional checks. Never silently swallow exceptions without logging or re-raising them, as this makes debugging nearly impossible. Use the else clause in try blocks for code that should run only when no exception occurred, and the finally clause for cleanup that must always run. Consider creating custom exception classes for your application's domain-specific errors to provide clearer error handling.

Q: What is the difference between __str__ and __repr__ in Python classes?
A: Both __str__ and __repr__ are special methods for creating string representations of objects, but they serve different purposes. __repr__ should return an unambiguous string representation that ideally could be used to recreate the object, primarily aimed at developers for debugging. __str__ should return a human-readable, user-friendly representation meant for end-user display. When you use print() or str(), Python calls __str__, but if __str__ is not defined, it falls back to __repr__. In the interactive interpreter and debugger, __repr__ is used. A good practice is to always implement __repr__ and only add __str__ if you need a different user-facing representation. For example, repr(datetime.now()) shows the full constructor call, while str(datetime.now()) shows a clean formatted date.

Q: How do you write effective unit tests in Python using pytest?
A: Effective unit tests follow the Arrange-Act-Assert pattern: set up test data, perform the action being tested, and verify the results. Keep tests isolated and independent so they can run in any order without affecting each other. Use pytest fixtures for shared setup code, and parametrize tests to cover multiple input cases without duplicating code. Mock external dependencies like databases and APIs using unittest.mock or pytest-mock to ensure tests are fast and deterministic. Name tests descriptively to document what behavior they verify, using patterns like test_function_does_something_when_condition. Aim for meaningful coverage rather than 100% line coverage; focus on testing critical paths, edge cases, and error handling. Run tests frequently during development to catch regressions early.

Q: What is the difference between shallow copy and deep copy in Python?
A: Shallow copy creates a new object but inserts references to the same nested objects from the original. Deep copy creates a new object and recursively copies all nested objects, creating completely independent copies. For simple objects without nested structures, both behave the same. The difference matters when you have lists containing lists, dictionaries with mutable values, or objects with object attributes. Use copy.copy() for shallow copies and copy.deepcopy() for deep copies from the copy module. Slicing (list[:]) and list(), dict(), etc., create shallow copies. Deep copying is more expensive in memory and time but necessary when you need to modify nested structures independently. Be aware that deep copy can fail on objects containing uncopyable elements like file handles or database connections.

Q: How do generators work in Python, and when should you use them instead of lists?
A: Generators are functions that yield values one at a time instead of returning a complete list, using the yield keyword instead of return. They implement the iterator protocol lazily, computing each value only when requested, which saves memory when working with large datasets. When you call a generator function, it returns a generator object without executing the function body; execution happens incrementally as you iterate. Use generators when processing large files line by line, implementing infinite sequences, or when you only need to iterate through data once. Generator expressions (similar to list comprehensions but with parentheses) provide a concise syntax for simple generators. The key advantage is O(1) memory usage regardless of sequence length, compared to O(n) for lists.

Q: What are the SOLID principles and how do they apply to Python development?
A: SOLID is an acronym for five object-oriented design principles that lead to maintainable, flexible code. Single Responsibility Principle states that a class should have only one reason to change, keeping classes focused and cohesive. Open/Closed Principle means classes should be open for extension but closed for modification, achieved through inheritance and composition. Liskov Substitution Principle requires that subclasses must be substitutable for their base classes without altering program correctness. Interface Segregation Principle advises creating specific interfaces rather than forcing clients to depend on methods they don't use, though Python's duck typing makes this less rigid. Dependency Inversion Principle suggests depending on abstractions rather than concrete implementations, using dependency injection to decouple components. While Python's dynamic nature makes some principles less strict, following SOLID leads to more testable, reusable code.

Q: How do you debug Python applications effectively beyond using print statements?
A: The built-in pdb debugger lets you set breakpoints, step through code, inspect variables, and evaluate expressions interactively using breakpoint() or import pdb; pdb.set_trace(). IDEs like PyCharm and VS Code provide graphical debuggers with breakpoints, variable watches, and call stack navigation that are more user-friendly. For post-mortem debugging of crashed programs, use python -m pdb script.py or pdb.pm() to examine the state at the crash point. Logging with the logging module provides different severity levels and can be configured to output to files, making it superior to print for production code. The traceback module helps format exception information, and sys.exc_info() provides programmatic access to exception details. For performance issues, use cProfile or the timeit module to identify bottlenecks before optimizing.

Q: What is duck typing in Python, and how does it relate to interfaces and abstract base classes?
A: Duck typing is Python's approach to type checking based on behavior rather than explicit type declarations: "if it walks like a duck and quacks like a duck, it's a duck." This means you can pass any object to a function as long as it has the required methods or attributes, regardless of its actual class. While this provides flexibility, it can lead to runtime errors if objects lack expected behavior. Abstract Base Classes (ABCs) from the abc module provide a middle ground, defining interfaces that classes must implement without dictating the implementation details. ABCs use @abstractmethod to declare methods that subclasses must override, raising TypeError if they don't. You can also register virtual subclasses to maintain duck typing flexibility while adding optional type checking. Many built-in types are defined through ABCs in collections.abc, like Iterable, Sequence, and Mapping.

Q: What are common Python performance optimization techniques?
A: Start by profiling with cProfile or line_profiler to identify actual bottlenecks rather than guessing, as premature optimization wastes time and reduces readability. Use built-in functions and data structures, which are implemented in C and highly optimized; for example, sum() is faster than manual loops, and sets provide O(1) membership testing. List comprehensions and generator expressions are faster than equivalent for loops with append. For numerical computing, use NumPy arrays instead of Python lists for vectorized operations that are orders of magnitude faster. Memoization with @functools.lru_cache automatically caches function results for expensive repeated calculations. Avoid global variable lookups in tight loops by assigning them to local variables. Consider using __slots__ in classes to reduce memory usage and slightly improve attribute access speed. For truly performance-critical code, consider Cython or writing C extensions.

Q: How do you manage dependencies and virtual environments in Python projects?
A: Virtual environments isolate project dependencies, preventing conflicts between projects that require different package versions. Create them with python -m venv venv_name or virtualenv, and activate with source venv/bin/activate on Unix or venv\Scripts\activate on Windows. Track dependencies in requirements.txt using pip freeze, or preferably use pip-tools to separate direct dependencies from their transitive dependencies. For more robust dependency management, tools like Poetry or Pipenv provide lock files for reproducible builds, dependency resolution, and combined virtual environment management. Always pin exact versions in production requirements to avoid unexpected breaking changes. Consider using pyproject.toml as the modern standard for project metadata and build configuration. Docker can provide even stronger isolation for deployment, ensuring consistent environments across development and production.

Q: What are Python decorators and how do they work internally?
A: Decorators are functions that modify the behavior of other functions or classes without changing their source code. Internally, a decorator takes a function as input and returns a new function that typically wraps the original. When you use the @decorator syntax, Python essentially executes my_function = decorator(my_function). Decorators leverage Python's first-class functions, meaning functions can be passed as arguments, returned from other functions, and assigned to variables. The functools.wraps decorator is commonly used inside decorators to preserve the original function's metadata like __name__ and __doc__. Decorators can also accept arguments by using a three-level nested function structure where the outermost function receives the decorator arguments.

Q: How do Python generators differ from regular functions and what are their memory benefits?
A: Generators are special functions that use the yield keyword instead of return, allowing them to produce a sequence of values lazily rather than computing all values at once. When a generator function is called, it returns a generator object without executing the function body; execution only begins when next() is called or the generator is iterated over. Each yield statement suspends the function's execution, saves its state, and returns a value to the caller. This lazy evaluation means generators are extremely memory-efficient when working with large datasets because only one value is held in memory at a time. Generator expressions like (x**2 for x in range(1000000)) provide a concise syntax for simple generators. The send() method allows bidirectional communication with generators, enabling coroutine-like patterns.

Q: What is the purpose of context managers and how do you implement custom ones?
A: Context managers provide a clean way to manage resources that need setup and teardown actions, ensuring proper cleanup even when exceptions occur. They are used with the with statement and guarantee that __exit__ is called regardless of how the block terminates. To implement a custom context manager as a class, you define __enter__ (which returns the resource) and __exit__ (which handles cleanup and receives any exception information). The contextlib module provides the @contextmanager decorator for creating context managers using generator functions, where code before yield runs on entry and code after yield runs on exit. Context managers are essential for file handling, database connections, locks, and temporary state changes. The __exit__ method receives exception type, value, and traceback, and can suppress exceptions by returning True.

Q: How does async/await work in Python and when should you use it?
A: Async/await enables cooperative multitasking for I/O-bound operations through coroutines that can pause execution while waiting for external resources. An async function defined with async def returns a coroutine object that must be awaited or scheduled on an event loop to execute. The await keyword suspends the coroutine until the awaited operation completes, allowing the event loop to run other tasks during the wait. This is ideal for network requests, database queries, file I/O, and other operations where your program spends time waiting rather than computing. Unlike threads, async code runs in a single thread and switches tasks only at await points, eliminating race conditions for shared state. The asyncio module provides the event loop, task management, and synchronization primitives needed for async programming. Use async/await when you have many concurrent I/O operations; for CPU-bound work, multiprocessing is more appropriate.

Q: What are metaclasses in Python and what problems do they solve?
A: Metaclasses are classes whose instances are themselves classes; they control class creation and can modify class definitions before the class is created. In Python, type is the default metaclass and calling type(name, bases, namespace) creates a new class dynamically. When you define a class, Python calls the metaclass's __new__ and __init__ methods, passing the class name, base classes, and namespace dictionary. Metaclasses solve problems like automatic registration of subclasses, enforcing API contracts across class hierarchies, implementing ORMs, and adding class-level behavior transparently. The __prepare__ method allows metaclasses to provide a custom namespace (like OrderedDict) for class body execution. While powerful, metaclasses add complexity and should be used sparingly; often class decorators or __init_subclass__ provide simpler alternatives. Famous uses include Django's ORM models and abstract base classes in the abc module.

Q: What are descriptors and how do they enable Python's attribute access protocol?
A: Descriptors are objects that define __get__, __set__, or __delete__ methods and control attribute access when stored as class attributes. When you access an attribute, Python's attribute lookup protocol checks if the class attribute is a descriptor and calls its descriptor methods instead of returning the object directly. Data descriptors (implementing __set__ or __delete__) take precedence over instance dictionaries, while non-data descriptors (only __get__) do not. Descriptors power many Python features including properties, methods, classmethod, staticmethod, and __slots__. The property built-in is actually a descriptor class that calls getter/setter functions you provide. Understanding descriptors is crucial for implementing lazy attributes, type validation, computed properties, and ORM field definitions. The descriptor protocol enables Python's elegant attribute access while allowing fine-grained control when needed.

Q: How does Python's memory management and garbage collection work?
A: Python uses automatic memory management with reference counting as the primary mechanism and a cyclic garbage collector for handling circular references. Each object has a reference count that increments when referenced and decrements when references are removed; when it reaches zero, the memory is immediately freed. However, reference counting cannot detect circular references (A references B, B references A), so Python includes a generational garbage collector that periodically scans for unreachable cycles. Objects are divided into three generations; new objects start in generation 0 and survive to older generations if they persist through garbage collection cycles. The gc module provides functions to interact with the collector, including gc.collect() to force collection and gc.disable() for performance-critical sections. Memory is allocated from pools and arenas managed by Python's memory allocator, which reduces system call overhead. Understanding this helps with optimizing memory-intensive applications and avoiding memory leaks from lingering references.

Q: How do type hints work in Python and what tools use them?
A: Type hints are annotations that indicate expected types for function parameters, return values, and variables without affecting runtime behavior. Introduced in PEP 484 and enhanced in subsequent PEPs, they use syntax like def greet(name: str) -> str and support generics like List[int] or Dict[str, Any]. The typing module provides constructs for complex types including Union, Optional, Callable, TypeVar for generics, and Protocol for structural subtyping. Static type checkers like mypy, pyright, and Pyre analyze code to catch type errors before runtime, significantly improving code reliability. IDEs use type hints for better autocomplete, refactoring, and documentation. At runtime, hints are stored in __annotations__ and can be accessed for documentation or runtime validation via libraries like pydantic. Type hints are especially valuable in large codebases where they serve as machine-checkable documentation and enable safer refactoring.

Q: What is the difference between __new__ and __init__ in Python classes?
A: __new__ is a static method responsible for creating and returning a new instance, while __init__ initializes that instance after creation. __new__ receives the class as its first argument and returns an instance (usually via super().__new__(cls)), whereas __init__ receives the already-created instance as self and returns None. Most classes only need __init__ because the default __new__ from object handles instance creation correctly. Override __new__ when you need to control instance creation itself: implementing singletons, caching instances, customizing immutable types like int or str, or returning instances of different classes. For immutable types, you must use __new__ because the object is already immutable by the time __init__ runs. Metaclasses use __new__ and __init__ to control class object creation, not instance creation. Understanding this distinction is essential for advanced patterns like flyweight, factory methods, and custom descriptors.

Q: How do you properly structure a Python package for distribution?
A: A well-structured Python package uses a src/ layout with pyproject.toml as the central configuration file, following PEP 517/518/621 standards. The src/ layout places your package under src/package_name/, preventing accidental imports from the source directory instead of the installed version. pyproject.toml defines build system requirements, project metadata (name, version, dependencies), and tool configurations for linters and formatters. Include a __init__.py in each package directory and use __all__ to control what from package import * exports. Specify entry points for console scripts and plugins, and declare dependencies with version constraints. Use setuptools, flit, or hatch as build backends, each offering different tradeoffs between simplicity and features. Include appropriate classifiers, a README for PyPI display, and a LICENSE file. Build with python -m build and upload to PyPI using twine after testing on TestPyPI first.

Q: What is the Global Interpreter Lock (GIL) and how does it affect concurrent Python code?
A: The GIL is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on multi-core processors. This design simplifies memory management and makes single-threaded programs faster, but prevents true parallel execution of Python code across threads. For I/O-bound operations, the GIL is released during I/O waits, so threading still provides concurrency benefits for network requests, file operations, and database queries. CPU-bound parallel work requires the multiprocessing module, which spawns separate Python processes each with their own GIL. C extensions can release the GIL during long computations, which is why NumPy and other scientific libraries achieve parallelism despite the GIL. Alternative implementations like Jython and IronPython don't have a GIL, and there are ongoing efforts to make CPython GIL-optional. Understanding the GIL helps you choose between threads, processes, and async based on your workload characteristics.

Q: How do you use __slots__ and what are the tradeoffs?
A: __slots__ is a class attribute that declares a fixed set of instance attributes, preventing the creation of __dict__ and __weakref__ for instances. By eliminating __dict__, slots significantly reduce memory usage per instance, which matters when creating millions of objects. Slots also provide slightly faster attribute access since Python doesn't need dictionary lookups. However, slots have limitations: you cannot add new attributes dynamically, inheritance with slots requires careful handling, and features relying on __dict__ (like vars()) won't work. If a child class doesn't define __slots__, it gets __dict__ back, negating memory benefits. Multiple inheritance with different slots in each parent class works but requires all non-empty slots to be disjoint. Slots are ideal for data classes with many instances and fixed attributes, like nodes in a graph or records from a database. Consider dataclasses with slots=True for a cleaner syntax in Python 3.10+.

Q: What are the different ways to handle errors and exceptions in Python?
A: Python provides try/except/else/finally blocks for comprehensive exception handling, where except catches specific exceptions, else runs if no exception occurred, and finally always executes for cleanup. Use specific exception types rather than bare except to avoid catching SystemExit, KeyboardInterrupt, and hiding bugs. The exception hierarchy allows catching categories of errors; for example, except OSError catches FileNotFoundError, PermissionError, and other OS-related errors. Custom exceptions should inherit from Exception (not BaseException) and can include additional attributes for context. Context managers and finally blocks ensure cleanup even when exceptions propagate. The raise ... from ... syntax chains exceptions, preserving the original cause while raising a new exception. Exception handling has performance overhead, so avoid using exceptions for normal control flow. The logging module integrates well with exception handling via logger.exception() which automatically includes traceback information.

Q: How do dataclasses work and when should you use them instead of regular classes?
A: Dataclasses, introduced in Python 3.7, automatically generate __init__, __repr__, __eq__, and other methods based on class attribute annotations. The @dataclass decorator inspects type-annotated class attributes and creates an initializer that assigns them to instance attributes. Options like frozen=True make instances immutable (useful for hashable objects), and slots=True generates __slots__ for memory efficiency. Field() allows specifying defaults, default factories for mutable defaults, and metadata for custom processing. Dataclasses are ideal for classes that primarily store data with minimal behavior, replacing verbose boilerplate with concise declarations. They integrate with type checkers and support inheritance, post-init processing via __post_init__, and field ordering. For complex validation or serialization, consider pydantic which extends dataclass concepts with runtime type checking. Regular classes remain better when you need custom __init__ logic, complex inheritance, or when the class is primarily about behavior rather than data.

Q: What are the best practices for writing testable Python code?
A: Writing testable code starts with separating concerns: pure functions without side effects are trivially testable, while I/O and state changes should be isolated at boundaries. Use dependency injection by passing dependencies as parameters rather than creating them inside functions; this allows tests to substitute mocks or fakes. Avoid global state and singletons which create hidden dependencies and make tests order-dependent. Structure code so that business logic is independent of frameworks, databases, and external services; hexagonal architecture exemplifies this pattern. Write small functions with single responsibilities that are easy to test in isolation. Use protocols or abstract base classes to define interfaces, enabling test doubles to substitute for real implementations. The unittest.mock module provides Mock, patch, and MagicMock for replacing dependencies during tests. pytest fixtures provide clean setup/teardown and support parametrized tests for covering multiple cases. Aim for fast, deterministic tests that can run in any order and don't require network, database, or filesystem access.
