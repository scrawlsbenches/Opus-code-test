Q: What is MongoDB and when should you use it as a document store?
A: MongoDB is a document-oriented NoSQL database that stores data as flexible JSON-like documents (BSON format), allowing for nested structures and varying schemas within a collection. It excels in scenarios requiring rapid iteration, such as content management systems, product catalogs, and real-time analytics where the data model evolves frequently. MongoDB is particularly well-suited when your application needs to store complex, hierarchical data structures that would require multiple joins in a relational database. Its horizontal scaling through sharding makes it ideal for applications expecting significant growth in data volume.

Q: How does Redis function as a key-value store and what are its primary use cases?
A: Redis is an in-memory key-value store that supports various data structures including strings, hashes, lists, sets, and sorted sets, providing sub-millisecond latency for read and write operations. Its primary use cases include session caching, real-time leaderboards, pub/sub messaging systems, and serving as a caching layer in front of slower databases. Redis persistence options (RDB snapshots and AOF logs) allow it to function as a primary database for certain workloads while maintaining its speed advantage. The combination of atomic operations and Lua scripting support makes Redis powerful for implementing distributed locks and rate limiters.

Q: What distinguishes Cassandra's column-family data model from traditional relational databases?
A: Cassandra organizes data into column families (tables) where each row can have a different set of columns, and columns are grouped into families based on access patterns rather than normalization rules. Unlike relational databases that optimize for query flexibility, Cassandra requires you to design your data model around your query patterns, often leading to data denormalization and duplication. This design enables Cassandra to achieve linear scalability and high write throughput across distributed nodes without sacrificing availability. The wide-column model is particularly effective for time-series data, event logging, and any workload requiring fast writes across geographically distributed clusters.

Q: How does Neo4j leverage graph structures for data relationships and when is it the right choice?
A: Neo4j stores data as nodes (entities) and relationships (connections between entities), both of which can have properties, enabling native traversal of complex relationships without expensive join operations. This graph model excels when relationships between data points are as important as the data itself, such as in social networks, recommendation engines, fraud detection, and knowledge graphs. Neo4j's Cypher query language allows intuitive pattern matching across multiple relationship hops that would require recursive CTEs or multiple joins in SQL. Choose Neo4j when your queries frequently involve finding paths, analyzing connectivity, or discovering patterns across highly interconnected data.

Q: What is the CAP theorem and how does it influence NoSQL database selection?
A: The CAP theorem states that a distributed database can only guarantee two of three properties simultaneously: Consistency (all nodes see the same data), Availability (every request receives a response), and Partition tolerance (the system continues operating despite network failures). Since network partitions are inevitable in distributed systems, the practical choice becomes between CP systems (like MongoDB with majority write concern) that sacrifice availability during partitions, and AP systems (like Cassandra) that remain available but may return stale data. Understanding CAP tradeoffs helps architects choose databases aligned with their application's requirements: financial transactions typically need consistency, while social media feeds can tolerate eventual consistency for better availability.

Q: What is eventual consistency and how do NoSQL databases implement it?
A: Eventual consistency is a consistency model where, given enough time without new updates, all replicas of data will converge to the same value, but reads may temporarily return stale data during the convergence period. NoSQL databases like Cassandra and DynamoDB implement this through asynchronous replication, where writes propagate to replica nodes in the background, combined with techniques like vector clocks, read repair, and anti-entropy protocols to detect and resolve conflicts. Applications can often tune consistency levels per-operation, choosing stronger consistency for critical reads while accepting eventual consistency for less sensitive operations. This model enables higher availability and lower latency compared to strongly consistent systems, making it suitable for use cases where temporary inconsistencies are acceptable.

Q: How do data modeling approaches differ between NoSQL and relational databases?
A: Relational database design follows normalization principles to eliminate redundancy and establish relationships through foreign keys, optimizing for data integrity and flexible querying at the cost of join operations. NoSQL data modeling inverts this approach by denormalizing data and embedding related information together based on how it will be accessed, optimizing read performance by pre-computing join results at write time. In document stores, you embed related data within a single document; in column-family stores, you create multiple tables with duplicated data to serve different query patterns. This query-driven design requires understanding access patterns upfront but eliminates expensive runtime joins and enables horizontal scaling.

Q: When should you choose NoSQL over a traditional relational database?
A: Choose NoSQL when your application requires horizontal scalability beyond what a single server can handle, when your data structure is highly variable or nested, or when you need to optimize for specific access patterns with very high throughput. NoSQL databases excel in scenarios involving massive write volumes (IoT sensor data, logging), flexible schemas (user-generated content, product attributes), or complex relationships (social graphs, recommendations). However, relational databases remain superior when you need ACID transactions across multiple tables, complex ad-hoc queries, or when your data model is well-defined and stable. Consider NoSQL as a complement rather than replacement: many architectures use both, with relational databases for transactional data and NoSQL for specific workloads.

Q: What indexing strategies are commonly used in MongoDB and how do they affect query performance?
A: MongoDB supports various index types including single-field, compound, multikey (for arrays), text, geospatial, and hashed indexes, with compound indexes being crucial for queries filtering or sorting on multiple fields. The order of fields in a compound index matters significantly: MongoDB can use an index for queries that match a prefix of the indexed fields, so place high-cardinality fields and equality conditions before range conditions. Covered queries, where all requested fields are in the index, avoid document lookups entirely and dramatically improve performance. Index intersection allows MongoDB to combine multiple indexes, but a single compound index covering your query pattern typically outperforms intersection, making understanding your query patterns essential for effective index design.

Q: How does Cassandra's partition key design impact query performance and data distribution?
A: Cassandra uses the partition key to determine which node stores a row by hashing the key and mapping it to a token range owned by a specific node, making partition key selection critical for both data distribution and query efficiency. Queries that include the partition key in the WHERE clause can route directly to the relevant node, while queries without it require expensive scatter-gather operations across all nodes. Hot partitions occur when partition keys have skewed distribution, causing some nodes to handle disproportionate load, so choose partition keys that distribute data evenly while supporting your primary access patterns. Compound partition keys and clustering columns provide additional flexibility, allowing you to group related data on the same partition for efficient range queries while maintaining distribution.

Q: What consistency levels does Cassandra offer and how do you choose between them?
A: Cassandra provides tunable consistency levels including ONE, QUORUM, LOCAL_QUORUM, and ALL, allowing per-operation control over the tradeoff between consistency and latency/availability. QUORUM requires acknowledgment from a majority of replicas, providing strong consistency when both reads and writes use QUORUM (since any majority must include at least one node with the latest write). LOCAL_QUORUM restricts the quorum to the local data center, reducing latency for multi-region deployments while maintaining consistency within a region. For critical data, combine write consistency of QUORUM or higher with read consistency of QUORUM to guarantee reading your own writes; for high-throughput, less critical operations, ONE provides better performance at the cost of potential staleness.

Q: How do graph database queries in Neo4j differ from SQL joins for relationship traversal?
A: In SQL, traversing relationships requires explicit JOIN operations whose cost increases multiplicatively with the number of relationships and depth of traversal, often requiring self-joins or recursive CTEs for variable-length paths. Neo4j stores relationships as direct pointers between nodes, making traversal a constant-time operation per hop regardless of total database size, enabling efficient queries across multiple relationship levels. Cypher pattern matching like MATCH (a)-[:KNOWS*1..5]->(b) naturally expresses variable-length paths that would require complex recursive SQL, and the query planner optimizes traversal order based on selectivity. This index-free adjacency model makes graph databases orders of magnitude faster for relationship-heavy queries while SQL databases remain more efficient for aggregations across entire tables.

Q: What strategies help manage schema evolution in document databases like MongoDB?
A: Document databases provide schema flexibility but still require strategies for managing evolution: schema versioning embeds a version field in documents allowing application code to handle different versions appropriately during reads. Lazy migration updates documents to the new schema when they are accessed and written back, spreading migration cost over time but requiring code to handle multiple versions simultaneously. Eager migration through batch updates converts all documents at once, providing consistency but requiring downtime or careful orchestration for large collections. MongoDB's schema validation feature can enforce required fields and types on writes, providing guardrails while maintaining flexibility, and aggregation pipelines with $addFields can transform documents at query time to present a consistent shape.

Q: How does Redis implement data persistence while maintaining in-memory performance?
A: Redis offers two persistence mechanisms: RDB (Redis Database) creates point-in-time snapshots at configured intervals by forking the process and writing the dataset to disk, providing compact backups with minimal impact on performance. AOF (Append-Only File) logs every write operation, enabling recovery by replaying the log, with configurable fsync policies balancing durability against performance (every second is a common compromise). Combining both approaches provides optimal disaster recovery: RDB for fast restarts from recent snapshots, AOF for minimal data loss by replaying operations since the last snapshot. Redis 7 introduced multi-part AOF and improved RDB performance, while Redis Enterprise adds active-active geo-distribution and durable storage options for mission-critical deployments.

Q: What are the key considerations when implementing a polyglot persistence architecture with multiple NoSQL databases?
A: Polyglot persistence uses different databases for different data types based on their strengths: Redis for caching and sessions, MongoDB for flexible document storage, Cassandra for time-series and high-write workloads, and Neo4j for graph queries. The primary challenges include maintaining data consistency across systems, managing increased operational complexity, and implementing synchronization when the same data appears in multiple stores. Event-driven architectures with message queues help coordinate updates across databases, while the saga pattern manages distributed transactions without requiring two-phase commit. Design boundaries carefully to minimize cross-database transactions, accept eventual consistency where possible, and ensure your team has expertise to operate multiple database systems effectively.
