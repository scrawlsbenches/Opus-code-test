Q: What is the fundamental difference between ETL and ELT, and when should you choose one over the other?
A: ETL (Extract, Transform, Load) transforms data before loading it into the target system, while ELT (Extract, Load, Transform) loads raw data first and transforms it within the destination. ETL is preferred when working with on-premises data warehouses with limited compute power, or when data must be cleansed before entering the target system for compliance reasons. ELT excels with modern cloud data warehouses like Snowflake or BigQuery that have massive parallel processing capabilities, allowing transformations to leverage the destination's compute resources. The choice often depends on where you want transformation logic to live and the computational capabilities of your target system.

Q: How do data pipelines differ from simple ETL jobs, and what components make up a robust data pipeline architecture?
A: Data pipelines are comprehensive systems for moving and processing data that go beyond simple ETL by incorporating orchestration, monitoring, error handling, and data lineage tracking. A robust pipeline architecture includes ingestion layers for capturing data from various sources, staging areas for intermediate processing, transformation engines, quality validation checkpoints, and delivery mechanisms to target systems. Unlike one-off ETL jobs, pipelines are designed for continuous operation with built-in retry logic, alerting, and the ability to handle schema changes gracefully. Modern pipelines also include metadata management and data cataloging to maintain visibility into data flow across the organization.

Q: What are the key tradeoffs between batch processing and streaming data processing approaches?
A: Batch processing handles data in discrete chunks at scheduled intervals, offering simplicity, cost efficiency, and easier debugging since you process known datasets. Streaming processes data continuously as it arrives, providing near-real-time insights but requiring more complex infrastructure for state management, exactly-once processing guarantees, and handling out-of-order events. Batch is ideal for analytical workloads where hourly or daily latency is acceptable, such as financial reporting or historical analysis. Streaming is essential for use cases requiring immediate action, like fraud detection, real-time recommendations, or operational monitoring where delays could mean missed opportunities or risks.

Q: How do data warehouses and data lakes serve different purposes in a modern data architecture?
A: Data warehouses are structured repositories optimized for analytical queries, storing processed and curated data in predefined schemas that enforce data quality and enable fast business intelligence queries. Data lakes store raw data in its native format across structured, semi-structured, and unstructured types, providing flexibility for data scientists and enabling storage of data before use cases are defined. Warehouses excel at serving business analysts with consistent metrics and governed data models, while lakes support exploratory analysis and machine learning workloads requiring access to raw granular data. Many organizations now implement a lakehouse architecture that combines both approaches, using lake storage with warehouse-like query performance and governance.

Q: What are the essential dimensions of data quality, and how should they be measured in production pipelines?
A: Data quality encompasses six core dimensions: completeness (percentage of non-null values), accuracy (correctness against source of truth), consistency (matching values across systems), timeliness (data freshness relative to requirements), validity (conformance to business rules and formats), and uniqueness (absence of unwanted duplicates). Production pipelines should implement automated quality checks at ingestion, after transformations, and before delivery to downstream consumers. Metrics should be tracked over time to identify degradation trends, with alerts triggered when thresholds are breached. Quality gates can halt pipeline execution when critical violations occur, preventing bad data from propagating to business-critical systems.

Q: What is schema evolution, and what strategies exist for handling it in data pipelines?
A: Schema evolution refers to changes in data structure over time, such as adding columns, changing data types, renaming fields, or removing attributes from source systems. Strategies for handling it include schema-on-read approaches where pipelines accommodate multiple versions by applying transformations at query time, and schema-on-write where incoming data is validated and transformed to match the target schema. Backward-compatible changes like adding nullable columns are typically safe, while breaking changes require versioning strategies or migration scripts. Modern data formats like Avro and Parquet support schema evolution natively, and tools like schema registries help track versions and enforce compatibility rules across producer-consumer boundaries.

Q: How does Apache Airflow use DAGs to orchestrate data workflows, and what are the key concepts for effective DAG design?
A: Apache Airflow represents workflows as Directed Acyclic Graphs (DAGs) where nodes are tasks and edges define dependencies, ensuring tasks execute in the correct order without circular dependencies. Key concepts include operators (predefined task templates for common operations), sensors (tasks that wait for external conditions), and hooks (interfaces to external systems). Effective DAG design involves keeping tasks atomic and idempotent so they can be safely retried, using XComs sparingly for inter-task communication, and structuring dependencies to maximize parallelization. DAGs should be parameterized with execution dates for backfilling historical data and should include proper error handling with retries, timeouts, and alerting on failure.

Q: What are the fundamental concepts of Apache Spark that data engineers should understand for large-scale data processing?
A: Spark's core abstraction is the Resilient Distributed Dataset (RDD), though most work uses the higher-level DataFrame and Dataset APIs that provide optimization through Spark's Catalyst query optimizer. Key concepts include lazy evaluation where transformations are not executed until an action triggers computation, partitioning which determines how data is distributed across cluster nodes, and shuffling which is the expensive redistribution of data across partitions for operations like joins and aggregations. Understanding the difference between narrow transformations (map, filter) that don't require shuffling and wide transformations (groupBy, join) that do is crucial for performance. Spark's in-memory computation model provides speed advantages over MapReduce, but engineers must manage memory carefully to avoid out-of-memory errors.

Q: What is star schema modeling, and why is it the preferred approach for analytical data warehouses?
A: Star schema organizes data into a central fact table containing quantitative metrics and foreign keys, surrounded by dimension tables that provide descriptive context for analysis. This denormalized design optimizes for query performance by minimizing joins, as most analytical queries can be answered by joining the fact table with one or more dimensions. Fact tables are typically narrow and very long, containing measures like sales amounts or click counts, while dimension tables are wide and relatively short, containing attributes like customer demographics or product categories. The simplicity of star schema makes it intuitive for business users writing queries and enables query optimizers to generate efficient execution plans, while also supporting common BI patterns like drill-down, slice-and-dice, and roll-up aggregations.

Q: What is Change Data Capture (CDC), and what are the common implementation approaches?
A: Change Data Capture is a technique for identifying and capturing changes made to source data so that downstream systems can be updated incrementally rather than through full data refreshes. Common approaches include timestamp-based CDC using modification timestamps to query changed records, trigger-based CDC that writes changes to shadow tables via database triggers, and log-based CDC that reads database transaction logs to capture inserts, updates, and deletes. Log-based CDC is generally preferred as it has minimal impact on source system performance and captures all changes including deletes without modifying source schemas. Tools like Debezium, AWS DMS, and Fivetran provide log-based CDC capabilities for common databases, enabling near-real-time data replication to analytical systems.

Q: How should data engineers approach testing data pipelines to ensure reliability?
A: Data pipeline testing should occur at multiple levels: unit tests for individual transformation functions using sample data, integration tests that verify components work together correctly with test databases, and end-to-end tests that validate complete pipeline execution against representative datasets. Data quality tests should assert expected row counts, null percentages, value distributions, and referential integrity after each pipeline stage. Contract tests verify that upstream changes don't break downstream consumers by checking schema compatibility and data format assumptions. Testing should include edge cases like empty datasets, malformed records, and late-arriving data, with production monitoring extending testing into runtime through anomaly detection and data profiling comparisons against baseline metrics.

Q: What is data lineage, and why is it critical for enterprise data governance?
A: Data lineage tracks the complete lifecycle of data from origin through all transformations to final consumption, documenting where data came from, how it was processed, and where it flows. This visibility is critical for regulatory compliance in industries like finance and healthcare where auditors require proof of data provenance and transformation accuracy. When data quality issues arise, lineage enables rapid root cause analysis by tracing problems back to their source rather than investigating entire systems. Lineage also supports impact analysis when source systems change, allowing teams to identify all downstream dependencies before making modifications. Modern data catalogs like Collibra, Alation, and DataHub automatically capture lineage metadata from pipeline execution, though maintaining accuracy requires consistent instrumentation across all data processing tools.

Q: What are the best practices for handling late-arriving data in streaming and batch pipelines?
A: Late-arriving data occurs when records arrive after the processing window they belong to has already closed, common in scenarios involving network delays, device offline periods, or source system batching. Streaming systems address this through watermarking, which defines how long to wait for late data before finalizing window results, combined with allowed lateness settings that can update previously emitted results when late records arrive. Batch pipelines should design fact tables to support updates and implement reprocessing strategies for time periods affected by late data. Idempotent processing ensures that reprocessing with late data produces correct results without duplicates. The business should define acceptable lateness thresholds based on use case requirements, balancing data completeness against the cost of maintaining longer processing windows or frequent recomputation.

Q: How do you design data pipelines for fault tolerance and exactly-once processing semantics?
A: Fault-tolerant pipelines require idempotent operations that produce the same result regardless of how many times they execute, enabling safe retries after failures. Exactly-once semantics can be achieved through various patterns: transactional writes that commit processing state and output atomically, deduplication using unique record identifiers to filter already-processed data, or checkpoint-based recovery that tracks processed offsets and resumes from the last successful position. Distributed systems like Kafka provide exactly-once guarantees through idempotent producers and transactional consumers, while Spark Structured Streaming achieves it through micro-batch checkpointing. Pipeline design should assume failures will occur, implementing dead-letter queues for records that cannot be processed, alerting on error rates, and maintaining operational runbooks for common failure scenarios.

Q: What metrics and monitoring should be implemented for production data pipelines?
A: Essential pipeline metrics include throughput (records processed per time unit), latency (time from data creation to availability in target), error rates (failed records as percentage of total), and resource utilization (CPU, memory, and storage consumption). Data freshness monitoring tracks the age of the most recent record in target systems, alerting when data becomes stale beyond acceptable thresholds. Pipeline execution metrics capture run duration trends, success rates, and retry counts to identify degradation before failures occur. Quality metrics from automated validation should be tracked historically to detect drift in data characteristics. Dashboards should provide both real-time operational views and historical trend analysis, with alerts configured for anomalies using statistical methods rather than just fixed thresholds to reduce false positives while catching genuine issues.
