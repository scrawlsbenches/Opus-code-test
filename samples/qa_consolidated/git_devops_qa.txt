Q: What is the difference between merge and rebase in Git, and when should you use each?
A: Merge creates a new commit that combines two branches while preserving the complete history of both branches, resulting in a non-linear history with merge commits. Rebase, on the other hand, replays your commits on top of another branch, creating a linear history that appears as if the work was done sequentially. Use merge when you want to preserve the exact history of how features were developed and integrated, which is valuable for understanding project evolution. Use rebase for cleaning up local commits before sharing them, or when you want a cleaner, linear history that is easier to read and bisect. Never rebase commits that have been pushed to a shared repository, as this rewrites history and can cause significant problems for other team members who have based work on those commits.

Q: What is GitFlow and how does it compare to trunk-based development?
A: GitFlow is a branching model that uses multiple long-lived branches including main, develop, feature branches, release branches, and hotfix branches, providing strict separation between different types of work. It works well for projects with scheduled releases and multiple versions in production simultaneously. Trunk-based development, in contrast, encourages developers to commit directly to the main branch or use very short-lived feature branches that are merged within a day or two. Trunk-based development supports continuous integration better because code is integrated frequently, reducing merge conflicts and enabling faster feedback loops. GitFlow can lead to integration problems when feature branches live too long, while trunk-based development requires strong testing practices and feature flags to manage incomplete features in production.

Q: How do you resolve a merge conflict in Git?
A: When Git detects conflicting changes that cannot be automatically merged, it marks the conflicted sections in the affected files with conflict markers showing both versions of the code. To resolve conflicts, open each conflicted file and look for the markers that separate your changes from the incoming changes. Edit the file to keep the desired code, removing all conflict markers and creating the final version you want. After resolving all conflicts in all files, stage the resolved files using git add and complete the merge with git commit. Tools like VS Code, IntelliJ, and dedicated merge tools can visualize conflicts side-by-side, making resolution easier. Always test your code after resolving conflicts to ensure the merged result works correctly, as syntactically correct resolutions can still introduce logical bugs.

Q: What is CI/CD and why is it important for modern software development?
A: Continuous Integration (CI) is the practice of automatically building and testing code every time a developer pushes changes, ensuring that new code integrates correctly with the existing codebase. Continuous Delivery (CD) extends this by automatically preparing code for release to production, while Continuous Deployment takes it further by automatically deploying every change that passes the pipeline. CI/CD pipelines catch bugs early when they are cheaper to fix, provide rapid feedback to developers, and reduce the risk of deployment by making releases smaller and more frequent. This approach eliminates the traditional integration phase where teams would spend days or weeks merging code, and instead spreads that work across many small, manageable integrations. CI/CD also creates a consistent, repeatable deployment process that reduces human error and enables teams to release with confidence at any time.

Q: How do containers differ from virtual machines, and what advantages do they offer for deployment?
A: Virtual machines include a complete operating system along with the application, running on a hypervisor that emulates hardware, resulting in significant overhead in terms of memory, storage, and startup time. Containers share the host operating system kernel and only package the application and its dependencies, making them much lighter weight with startup times measured in seconds rather than minutes. This efficiency allows you to run many more containers than VMs on the same hardware, reducing infrastructure costs. Containers provide consistency across environments because the same container image runs identically on a developer laptop, test server, and production cluster. They also enable microservices architectures by making it practical to deploy, scale, and update individual services independently. Container orchestration platforms like Kubernetes can automatically manage container placement, scaling, networking, and recovery from failures.

Q: What are the best practices for writing effective code review comments?
A: Focus on the code, not the person, using phrases like "this code could be improved" rather than "you wrote this incorrectly" to maintain a constructive atmosphere. Be specific about what you are suggesting and why, providing context that helps the author understand your reasoning and learn from the feedback. Distinguish between required changes that block approval and optional suggestions or nitpicks that are nice-to-have improvements. Ask questions when you do not understand something rather than assuming it is wrong, as the author may have context you lack. Acknowledge good work and clever solutions alongside pointing out issues, as positive feedback reinforces good practices. Keep review scope manageable by reviewing promptly and avoiding the temptation to request major refactoring that should be a separate task.

Q: How do you recover a file that was accidentally deleted and committed in Git?
A: First, use git log to find the commit hash where the file still existed, or use git log --all --full-history -- path/to/file to see the history of that specific file. Once you identify the last commit containing the file, you can restore it using git checkout commit_hash -- path/to/file which retrieves that specific file from the old commit and stages it. Alternatively, git show commit_hash:path/to/file will display the file contents, which you can redirect to recreate the file. If you need to find when the file was deleted, git log --diff-filter=D --summary will show all commits that deleted files. After restoring the file, commit the restoration to add it back to your repository. This demonstrates Git's power as a time machine for your code, where almost nothing is truly lost as long as it was committed at some point.

Q: What is infrastructure as code (IaC) and what are its benefits?
A: Infrastructure as Code is the practice of managing and provisioning computing infrastructure through machine-readable configuration files rather than manual processes or interactive configuration tools. Tools like Terraform, CloudFormation, Ansible, and Pulumi allow you to define servers, networks, databases, and other infrastructure in code that can be version controlled, reviewed, and tested. IaC enables consistent environments because the same code produces identical infrastructure every time it runs, eliminating configuration drift between environments. It supports disaster recovery by allowing you to recreate your entire infrastructure from code if needed. Changes to infrastructure go through the same review and approval processes as application code, improving security and reducing errors. IaC also enables self-service infrastructure where developers can provision resources they need without waiting for operations teams, while still maintaining governance through code reviews and policy enforcement.

Q: What is the purpose of git stash and when should you use it?
A: Git stash temporarily saves your uncommitted changes and reverts your working directory to match the HEAD commit, allowing you to switch contexts without committing incomplete work. This is useful when you need to quickly switch to another branch to fix an urgent bug but have work in progress that is not ready for a commit. Use git stash push to save changes, optionally with -m "message" to describe what you stashed for easier identification later. Git stash list shows all stashed changes, and git stash pop applies the most recent stash and removes it from the stash list. You can also use git stash apply to apply changes while keeping them in the stash, useful if you want to apply the same changes to multiple branches. Be cautious with stashes as they can accumulate and become confusing; for longer-term work in progress, creating a work-in-progress commit on a branch is often a better approach.

Q: How do you implement blue-green deployments and what problems do they solve?
A: Blue-green deployment maintains two identical production environments where one (blue) serves live traffic while the other (green) is idle or being updated with the new version. When you deploy, you update the idle environment, run tests against it, and then switch traffic from blue to green by updating the load balancer or DNS. This approach enables zero-downtime deployments because users are instantly switched from old to new without any interruption in service. If problems are discovered after switching, you can immediately roll back by redirecting traffic back to the previous environment. Blue-green deployments also allow thorough testing of the new version in a production-identical environment before exposing it to users. The main challenges are the cost of maintaining two production environments and managing database schema changes that must be compatible with both versions during the transition period.

Q: What is the difference between git reset and git revert, and when should you use each?
A: Git reset moves the branch pointer backward to a previous commit, effectively removing commits from the branch history, and can optionally modify the staging area and working directory depending on the mode used (soft, mixed, or hard). Git revert creates a new commit that undoes the changes made by a specific commit, preserving the original commit in history while adding a new commit that reverses its effects. Use reset for local commits that have not been pushed, when you want to completely remove commits from history as if they never happened. Use revert for commits that have been shared with others, because it does not rewrite history and therefore does not cause problems for team members who have pulled those commits. Reset with the hard option is particularly dangerous as it discards all uncommitted changes, so always ensure you have no important unsaved work before using it. The key principle is that rewriting history is acceptable for local work but should be avoided for shared commits.

Q: What strategies can you use to manage secrets and sensitive configuration in DevOps pipelines?
A: Never store secrets in source code or configuration files that are committed to version control, as this exposes them to everyone with repository access and makes them difficult to rotate. Use dedicated secrets management tools like HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or Kubernetes Secrets to store and retrieve sensitive values at runtime. CI/CD platforms provide encrypted secret variables that are injected into pipeline runs without being visible in logs or configuration files. Implement the principle of least privilege by giving each application and service access only to the specific secrets it needs. Rotate secrets regularly and have a process for emergency rotation if a secret is compromised. Use different secrets for each environment (development, staging, production) to limit the blast radius of any exposure and prevent development credentials from accidentally being used against production systems.

Q: How do you use git bisect to find the commit that introduced a bug?
A: Git bisect performs a binary search through your commit history to efficiently find the commit that introduced a bug, even across hundreds or thousands of commits. Start with git bisect start, then mark the current commit as bad with git bisect bad and identify a known good commit with git bisect good commit_hash. Git then checks out a commit halfway between good and bad, and you test whether the bug exists at that point, marking it as good or bad accordingly. This process repeats, halving the search space each time, until Git identifies the exact commit that introduced the bug. You can automate this process with git bisect run script.sh where the script returns 0 for good commits and non-zero for bad commits, allowing Git to find the problematic commit without manual intervention. After finding the bug, use git bisect reset to return to your original branch and examine the identified commit to understand what change caused the problem.

Q: What is a monorepo and what are the tradeoffs of using one versus multiple repositories?
A: A monorepo stores multiple projects, services, or packages in a single repository, allowing atomic commits that span multiple components and simplifying dependency management between related code. Companies like Google, Facebook, and Microsoft use monorepos to enable large-scale code sharing, consistent tooling, and easier refactoring across their entire codebase. The advantages include simplified dependency management, easier code sharing, atomic changes across multiple projects, and consistent tooling and configurations. However, monorepos can become slow as they grow, requiring specialized tooling for efficient operations, and access control becomes more complex when different teams need different permissions. Multiple repositories (polyrepo) provide clearer boundaries between projects, independent versioning and release cycles, and simpler access control, but make cross-cutting changes more difficult and can lead to dependency versioning challenges. The choice depends on your team structure, how tightly coupled your projects are, and whether you have the tooling to support monorepo operations at scale.

Q: What are feature flags and how do they support continuous deployment?
A: Feature flags are conditional statements in code that enable or disable functionality based on configuration, allowing you to deploy code to production without immediately exposing new features to users. They support continuous deployment by decoupling deployment from release: you can deploy incomplete features behind flags, enabling trunk-based development without long-lived feature branches. Feature flags enable gradual rollouts where you can expose new features to a small percentage of users, monitor for problems, and gradually increase exposure while having the ability to instantly disable the feature if issues arise. They also support A/B testing by showing different variations to different user segments and measuring which performs better. Operations teams can use flags as kill switches to disable problematic features without deploying new code. The main challenges are technical debt from accumulating flags that should be cleaned up after features are fully released, and the complexity of testing all possible flag combinations.

Q: What is Git Flow and when should you use it?
A: Git Flow is a branching model that defines a strict branching structure designed around project releases. It uses two main branches: master (or main) for production-ready code and develop for integration of features. Feature branches are created from develop, while release and hotfix branches handle versioning and urgent fixes. Git Flow is ideal for projects with scheduled release cycles, such as traditional software products with version numbers. However, it can be overly complex for continuous deployment environments where simpler strategies like GitHub Flow or trunk-based development may be more appropriate.

Q: What is the difference between git rebase and git merge, and when should you use each?
A: Git merge creates a new commit that combines two branches while preserving the complete history of both branches, resulting in a merge commit. Git rebase, on the other hand, replays your commits on top of another branch, creating a linear history without merge commits. Use merge when you want to preserve the exact history of how features were developed and integrated, especially on shared branches. Use rebase for cleaning up local commits before pushing, or to incorporate upstream changes into a feature branch while maintaining a clean, linear history. Never rebase commits that have been pushed to a shared repository, as this rewrites history and can cause problems for other collaborators.

Q: What are the key stages of a typical CI/CD pipeline?
A: A typical CI/CD pipeline consists of several key stages that automate the software delivery process. The first stage is source control, where code changes trigger the pipeline. The build stage compiles the code and creates artifacts. The test stage runs automated tests including unit tests, integration tests, and sometimes end-to-end tests. Static analysis performs code quality checks and security scanning. The artifact stage stores built packages in a registry. The deploy stage pushes the application to various environments (development, staging, production). Finally, monitoring and feedback stages collect metrics and alert teams to issues. Each stage acts as a quality gate, preventing problematic code from advancing further in the pipeline.

Q: How does Docker differ from traditional virtual machines?
A: Docker containers and virtual machines (VMs) both provide isolation but at different levels. VMs virtualize the entire hardware stack, running a complete guest operating system on top of a hypervisor, which consumes significant resources. Docker containers share the host OS kernel and only package the application and its dependencies, making them much lighter and faster to start. Containers typically use megabytes of storage and start in seconds, while VMs use gigabytes and take minutes to boot. However, VMs provide stronger isolation since they have separate kernels, making them more suitable for running untrusted workloads or different operating systems. Docker excels at packaging microservices and ensuring consistent environments across development, testing, and production.

Q: What is a Kubernetes Pod and how does it relate to containers?
A: A Pod is the smallest deployable unit in Kubernetes and represents a single instance of a running process in your cluster. A Pod can contain one or more containers that share storage, network, and specifications for how to run. Containers within a Pod share the same IP address and port space, can communicate via localhost, and can share volumes. The most common pattern is a single-container Pod, but multi-container Pods are used for sidecar patterns where helper containers provide logging, monitoring, or proxy functionality. Pods are ephemeral by design and can be terminated and replaced at any time, which is why higher-level controllers like Deployments manage their lifecycle and ensure the desired number of replicas are running.

Q: What is Infrastructure as Code (IaC) and what are its benefits?
A: Infrastructure as Code is the practice of managing and provisioning computing infrastructure through machine-readable configuration files rather than manual processes or interactive tools. Tools like Terraform, Ansible, Pulumi, and CloudFormation enable teams to define infrastructure declaratively. The key benefits include version control for infrastructure changes, enabling code review and audit trails. IaC ensures consistency by eliminating configuration drift between environments. It enables rapid provisioning and destruction of environments, supporting practices like ephemeral staging environments. Disaster recovery becomes faster since infrastructure can be recreated from code. Teams can test infrastructure changes before applying them to production, and documentation is inherent in the code itself.

Q: What is the difference between blue-green deployments and canary deployments?
A: Blue-green deployment maintains two identical production environments called blue and green. At any time, one environment serves live traffic while the other is idle or staging the new version. When deploying, you switch traffic from the current environment to the updated one, enabling instant rollback by switching back. Canary deployment, in contrast, gradually routes a small percentage of traffic to the new version while most traffic continues to the stable version. The percentage is slowly increased as confidence grows, allowing teams to detect issues with minimal user impact. Blue-green requires double the infrastructure but provides instant, complete switchover. Canary uses resources more efficiently and provides real-world testing with production traffic, but rollback is slower and more complex.

Q: How do you handle database migrations in a CI/CD pipeline?
A: Database migrations in CI/CD require careful handling to avoid downtime and data loss. Use migration tools like Flyway, Liquibase, or framework-specific tools like Django migrations or Rails ActiveRecord. Migrations should be version-controlled alongside application code and run automatically as part of the deployment pipeline. Design migrations to be backward-compatible, especially for zero-downtime deployments where old and new application versions may run simultaneously. Use expand-contract patterns: first add new columns or tables, deploy the new code, then remove old structures in a later migration. Always test migrations against production-like data volumes since operations that are fast on small datasets can lock tables for extended periods on large datasets. Maintain rollback scripts for each migration, even if you rarely use them.

Q: What is GitOps and how does it improve operations?
A: GitOps is an operational framework that applies DevOps best practices for infrastructure automation, using Git as the single source of truth for declarative infrastructure and applications. In GitOps, the desired state of the system is versioned in Git, and automated processes ensure the actual state matches the desired state. Changes are made through pull requests, enabling code review, approval workflows, and audit trails for all infrastructure changes. Tools like ArgoCD or Flux continuously monitor Git repositories and automatically apply changes to Kubernetes clusters. GitOps improves operations by providing complete version history, easy rollbacks, consistent environments, and developer-friendly workflows. It shifts the operational model from imperative commands to declarative desired state, reducing configuration drift and improving reliability.

Q: What are the key metrics to monitor in a production system?
A: The four golden signals provide a foundation for monitoring: latency (how long requests take), traffic (demand on the system), errors (rate of failed requests), and saturation (how full the system is). Beyond these, monitor application-specific metrics like queue depths, cache hit rates, and business metrics. Infrastructure metrics include CPU, memory, disk I/O, and network utilization. For distributed systems, track request tracing to understand latency across services. Set up alerting on symptoms (user-facing issues) rather than just causes (high CPU). Use percentiles rather than averages for latency to catch tail latency issues. Implement structured logging for easier querying and correlation. Create dashboards that show service health at a glance while enabling drill-down for troubleshooting. Store metrics with sufficient retention for capacity planning and trend analysis.

Q: What is the purpose of git cherry-pick and when should you use it?
A: Git cherry-pick applies the changes from a specific commit to your current branch, creating a new commit with those changes. This is useful when you need to apply a specific fix or feature from one branch to another without merging the entire branch. Common use cases include applying a hotfix from a release branch back to the development branch, or pulling a single feature commit from a feature branch that is not ready for full integration. Cherry-pick is also valuable when you accidentally committed to the wrong branch and need to move that commit. However, overuse of cherry-pick can lead to duplicate commits and merge conflicts later. For regular integration of changes, prefer merge or rebase. When cherry-picking, be aware that the new commit will have a different SHA since it has a different parent, which can complicate history tracking.

Q: How do you implement secrets management in a CI/CD pipeline?
A: Secrets management in CI/CD requires keeping sensitive data like API keys, passwords, and certificates secure while making them available to build and deployment processes. Never store secrets in version control, even in private repositories. Use dedicated secrets management tools like HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or cloud-native solutions. CI/CD platforms like GitHub Actions, GitLab CI, and Jenkins provide encrypted secrets storage that injects values as environment variables during pipeline execution. Implement the principle of least privilege, giving each service or pipeline only the secrets it needs. Rotate secrets regularly and automate the rotation process where possible. Audit secret access and use separate secrets for different environments. For container deployments, Kubernetes Secrets or external secrets operators can inject secrets at runtime rather than baking them into images.

Q: What is a service mesh and when would you implement one?
A: A service mesh is a dedicated infrastructure layer that handles service-to-service communication in a microservices architecture. It provides capabilities like load balancing, service discovery, encryption, observability, and traffic management without requiring changes to application code. Popular implementations include Istio, Linkerd, and Consul Connect. A service mesh is valuable when you have many microservices that need consistent security policies, detailed telemetry, or sophisticated traffic routing like canary deployments or A/B testing. The mesh works by deploying sidecar proxies alongside each service instance, intercepting all network traffic. However, service meshes add operational complexity and resource overhead. Consider implementing one when the benefits outweigh these costs, typically in larger deployments where manual implementation of these features would be impractical or inconsistent.

Q: What is trunk-based development and how does it differ from feature branch workflows?
A: Trunk-based development is a branching strategy where developers collaborate on a single branch called trunk or main, with short-lived feature branches that last at most a few days. Changes are integrated frequently, often multiple times per day, keeping the trunk always in a releasable state. This contrasts with feature branch workflows where branches can live for weeks or months before merging. Trunk-based development reduces merge conflicts, enables continuous integration, and forces teams to break work into small, incremental changes. It requires strong automated testing and often uses feature flags to hide incomplete features from users. Release branches may still be used for hotfixes to production versions. This approach is favored by high-performing DevOps teams as it minimizes integration pain and supports continuous deployment. However, it requires discipline and good practices like code review, pair programming, and comprehensive test suites.

Q: How do you design a disaster recovery strategy for cloud infrastructure?
A: A robust disaster recovery strategy starts with defining Recovery Time Objective (RTO) and Recovery Point Objective (RPO) for each system. RTO is the maximum acceptable downtime, while RPO is the maximum acceptable data loss. Based on these requirements, implement appropriate backup strategies: point-in-time recovery for databases, cross-region replication for critical data, and infrastructure-as-code for rapid environment recreation. Use multi-region or multi-zone deployments for high availability. Implement automated health checks and failover mechanisms. Store backups in geographically separate locations with different failure domains. Regularly test disaster recovery procedures through chaos engineering practices and scheduled drills. Document runbooks for recovery procedures and ensure multiple team members are trained. Consider the cost trade-offs between different DR strategies: cold standby is cheapest but has longer recovery times, while hot standby with active replication is expensive but enables near-instant failover. Automate as much of the recovery process as possible to reduce human error during high-stress situations.
