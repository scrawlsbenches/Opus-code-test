Q: What distinguishes hard real-time systems from soft real-time systems?
A: Hard real-time systems have strict timing constraints where missing a deadline constitutes a system failure, often with catastrophic consequences such as in medical devices, aircraft control systems, or nuclear plant monitoring. Soft real-time systems have more flexible timing requirements where occasional deadline misses degrade performance but do not cause system failure, as seen in video streaming or online gaming. The key distinction lies in the consequences of missing deadlines: hard systems require deterministic guarantees and formal verification, while soft systems can employ best-effort approaches with statistical quality of service targets.

Q: How do latency requirements differ between financial trading systems and consumer applications?
A: Financial high-frequency trading systems demand sub-millisecond latency, often measured in microseconds, where even nanosecond delays can result in significant monetary losses due to market price movements. Consumer applications typically tolerate latency in the tens to hundreds of milliseconds range, with users perceiving delays under 100ms as instantaneous. Trading systems achieve ultra-low latency through kernel bypass networking, FPGA acceleration, and co-location with exchange servers, while consumer apps focus on perceived responsiveness through optimistic UI updates and progressive loading strategies.

Q: What are the key differences between WebSockets and Server-Sent Events for real-time communication?
A: WebSockets provide full-duplex bidirectional communication over a single persistent TCP connection, making them ideal for interactive applications like chat, collaborative editing, and gaming where both client and server need to send data freely. Server-Sent Events (SSE) offer unidirectional server-to-client streaming over HTTP, which simplifies implementation and works seamlessly with existing HTTP infrastructure including proxies, load balancers, and firewalls. WebSockets require special handling for connection management and reconnection logic, while SSE has built-in automatic reconnection and event ID tracking, making it preferable for scenarios like live feeds, notifications, and real-time dashboards where clients primarily receive data.

Q: How does long polling work and when should it be used over WebSockets?
A: Long polling maintains an open HTTP request until the server has new data to send, then immediately issues a new request upon receiving a response, simulating a persistent connection through sequential requests. This technique works well in environments where WebSocket connections are blocked by firewalls or proxies, providing broader compatibility at the cost of higher latency and increased server overhead from repeated connection establishment. Long polling remains valuable for legacy system integration, environments with strict network policies, and scenarios requiring simple implementation without WebSocket infrastructure, though modern applications should prefer WebSockets or SSE when infrastructure permits.

Q: What characteristics define a real-time database and how does it differ from traditional databases?
A: Real-time databases are designed for immediate data synchronization and live queries, automatically pushing updates to connected clients when underlying data changes without requiring manual polling or refresh operations. Unlike traditional request-response databases, real-time databases like Firebase Realtime Database, RethinkDB, or Supabase maintain persistent connections and use change data capture to detect modifications and broadcast them to subscribers. These systems optimize for low-latency reads and fan-out to many clients, often trading off consistency guarantees and complex query capabilities found in traditional relational databases.

Q: What is CRDT and how does it enable real-time collaborative editing without conflicts?
A: Conflict-free Replicated Data Types (CRDTs) are data structures mathematically designed to be merged without conflicts, allowing multiple users to edit simultaneously without coordination or locking. CRDTs guarantee eventual consistency by ensuring that all replicas converge to the same state regardless of the order in which operations are received, using techniques like vector clocks, unique identifiers, and commutative or idempotent operations. Common CRDT types include G-Counters for increment-only values, LWW-Registers for last-writer-wins semantics, and sequence CRDTs like LSEQ or RGA for collaborative text editing in applications like Figma, Google Docs alternatives, and distributed note-taking tools.

Q: How does Operational Transformation differ from CRDT for collaborative editing?
A: Operational Transformation (OT) works by transforming operations against concurrent edits to preserve user intent, requiring a central server to serialize operations and compute transformations, as implemented in Google Docs and many collaborative coding tools. Unlike CRDTs which are inherently decentralized and conflict-free, OT algorithms require careful ordering guarantees and become increasingly complex with multiple operation types, though they typically produce more compact operation representations. OT excels in server-centric architectures with reliable connectivity, while CRDTs better suit peer-to-peer scenarios, offline-first applications, and systems where network partitions are common.

Q: What are presence systems and how are they implemented in real-time applications?
A: Presence systems track and display the real-time status of users, showing who is online, idle, or actively engaged, commonly seen as typing indicators, cursor positions, or avatar highlights in collaborative applications. Implementation typically involves heartbeat mechanisms where clients periodically signal their status to a server, combined with pub/sub channels to broadcast presence changes to interested parties. Challenges include handling network disconnections gracefully with appropriate timeouts, scaling presence state across distributed servers using consistent hashing or dedicated presence services, and minimizing bandwidth through delta updates rather than full presence state broadcasts.

Q: How should rate limiting be implemented in real-time systems without degrading user experience?
A: Effective rate limiting in real-time systems uses token bucket or leaky bucket algorithms that allow burst traffic while enforcing average rate limits, preventing abuse without penalizing legitimate rapid interactions common in collaborative editing or gaming. Implementation should differentiate between operation types, applying stricter limits to expensive operations like database writes while allowing more frequent lightweight operations like cursor movements or typing indicators. Client-side rate limiting with exponential backoff, combined with server-side enforcement and clear feedback through HTTP 429 responses with Retry-After headers, maintains system stability while keeping users informed about temporary restrictions.

Q: What networking techniques do multiplayer games use to handle real-time synchronization?
A: Multiplayer games employ client-side prediction where the local client immediately applies player inputs and renders results, then reconciles with authoritative server state through rollback and replay when corrections arrive, masking network latency from players. Server reconciliation uses techniques like entity interpolation, where clients render other players slightly in the past using buffered state updates, and lag compensation on the server to account for network delay when processing hit detection and interactions. Games also implement dead reckoning to extrapolate entity positions between updates, delta compression to minimize bandwidth by sending only changed state, and priority systems that allocate bandwidth to the most relevant entities based on distance and game significance.

Q: What is the optimistic UI pattern and how does it improve perceived real-time performance?
A: Optimistic UI immediately reflects user actions in the interface before server confirmation, assuming the operation will succeed, then reconciles with actual server state when the response arrives, making applications feel instantaneous despite network latency. This pattern requires careful error handling to gracefully roll back changes if the server rejects the operation, typically through visual feedback indicating the failed state and offering retry options. Applications like Twitter, Facebook, and Slack use optimistic UI for likes, messages, and reactions, balancing perceived responsiveness against the occasional need to correct optimistic assumptions when conflicts or failures occur.

Q: How do event-driven architectures support real-time system requirements?
A: Event-driven architectures decouple producers and consumers through message queues or event streams, enabling real-time systems to handle variable load by buffering events during traffic spikes and processing them asynchronously at sustainable rates. This architecture supports real-time features by allowing multiple consumers to react to the same events simultaneously, enabling features like real-time notifications, activity feeds, and live dashboards from a single event source. Systems like Apache Kafka provide ordered, durable event logs that support both real-time stream processing and historical replay, allowing new consumers to catch up on past events while also receiving live updates.

Q: What strategies help maintain consistency in distributed real-time systems?
A: Distributed real-time systems often adopt eventual consistency models where replicas may temporarily diverge but guarantee convergence, using vector clocks or hybrid logical clocks to track causality and detect concurrent modifications. Consistency strategies include read-your-writes guarantees through sticky sessions or version tokens, causal consistency that preserves operation ordering visible to each user, and quorum-based approaches that trade latency for stronger consistency by requiring acknowledgment from multiple replicas. The choice between consistency levels depends on application requirements: collaborative editing may tolerate eventual consistency with CRDT-based merging, while financial systems require stronger guarantees through techniques like distributed transactions or saga patterns.

Q: How do real-time systems handle connection management and reconnection?
A: Robust real-time systems implement connection management with heartbeat mechanisms to detect dead connections, automatic reconnection with exponential backoff to prevent thundering herd problems during server restarts, and session resumption to restore state after brief disconnections. Connection state tracking enables servers to maintain context across reconnections, using session tokens or connection IDs to resume subscriptions and replay missed events from persistent buffers or event logs. Edge cases like split-brain scenarios, where clients believe they are connected but messages are not delivered, require application-level acknowledgments and timeout-based failover to alternative servers or connection paths.

Q: What are the key metrics for monitoring real-time system health and performance?
A: Essential real-time system metrics include end-to-end latency percentiles (p50, p95, p99) measuring time from user action to visible update, message delivery success rates tracking the percentage of events successfully delivered to subscribers, and connection churn rates indicating client stability. Infrastructure metrics encompass message queue depths showing backpressure accumulation, fan-out latency measuring time to distribute events to all subscribers, and connection counts per server for capacity planning. Alerting should focus on latency budget violations where operations exceed acceptable bounds, delivery failure rates exceeding thresholds, and resource exhaustion indicators like memory pressure or file descriptor limits that precede system degradation.
