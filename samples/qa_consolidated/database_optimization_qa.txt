Database Optimization Q&A

Q: What is the primary purpose of database indexing and when should you create an index?
A: Database indexing creates a separate data structure that maintains pointers to rows based on specific column values, enabling the database to locate data without scanning entire tables. You should create indexes on columns frequently used in WHERE clauses, JOIN conditions, and ORDER BY statements. However, indexes have overhead costs for INSERT, UPDATE, and DELETE operations since the index must also be maintained, so avoid over-indexing columns that are rarely queried or frequently modified.

Q: How do you interpret an EXPLAIN plan and what are the most important metrics to examine?
A: An EXPLAIN plan shows the query execution strategy chosen by the database optimizer, revealing how tables are accessed and joined. The most critical metrics include the access type (full table scan vs index seek), estimated row counts, and join methods used. Look for sequential scans on large tables which indicate missing indexes, nested loop joins on large datasets which may benefit from hash joins, and high estimated costs relative to actual execution time. Understanding the difference between estimated and actual rows helps identify stale statistics.

Q: What is connection pooling and why is it essential for database performance?
A: Connection pooling maintains a cache of database connections that can be reused across multiple client requests, eliminating the overhead of establishing new connections for each query. Creating a database connection involves TCP handshakes, authentication, and memory allocation, which can take 50-100ms or more. By reusing connections from a pool, applications can serve thousands of requests per second while maintaining only dozens of actual database connections, dramatically reducing both latency and server resource consumption.

Q: When should you consider implementing read replicas and what are the tradeoffs?
A: Read replicas should be considered when your application has a read-heavy workload that exceeds what a single database instance can handle, or when you need geographic distribution for lower latency. The primary tradeoff is replication lag, meaning replicas may serve slightly stale data which is problematic for use cases requiring strong consistency. Read replicas also increase infrastructure complexity and costs, and you must implement logic to route queries appropriately between the primary and replicas.

Q: What is database sharding and what challenges does it introduce?
A: Sharding horizontally partitions data across multiple database instances based on a shard key, allowing databases to scale beyond single-server limits for both storage and throughput. The main challenges include choosing an appropriate shard key that evenly distributes data and queries, handling cross-shard queries which require scatter-gather operations, and managing transactions that span multiple shards. Resharding when data distribution becomes uneven is particularly complex and often requires significant downtime or sophisticated online migration strategies.

Q: How does denormalization improve query performance and when is it appropriate?
A: Denormalization intentionally introduces data redundancy by storing derived or copied data to eliminate expensive JOIN operations at query time. This is appropriate for read-heavy workloads where the same complex queries run frequently, such as reporting dashboards or product catalog displays. The tradeoff is increased storage requirements and the need to maintain consistency across redundant data during writes. Materialized views offer a managed form of denormalization where the database automatically maintains the derived data.

Q: What role do caching layers play in database optimization and where should they be implemented?
A: Caching layers store frequently accessed data in faster storage tiers like Redis or Memcached to reduce database load and improve response times. They should be implemented at multiple levels: application-level caching for computed results, query result caching for expensive aggregations, and object caching for frequently accessed entities. The key challenges are cache invalidation strategies to prevent stale data, cache warming after restarts, and cache stampede prevention when many requests simultaneously miss the cache.

Q: What do VACUUM and ANALYZE commands do in PostgreSQL and why are they critical?
A: VACUUM reclaims storage occupied by dead tuples left behind by UPDATE and DELETE operations, preventing table bloat and maintaining query performance. ANALYZE updates the statistics that the query planner uses to choose optimal execution plans. Without regular VACUUM, tables grow indefinitely and queries slow down; without ANALYZE, the planner makes poor decisions based on outdated statistics. Most PostgreSQL deployments rely on autovacuum but may need manual tuning of its aggressiveness for high-write workloads.

Q: How do you identify and analyze slow queries in a production database?
A: Slow query analysis starts with enabling the database's slow query log with an appropriate threshold, typically starting at 100ms and adjusting based on your SLA requirements. Examine the slow query log for patterns including frequently repeated queries, queries with high execution times, and queries appearing during peak load periods. Use EXPLAIN ANALYZE on identified queries to understand their execution plans, and correlate slow queries with system metrics like CPU, memory, and disk I/O to distinguish between query optimization issues and resource constraints.

Q: What is the N+1 query problem and how do you solve it?
A: The N+1 query problem occurs when code fetches a list of N records and then executes a separate query for each record to fetch related data, resulting in N+1 total queries instead of an optimal 2. This commonly happens with ORM lazy loading when iterating over a collection and accessing related entities. Solutions include eager loading to fetch all related data in a single JOIN query, batch loading to fetch related data in chunks using IN clauses, or implementing a DataLoader pattern that automatically batches and caches requests within a single request context.

Q: When should you use batch operations instead of individual database operations?
A: Batch operations should be used whenever you need to insert, update, or delete multiple rows, as each individual operation incurs network round-trip latency, transaction overhead, and logging costs. Bulk INSERT statements can be 10-100x faster than individual inserts by amortizing these fixed costs across many rows. Similarly, UPDATE and DELETE statements with WHERE clauses affecting multiple rows are far more efficient than loops of individual operations. Most databases also support COPY commands or bulk loading utilities for maximum throughput when loading large datasets.

Q: How do composite indexes differ from single-column indexes and when should you use them?
A: Composite indexes contain multiple columns in a specific order and can satisfy queries that filter or sort on any left prefix of those columns. A composite index on (country, city, street) can efficiently serve queries filtering on country alone, country and city, or all three columns, but not queries filtering only on city or street. Use composite indexes when queries consistently filter on the same combination of columns, particularly for covering indexes that include all columns needed by a query to avoid table lookups entirely.

Q: What is query optimization and what techniques do database optimizers use?
A: Query optimization is the process by which the database chooses the most efficient execution plan from many possible ways to execute a query. Optimizers use statistics about data distribution, available indexes, and cost models to estimate the expense of different plans. Key techniques include predicate pushdown to filter early, join reordering to minimize intermediate result sizes, index selection, and choosing between nested loop, hash, and merge join algorithms. Modern optimizers may also apply transformations like subquery flattening and common subexpression elimination.

Q: How do you optimize queries that involve sorting large result sets?
A: Sorting large result sets is expensive because it requires either sufficient memory to hold all rows or spilling to disk for external sorting. The primary optimization is creating an index that matches the ORDER BY clause, allowing the database to read rows in sorted order without a separate sort step. For queries with both WHERE and ORDER BY clauses, a composite index covering both can eliminate both the filter scan and the sort. When indexes are not practical, consider pagination with keyset pagination instead of OFFSET, or pre-computing and caching sorted results.

Q: What monitoring metrics are most important for database performance optimization?
A: Critical database metrics include query throughput and latency distributions, connection pool utilization, cache hit ratios for both buffer cache and query cache, lock wait times and deadlock frequency, and replication lag for replica setups. At the system level, monitor CPU utilization, memory pressure, disk I/O latency, and network throughput. Correlate spikes in these metrics with slow query occurrences to identify root causes. Establish baselines during normal operation so you can quickly detect anomalies and performance regressions after deployments or data growth.
