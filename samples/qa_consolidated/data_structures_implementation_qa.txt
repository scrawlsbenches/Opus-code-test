Q: What are the main collision resolution strategies in hash table implementations, and when should each be preferred?
A: The two primary collision resolution strategies are chaining and open addressing. Chaining stores colliding elements in linked lists at each bucket, offering simpler deletion and consistent performance even at high load factors. Open addressing (including linear probing, quadratic probing, and double hashing) stores all elements directly in the array, providing better cache locality but degraded performance as load factor increases. Chaining is preferred when deletion frequency is high or load factor exceeds 0.7, while open addressing excels in memory-constrained environments with predictable insertion patterns.

Q: How do red-black trees maintain balance, and what are the specific properties they must satisfy?
A: Red-black trees maintain balance through five invariant properties: every node is either red or black, the root is always black, all leaves (NIL nodes) are black, red nodes cannot have red children, and every path from root to leaf contains the same number of black nodes. When insertions or deletions violate these properties, the tree performs rotations and recoloring operations to restore balance. This guarantees O(log n) height by ensuring the longest path is never more than twice the shortest path, providing predictable worst-case performance for all operations.

Q: What distinguishes B-trees from binary search trees, and why are they preferred for database indexing?
A: B-trees are balanced multi-way search trees where each node can contain multiple keys and children, with a configurable branching factor typically chosen to match disk block sizes. Unlike binary trees with two children per node, B-trees minimize disk I/O by maximizing keys per disk read and maintaining shallow tree heights even for massive datasets. The self-balancing property ensures all leaf nodes remain at the same depth, guaranteeing O(log n) operations. Database systems prefer B-trees because a single disk read can retrieve an entire node containing hundreds of keys, dramatically reducing the number of expensive disk accesses needed for searches.

Q: How do skip lists achieve probabilistic balancing, and what are their advantages over balanced binary search trees?
A: Skip lists use randomized tower heights to create multiple linked list levels, where higher levels act as express lanes for faster traversal. When inserting an element, a coin-flip process determines how many levels it participates in, with each level having half the elements of the level below on average. This probabilistic approach achieves expected O(log n) search time without requiring complex rebalancing rotations. Skip lists offer simpler implementation, easier concurrent access patterns, and cache-friendly sequential memory layout compared to tree structures, making them popular in databases like Redis and LevelDB.

Q: What is the mathematical basis for bloom filter false positive rates, and how should the filter be sized?
A: The false positive probability in bloom filters is approximately (1 - e^(-kn/m))^k, where k is the number of hash functions, n is the number of inserted elements, and m is the bit array size. For optimal performance, k should equal (m/n) * ln(2), roughly 0.7 times the bits-per-element ratio. To achieve a target false positive rate p, the filter needs approximately -n*ln(p)/(ln(2))^2 bits. This mathematical foundation allows precise capacity planning, ensuring bloom filters provide space-efficient probabilistic set membership testing with guaranteed upper bounds on false positive rates while never producing false negatives.

Q: How is an LRU cache typically implemented to achieve O(1) time complexity for all operations?
A: An LRU cache combines a hash map with a doubly-linked list to achieve O(1) get, put, and eviction operations. The hash map provides constant-time key lookup, mapping keys to corresponding nodes in the doubly-linked list. The linked list maintains access order, with recently accessed items moved to the head and the least recently used item always at the tail. When the cache reaches capacity, the tail node is evicted in O(1) time by updating a few pointers. This hybrid data structure elegantly solves the problem of maintaining both fast access and temporal ordering simultaneously.

Q: What optimizations make union-find with path compression and union by rank achieve near-constant amortized time?
A: Union-find achieves nearly O(1) amortized time through two key optimizations working together. Path compression flattens the tree structure during find operations by making each traversed node point directly to the root, dramatically reducing future traversal distances. Union by rank (or size) always attaches the smaller tree under the larger tree's root, preventing the creation of long chains. Together, these optimizations yield O(alpha(n)) amortized time per operation, where alpha is the inverse Ackermann function that grows so slowly it's effectively constant (less than 5) for any practical input size. This makes union-find ideal for dynamic connectivity problems like Kruskal's algorithm.

Q: How do segment trees support efficient range queries and point updates simultaneously?
A: Segment trees are binary trees where each node stores aggregate information about a range of the underlying array, with leaves representing individual elements and internal nodes representing merged intervals. A query traverses O(log n) nodes by recursively visiting only nodes whose ranges overlap with the query range, combining their stored values. Point updates propagate from leaf to root, updating O(log n) ancestor nodes. The key insight is that any contiguous range can be decomposed into O(log n) disjoint pre-computed segments, enabling both queries and updates in logarithmic time. Lazy propagation extends this to support range updates while maintaining the same complexity.

Q: What is the fundamental principle behind Fenwick trees, and how do they differ from segment trees?
A: Fenwick trees (Binary Indexed Trees) exploit binary representations to implicitly store cumulative sums, where each index i stores the sum of elements from (i - lowbit(i) + 1) to i, with lowbit(i) being the lowest set bit. This encoding allows prefix sum queries by summing O(log n) strategically positioned partial sums following the binary representation of the index. Unlike segment trees requiring 2n-4n space and explicit tree structure, Fenwick trees use exactly n space with array indices serving as implicit navigation. While segment trees support arbitrary range queries directly, Fenwick trees compute range sums as the difference of two prefix sums, trading some flexibility for simpler implementation and lower memory overhead.

Q: What makes data structures persistent, and what techniques enable efficient persistent implementations?
A: Persistent data structures preserve all previous versions after modifications, enabling access to any historical state without full copying. The key technique is path copying, where modifications only duplicate nodes along the path from root to the changed location, sharing unchanged subtrees between versions. For balanced trees, this yields O(log n) time and space per update while maintaining O(log n) queries on any version. Fat nodes offer an alternative by storing modification history within nodes themselves. Confluently persistent structures additionally support merging version histories. These techniques are fundamental to functional programming, database MVCC implementations, and undo systems.

Q: How does cuckoo hashing achieve worst-case O(1) lookup time, and what are its implementation challenges?
A: Cuckoo hashing uses two hash tables with two hash functions, guaranteeing each key is in exactly one of two possible positions, enabling O(1) worst-case lookups with a single comparison per table. Insertion follows a displacement chain: if both positions are occupied, an existing element is kicked out and reinserted using its alternate location, potentially triggering further displacements. The main challenges are handling insertion cycles (requiring rehashing with new hash functions) and maintaining low load factors (typically under 50% per table). Modern variants like bucketized cuckoo hashing improve space efficiency by allowing multiple keys per bucket while preserving constant-time lookups.

Q: What are the key differences between min-heaps and Fibonacci heaps in terms of implementation complexity and use cases?
A: Binary min-heaps use a simple array representation with O(log n) insert, delete-min, and decrease-key operations, implemented through straightforward bubble-up and bubble-down procedures. Fibonacci heaps achieve O(1) amortized insert and decrease-key with O(log n) delete-min through a lazy forest structure with sophisticated consolidation and cascading cuts. However, Fibonacci heaps have large constant factors, complex implementation, and poor cache performance. In practice, binary heaps outperform Fibonacci heaps for most workloads; Fibonacci heaps only provide advantages for algorithms with many decrease-key operations relative to delete-min, such as Dijkstra's algorithm on dense graphs.

Q: How do treaps combine properties of binary search trees and heaps, and what guarantees do they provide?
A: Treaps assign each node both a key (maintaining BST ordering) and a random priority (maintaining heap ordering), creating a unique tree structure determined by priority comparisons. The BST property enables efficient searching while random priorities ensure expected O(log n) height without explicit balancing. Insertions add nodes as leaves then rotate upward until heap property is restored; deletions rotate nodes down until they become leaves. The randomization provides probabilistic balance guarantees similar to skip lists, with simpler implementation than deterministic balanced trees. Treaps excel in scenarios requiring efficient split and merge operations, as these operations preserve both properties naturally.

Q: What implementation strategies enable efficient concurrent access to hash tables without global locking?
A: Concurrent hash tables employ several strategies to minimize contention. Lock striping partitions the table into segments with independent locks, allowing parallel access to different segments. Lock-free implementations use compare-and-swap operations for atomic updates, with techniques like Harris's linked list for chaining-based collision resolution. Read-copy-update (RCU) allows readers to proceed without synchronization while writers create modified copies. Hopscotch hashing provides cache-friendly concurrent access through neighborhood-based probing with fine-grained locking. The choice depends on read/write ratio, contention levels, and whether operations span multiple keys, with most systems favoring read-optimized designs given typical workload patterns.

Q: How do interval trees extend binary search trees to support efficient stabbing queries and overlap detection?
A: Interval trees augment balanced BST nodes with additional metadata to support queries finding all intervals containing a point (stabbing queries) or overlapping a range. Each node stores an interval and is ordered by left endpoint, while also maintaining the maximum right endpoint in its subtree as auxiliary data. Stabbing queries achieve O(log n + k) time, where k is the number of results, by pruning subtrees whose maximum endpoint falls short of the query point. Centered interval trees take an alternative approach, organizing intervals around median points with separate sorted lists by endpoints. These structures are essential for computational geometry, database query optimization, and scheduling conflict detection.
