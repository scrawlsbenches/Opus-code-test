Q: What is SQL injection and how can developers prevent it?
A: SQL injection is a code injection technique where attackers insert malicious SQL statements into application queries through user input fields. This vulnerability occurs when user-supplied data is concatenated directly into SQL queries without proper sanitization. Attackers can exploit this to bypass authentication, extract sensitive data, modify database contents, or even execute administrative operations. Prevention strategies include using parameterized queries (prepared statements), employing stored procedures, implementing input validation with allowlists, applying the principle of least privilege to database accounts, and using ORM frameworks that handle query construction safely. Modern web frameworks provide built-in protection, but developers must still be vigilant when writing raw SQL queries.

Q: What are the OWASP Top 10 vulnerabilities and why are they important?
A: The OWASP Top 10 is a regularly updated list of the most critical web application security risks, maintained by the Open Web Application Security Project. The current categories include Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable and Outdated Components, Identification and Authentication Failures, Software and Data Integrity Failures, Security Logging and Monitoring Failures, and Server-Side Request Forgery. This list is important because it represents a consensus among security experts about the most prevalent and dangerous vulnerabilities affecting web applications. Organizations use the OWASP Top 10 as a baseline for security testing, developer training, and compliance requirements. Understanding these vulnerabilities helps development teams prioritize security efforts and allocate resources effectively.

Q: How does Cross-Site Scripting (XSS) work and what are its different types?
A: Cross-Site Scripting occurs when an attacker injects malicious scripts into web pages viewed by other users, exploiting the trust a user has for a particular website. There are three main types: Stored XSS persists on the target server in databases or message forums, affecting all users who view the compromised content. Reflected XSS occurs when malicious scripts are reflected off a web server through error messages, search results, or other responses that include user input. DOM-based XSS happens when the vulnerability exists in client-side code rather than server-side, manipulating the Document Object Model directly. Prevention measures include encoding output data, validating and sanitizing input, implementing Content Security Policy headers, using HTTPOnly cookies to protect session data, and employing modern frameworks that automatically escape output.

Q: What is Cross-Site Request Forgery (CSRF) and how do anti-CSRF tokens work?
A: Cross-Site Request Forgery is an attack that forces authenticated users to execute unwanted actions on a web application where they are currently authenticated. The attacker tricks the victim into submitting a malicious request, leveraging the user's existing session with the target site. For example, a hidden form on a malicious website could transfer funds from a victim's bank account if they happen to be logged into that bank. Anti-CSRF tokens work by including a unique, unpredictable value in each form or request that the server verifies before processing. These tokens are tied to the user's session and change with each request or session, making it impossible for attackers to forge valid requests. Additional defenses include checking the Referer header, using SameSite cookie attributes, and requiring re-authentication for sensitive operations.

Q: What is the principle of least privilege and how does it apply to secure coding?
A: The principle of least privilege states that every program, user, and system component should operate using the minimum set of privileges necessary to complete its intended function. In secure coding, this means applications should request only the permissions they need, database connections should use accounts with restricted access, API keys should have limited scopes, and file system operations should be confined to specific directories. This principle reduces the attack surface by limiting what an attacker can accomplish even if they successfully exploit a vulnerability. Implementation includes creating separate database users for read and write operations, running services under dedicated non-root accounts, using capability-based security models, and regularly auditing permissions to remove unnecessary access rights.

Q: How should passwords be securely stored in a database?
A: Passwords should never be stored in plaintext or using reversible encryption. Instead, they should be hashed using a modern, slow hashing algorithm specifically designed for passwords, such as Argon2, bcrypt, or scrypt. These algorithms are intentionally computationally expensive to make brute-force attacks impractical. Each password should be hashed with a unique, randomly generated salt to prevent rainbow table attacks and ensure identical passwords produce different hashes. The salt should be stored alongside the hash. Additional security measures include setting minimum password complexity requirements, implementing rate limiting on login attempts, supporting multi-factor authentication, and using pepper (a secret key added to passwords before hashing) stored separately from the database. Regular security audits should verify that password storage meets current best practices.

Q: What is a penetration test and what are the main phases involved?
A: A penetration test is an authorized simulated cyberattack performed to evaluate the security of a system by attempting to exploit vulnerabilities just as a malicious attacker would. The main phases include reconnaissance (gathering information about the target through passive and active methods), scanning (identifying live hosts, open ports, and running services), vulnerability assessment (identifying potential weaknesses using automated tools and manual techniques), exploitation (attempting to compromise systems using discovered vulnerabilities), post-exploitation (determining the value of compromised systems and maintaining access), and reporting (documenting findings, risk levels, and remediation recommendations). Penetration tests can be black-box (no prior knowledge), white-box (full system knowledge), or gray-box (partial knowledge). Regular penetration testing helps organizations identify security gaps before malicious actors can exploit them.

Q: What is encryption and what is the difference between symmetric and asymmetric encryption?
A: Encryption is the process of converting plaintext data into ciphertext using an algorithm and key, making the data unreadable to unauthorized parties. Symmetric encryption uses the same key for both encryption and decryption, making it fast and efficient for large amounts of data, with algorithms like AES being widely used. The main challenge is securely sharing the key between parties. Asymmetric encryption uses a mathematically related key pair: a public key for encryption and a private key for decryption. This solves the key distribution problem since the public key can be shared openly, but it is computationally more expensive. Common asymmetric algorithms include RSA and elliptic curve cryptography. In practice, hybrid systems combine both: asymmetric encryption securely exchanges a symmetric session key, which then encrypts the actual data.

Q: What is input validation and why is it critical for application security?
A: Input validation is the process of verifying that user-supplied data meets expected criteria before the application processes it. This practice is critical because most attacks exploit applications that trust user input implicitly. Validation should occur on both client-side (for user experience) and server-side (for security, as client-side validation can be bypassed). Effective validation includes checking data type, length, format, and range; using allowlists rather than blocklists when possible; encoding or escaping special characters based on context; and rejecting invalid input rather than attempting to sanitize it. Input validation prevents injection attacks, buffer overflows, and many other vulnerability classes. It should be applied consistently across all entry points including form fields, URL parameters, HTTP headers, cookies, and API endpoints.

Q: What are security headers and which ones should every web application implement?
A: Security headers are HTTP response headers that instruct browsers to enable specific security features, adding layers of protection against common attacks. Essential headers include Content-Security-Policy (CSP), which prevents XSS by specifying allowed sources for scripts, styles, and other resources. X-Content-Type-Options with the nosniff value prevents MIME type sniffing attacks. X-Frame-Options or the frame-ancestors CSP directive protects against clickjacking by controlling whether the page can be embedded in frames. Strict-Transport-Security (HSTS) enforces HTTPS connections and prevents protocol downgrade attacks. X-XSS-Protection enables browser-based XSS filtering (though modern CSP is preferred). Referrer-Policy controls how much referrer information is included with requests. These headers provide defense-in-depth and should be configured based on the application's specific requirements and functionality.

Q: What is a security audit and how does it differ from a penetration test?
A: A security audit is a comprehensive, systematic evaluation of an organization's information systems, policies, and procedures against established standards or regulatory requirements. It examines documentation, configurations, access controls, and operational practices through interviews, observations, and technical reviews. Security audits are typically broader in scope than penetration tests, covering governance, risk management, compliance, physical security, and personnel policies in addition to technical controls. While penetration tests focus on actively exploiting vulnerabilities to demonstrate impact, audits assess whether proper security controls exist and are functioning as intended. Audits often result in compliance certifications and are conducted by internal teams or third-party auditors. Organizations typically need both: audits ensure security frameworks and processes are in place, while penetration tests validate that technical defenses actually work against real-world attack techniques.

Q: What is secure session management and what are common session-related vulnerabilities?
A: Secure session management involves properly creating, maintaining, and destroying user sessions to prevent unauthorized access. Sessions should use strong, randomly generated identifiers that are sufficiently long to resist brute-force attacks. Common vulnerabilities include session fixation (attacker sets a known session ID before authentication), session hijacking (stealing valid session tokens through XSS or network interception), insufficient session expiration (sessions remaining valid too long), and insecure session storage. Best practices include regenerating session IDs after authentication and privilege changes, setting appropriate timeout values for both idle and absolute session duration, transmitting session tokens only over HTTPS, using HTTPOnly and Secure cookie flags, implementing proper logout functionality that invalidates sessions server-side, and binding sessions to additional attributes like IP address or user agent fingerprint where appropriate.

Q: What is the Secure Development Lifecycle (SDL) and what are its key phases?
A: The Secure Development Lifecycle is a software development process that integrates security practices at every stage rather than treating security as an afterthought. Key phases include security training for development teams, requirements gathering that includes security requirements and abuse cases, secure design incorporating threat modeling and attack surface analysis, secure implementation following coding standards and using approved libraries, security testing including static analysis, dynamic testing, and code review, and secure deployment with hardened configurations and incident response planning. Post-release activities include vulnerability management, patch deployment, and continuous monitoring. The SDL reduces vulnerabilities by addressing security early when fixes are less expensive, creates documentation for compliance requirements, and establishes consistent security practices across projects. Popular frameworks include Microsoft SDL, OWASP SAMM, and BSIMM.

Q: What is threat modeling and how is it performed?
A: Threat modeling is a structured approach to identifying, quantifying, and addressing security threats to an application or system during the design phase. The process typically involves defining security objectives and the scope of analysis, creating a visual representation of the system architecture including data flows and trust boundaries, identifying potential threats using frameworks like STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), rating threats based on likelihood and impact using methods like DREAD, and determining appropriate countermeasures or accepting residual risk. Threat modeling should be iterative, updated when the system design changes significantly, and involve stakeholders from development, security, and operations. By identifying threats early in development, teams can implement security controls proactively rather than reactively patching vulnerabilities after deployment.

Q: What are the best practices for API security?
A: API security requires multiple layers of protection since APIs expose application logic and sensitive data directly. Authentication should use robust mechanisms like OAuth 2.0 with JWT tokens rather than API keys alone, and all endpoints should verify user identity. Authorization must enforce access controls at each endpoint, validating that authenticated users have permission for requested operations. Input validation should be strict, with schemas defining expected request formats. Rate limiting and throttling prevent abuse and denial-of-service attacks. Transport security requires TLS for all communications, with proper certificate validation. APIs should return minimal error information to avoid leaking implementation details. Logging should capture security-relevant events without exposing sensitive data. Versioning helps manage security updates, and deprecated versions should be sunset promptly. Regular security testing, including automated scanning and manual review, should verify that security controls function correctly across all API endpoints.

Q: What is the OWASP Top 10 and why is it important for application security?
A: The OWASP Top 10 is a regularly updated document published by the Open Web Application Security Project that identifies the ten most critical security risks to web applications. It serves as an industry-standard awareness document that helps organizations prioritize their security efforts based on the most prevalent and impactful vulnerabilities. The list includes risks like injection attacks, broken authentication, sensitive data exposure, and security misconfigurations. Development teams use it as a baseline for security requirements, code review checklists, and penetration testing scope. Understanding the OWASP Top 10 is essential because it represents consensus from security experts worldwide about what attackers most commonly exploit. Organizations that address these top risks significantly reduce their attack surface and demonstrate due diligence in protecting user data.

Q: How does Cross-Site Scripting (XSS) work and what are the different types?
A: Cross-Site Scripting (XSS) is a vulnerability that allows attackers to inject malicious scripts into web pages viewed by other users, enabling them to steal session cookies, redirect users, or deface websites. There are three main types: Stored XSS occurs when malicious script is permanently stored on the target server (like in a database) and executed whenever users view the affected content. Reflected XSS happens when the malicious script is reflected off a web server through error messages, search results, or other responses that include user input. DOM-based XSS occurs entirely in the browser when client-side JavaScript processes untrusted data and writes it to the DOM without proper sanitization. Prevention requires output encoding appropriate to the context (HTML, JavaScript, URL, CSS), implementing Content Security Policy headers, and using frameworks that automatically escape output.

Q: What is SQL injection and how can developers prevent it?
A: SQL injection is an attack technique where malicious SQL statements are inserted into application queries through user input, potentially allowing attackers to read, modify, or delete database contents, bypass authentication, or execute administrative operations. The vulnerability occurs when applications construct SQL queries by concatenating user input directly into query strings without proper validation or parameterization. Prevention requires using parameterized queries or prepared statements, which separate SQL logic from data and prevent user input from being interpreted as SQL commands. Additionally, developers should implement least privilege database accounts, use stored procedures where appropriate, validate and sanitize all input, and employ web application firewalls as a defense-in-depth measure. Modern ORMs typically use parameterized queries by default, but developers must be vigilant when writing raw SQL or using dynamic query features.

Q: What is CSRF (Cross-Site Request Forgery) and how do anti-CSRF tokens work?
A: Cross-Site Request Forgery (CSRF) is an attack that tricks authenticated users into unknowingly submitting malicious requests to a web application, exploiting the trust that a site has in the user's browser. When a user is logged into a banking site, for example, an attacker could craft a hidden form on a malicious page that submits a money transfer request using the user's existing session cookies. Anti-CSRF tokens prevent these attacks by requiring each state-changing request to include a unique, unpredictable token that the server validates. The server generates a cryptographically random token for each session or request and embeds it in forms as a hidden field. Since attackers cannot predict or access this token from their malicious site due to same-origin policy, they cannot forge valid requests. Modern frameworks like Django, Rails, and Spring Security include built-in CSRF protection that should be enabled for all non-idempotent operations.

Q: What are the best practices for secure password storage?
A: Secure password storage requires using modern adaptive hashing algorithms specifically designed for passwords, such as bcrypt, scrypt, or Argon2, which are intentionally slow and computationally expensive to resist brute-force attacks. Never store passwords in plain text or use fast cryptographic hashes like MD5 or SHA-256 alone, as these can be rapidly attacked with modern hardware. Each password should be hashed with a unique, randomly generated salt of at least 16 bytes to prevent rainbow table attacks and ensure identical passwords produce different hashes. The work factor or cost parameter should be tuned to make hashing take at least 250 milliseconds on your hardware, balancing security against legitimate user experience. Implement account lockout policies, rate limiting, and monitoring to detect brute-force attempts. Consider using established libraries like libsodium or your framework's built-in password hashing rather than implementing your own cryptographic code.

Q: What is the principle of least privilege and how should it be applied in application security?
A: The principle of least privilege states that every user, process, or system component should operate with only the minimum permissions necessary to perform its intended function, reducing the potential damage from accidents, errors, or security breaches. In application security, this means database connections should use accounts that can only access required tables and operations, not administrative accounts. Service accounts should run with restricted permissions rather than root or administrator privileges. API keys and tokens should be scoped to specific resources and actions needed by each component. Application users should be assigned roles with granular permissions rather than broad access levels. File system permissions should restrict write access to only directories where the application legitimately needs to store data. This approach limits the blast radius when any single component is compromised and makes it harder for attackers to escalate privileges or move laterally through systems.

Q: How does encryption at rest differ from encryption in transit, and when should each be used?
A: Encryption at rest protects data stored on disk, databases, backups, and other persistent storage by encrypting it when written and decrypting when read, defending against physical theft, unauthorized storage access, and data breaches where attackers obtain database dumps. Encryption in transit protects data as it moves between systems over networks using protocols like TLS/SSL, preventing eavesdropping, man-in-the-middle attacks, and data interception. Both should be used together as they address different threat vectors. Encryption in transit should be enforced for all network communications using TLS 1.2 or higher with strong cipher suites. Encryption at rest should protect sensitive data including PII, credentials, financial information, and health records using AES-256 or similar algorithms. Key management is critical for both; use hardware security modules (HSMs) or cloud key management services for production systems, rotate keys regularly, and ensure encryption keys are stored separately from the encrypted data.

Q: What is input validation and what are the key strategies for implementing it effectively?
A: Input validation is the process of ensuring that all data entering an application conforms to expected formats, types, lengths, and ranges before processing, serving as a critical first line of defense against injection attacks, buffer overflows, and data corruption. Whitelisting (allow-listing) is preferred over blacklisting because it defines exactly what is acceptable rather than trying to anticipate all malicious patterns. Server-side validation is mandatory since client-side validation can be easily bypassed; client-side checks should only be used for user experience improvements. Validation should occur as early as possible in the data flow and should be applied consistently across all entry points including forms, APIs, file uploads, and URL parameters. Use strong typing and schema validation for structured data like JSON or XML. Implement length limits appropriate to each field to prevent denial-of-service attacks and buffer overflows. Remember that validation prevents malformed data from entering the system, but output encoding is still necessary to prevent injection when data is used in different contexts.

Q: What are the essential elements of secure session management?
A: Secure session management protects user authentication state from hijacking, fixation, and replay attacks through multiple defensive measures. Session identifiers must be cryptographically random, sufficiently long (at least 128 bits), and generated using secure random number generators to prevent prediction or brute-force guessing. Sessions should be regenerated after login to prevent session fixation attacks where attackers set a known session ID before authentication. Implement absolute timeouts (maximum session lifetime) and idle timeouts (inactivity limits) appropriate to your application's sensitivity level. Store session data server-side and only transmit the session identifier to the client. Cookie security flags are essential: set HttpOnly to prevent JavaScript access, Secure to ensure HTTPS-only transmission, and SameSite to mitigate CSRF. Properly invalidate sessions on logout by destroying server-side session data rather than just clearing the cookie. Monitor for concurrent sessions and implement mechanisms to detect and respond to session anomalies.

Q: What is secrets management and what are best practices for handling sensitive credentials?
A: Secrets management encompasses the secure storage, distribution, rotation, and auditing of sensitive credentials like API keys, database passwords, encryption keys, and certificates that applications need to function. Never hardcode secrets in source code, configuration files committed to version control, or container images, as these can be exposed through repository leaks, decompilation, or image inspection. Use dedicated secrets management solutions like HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or Kubernetes Secrets with encryption at rest. Implement secret rotation policies to limit the window of exposure if credentials are compromised, and design applications to handle credential changes without downtime. Apply the principle of least privilege by issuing unique credentials per application or service with minimal required permissions. Audit secret access to detect unauthorized usage patterns. Environment variables are acceptable for containerized deployments but should be injected from secure stores rather than stored in orchestration configurations.

Q: How does vulnerability scanning fit into a secure development lifecycle?
A: Vulnerability scanning is an automated process that identifies known security weaknesses in applications, dependencies, infrastructure, and configurations, forming a critical component of continuous security assurance. Static Application Security Testing (SAST) analyzes source code without execution to find vulnerabilities like SQL injection, XSS, and insecure cryptographic usage early in development. Dynamic Application Security Testing (DAST) tests running applications by simulating attacks to discover runtime vulnerabilities that static analysis might miss. Software Composition Analysis (SCA) identifies vulnerabilities in third-party libraries and dependencies, which often constitute 80% or more of modern applications. Container and infrastructure scanning checks for misconfigurations and vulnerabilities in deployment environments. These scans should be integrated into CI/CD pipelines to catch issues before deployment, with critical findings blocking releases. Regular scheduled scans of production systems detect newly disclosed vulnerabilities in existing deployments. Findings must be triaged, prioritized based on exploitability and impact, and remediated within defined SLAs.

Q: What security headers should web applications implement and why?
A: Security headers are HTTP response headers that instruct browsers to enable built-in security features, providing defense-in-depth against common web attacks. Content-Security-Policy (CSP) restricts which resources can be loaded and executed, dramatically reducing XSS impact by preventing inline scripts and unauthorized script sources. Strict-Transport-Security (HSTS) forces browsers to use HTTPS for all future requests to the domain, preventing protocol downgrade attacks and cookie hijacking. X-Content-Type-Options with value "nosniff" prevents browsers from MIME-sniffing responses, blocking attacks that trick browsers into executing malicious content as scripts. X-Frame-Options or the frame-ancestors CSP directive prevents clickjacking by controlling whether the page can be embedded in iframes. Referrer-Policy controls how much information is shared in the Referer header when navigating away, protecting sensitive URL parameters. Permissions-Policy restricts which browser features the page can use, limiting potential attack surface. Start with restrictive policies and relax only as needed, using report-only mode to test CSP before enforcement.

Q: What is secure code review and what should reviewers look for?
A: Secure code review is a systematic examination of source code to identify security vulnerabilities, logic flaws, and deviations from secure coding standards before they reach production. Reviewers should examine authentication and authorization logic for bypass vulnerabilities, ensuring all protected resources check permissions consistently. Input handling code must be scrutinized for proper validation, sanitization, and parameterization to prevent injection attacks. Look for sensitive data exposure through logging, error messages, comments, or improper storage. Cryptographic implementations should use established libraries with secure algorithms and proper key management rather than custom solutions. Review session management for secure token generation, proper timeout handling, and complete invalidation on logout. Check for race conditions and time-of-check-time-of-use vulnerabilities in concurrent code. Examine error handling to ensure exceptions don't leak sensitive information or create exploitable states. Use checklists based on OWASP guidelines and language-specific secure coding standards to ensure comprehensive coverage.

Q: How should applications handle authentication failures and implement account lockout?
A: Authentication failure handling must balance security against usability while providing attackers minimal information for reconnaissance. Error messages should be generic and identical whether the username or password is incorrect, preventing username enumeration attacks. Implement progressive delays or rate limiting that increases wait time between failed attempts, making brute-force attacks impractical without permanently locking out legitimate users. Account lockout should trigger after a configurable number of failures (typically 5-10) within a time window, with automatic unlock after a cooling-off period rather than requiring administrator intervention. Log all authentication failures with timestamps, source IPs, and usernames for security monitoring and incident response, but ensure logs don't contain passwords. Consider implementing CAPTCHA challenges after initial failures before full lockout. Notify users of successful logins from new devices or locations to detect account compromise. For high-security applications, implement risk-based authentication that considers factors like geographic location, device fingerprint, and behavior patterns to trigger additional verification steps.

Q: What is threat modeling and how should development teams approach it?
A: Threat modeling is a structured approach to identifying, prioritizing, and mitigating potential security threats to an application by systematically analyzing its architecture, data flows, and trust boundaries. Teams should begin by creating a data flow diagram that maps how information moves through the system, identifying entry points, storage locations, and external dependencies. Use frameworks like STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) to systematically brainstorm threats against each component. Prioritize identified threats using risk assessment methodologies that consider both likelihood of exploitation and potential business impact. For each significant threat, determine whether to mitigate through technical controls, accept the risk, transfer it through insurance or contracts, or avoid it by changing design. Document the threat model and its assumptions, updating it when architecture changes or new threats emerge. Involve diverse perspectives including developers, architects, security specialists, and operations staff to capture threats from different angles. Threat modeling is most valuable when performed early in design but should continue throughout the development lifecycle.
