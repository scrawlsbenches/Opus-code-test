Q: What is the Singleton pattern and when should it be used in software design?
A: The Singleton pattern ensures that a class has only one instance and provides a global point of access to that instance. It is commonly used for resources that should be shared across an application, such as configuration managers, logging services, or database connection pools. The pattern typically implements a private constructor and a static method that returns the single instance, creating it on first access if necessary. While useful for managing shared state, Singletons should be used sparingly as they can introduce hidden dependencies and make unit testing more difficult.

Q: How does the Factory Method pattern differ from simply using a constructor to create objects?
A: The Factory Method pattern defines an interface for creating objects but lets subclasses decide which class to instantiate, deferring instantiation to derived classes. Unlike direct constructor calls, Factory Methods encapsulate the creation logic and can return different concrete types based on runtime conditions or configuration. This approach follows the Open-Closed Principle by allowing new product types to be added without modifying existing client code. Factory Methods are particularly valuable when the exact type of object needed cannot be determined until runtime or when creation involves complex initialization logic.

Q: What problem does the Abstract Factory pattern solve that the simple Factory pattern cannot?
A: The Abstract Factory pattern provides an interface for creating families of related or dependent objects without specifying their concrete classes. While a simple Factory creates individual objects, Abstract Factory ensures that products from the same family are used together, maintaining consistency across the system. For example, a UI toolkit might use Abstract Factory to create matching buttons, text fields, and scroll bars for either Windows or macOS. This pattern is essential when a system must be independent of how its products are created and when products from one family should not be mixed with products from another.

Q: When is the Builder pattern preferable to using a constructor with many parameters?
A: The Builder pattern separates the construction of a complex object from its representation, allowing the same construction process to create different representations. It excels when objects require numerous optional parameters, as it avoids the telescoping constructor anti-pattern where multiple overloaded constructors become unwieldy. Builders provide a fluent interface that makes code more readable and allows step-by-step construction with clear parameter names. The pattern also enforces immutability of the final product since all configuration happens during building, and the resulting object can be made immutable once constructed.

Q: How does the Prototype pattern enable object creation, and what are its advantages over traditional instantiation?
A: The Prototype pattern creates new objects by cloning an existing instance rather than calling a constructor, which is useful when object creation is expensive or complex. It allows dynamic addition of new object types at runtime by simply registering new prototype instances with a registry. This pattern is particularly valuable when classes to instantiate are specified at runtime or when avoiding the overhead of creating objects from scratch through class hierarchies. Implementations must carefully consider shallow versus deep copying to ensure cloned objects are properly independent of their prototypes.

Q: What is the Adapter pattern and how does it enable incompatible interfaces to work together?
A: The Adapter pattern converts the interface of a class into another interface that clients expect, allowing classes with incompatible interfaces to collaborate. It acts as a wrapper that translates calls from the target interface to the appropriate methods on the adaptee, effectively bridging the gap between two systems. Adapters are commonly used when integrating legacy code with new systems or when incorporating third-party libraries with different interface conventions. The pattern can be implemented through class adaptation using inheritance or object adaptation using composition, with composition generally being more flexible.

Q: How does the Decorator pattern add functionality to objects without altering their structure?
A: The Decorator pattern attaches additional responsibilities to an object dynamically by wrapping it in a decorator object that has the same interface. Unlike inheritance which adds behavior at compile time for all instances, decorators can add behavior to individual objects at runtime without affecting other instances of the same class. Decorators can be stacked, allowing multiple behaviors to be combined in flexible ways, such as adding encryption, compression, and buffering to an I/O stream. This pattern follows the Single Responsibility Principle by allowing functionality to be divided between classes with unique areas of concern.

Q: What role does the Facade pattern play in managing complex subsystems?
A: The Facade pattern provides a simplified, unified interface to a complex subsystem, making the subsystem easier to use and reducing dependencies between clients and the subsystem's components. It does not hide the subsystem's classes but rather provides a convenient high-level interface while still allowing direct access to lower-level functionality when needed. Facades are commonly used in layered architectures to define entry points to each subsystem level, reducing coupling and promoting loose connections between subsystems. This pattern improves readability and usability by encapsulating complex sequences of operations behind simple method calls.

Q: How does the Proxy pattern control access to objects, and what are its common use cases?
A: The Proxy pattern provides a surrogate or placeholder for another object to control access to it, with the proxy maintaining a reference to the real subject and forwarding requests appropriately. Virtual proxies defer the creation and initialization of expensive objects until they are actually needed, implementing lazy loading. Protection proxies control access to the original object based on access rights, while remote proxies represent objects located in different address spaces. Smart proxies perform additional actions when the object is accessed, such as reference counting, thread safety locks, or logging access history.

Q: What is the Observer pattern and how does it support loose coupling between components?
A: The Observer pattern defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically. The subject maintains a list of observers and notifies them of state changes without needing to know their concrete types, enabling loose coupling between the subject and its observers. This pattern is fundamental to event-driven programming and is widely used in GUI frameworks, reactive programming, and publish-subscribe systems. Observers can be added or removed at runtime, and the pattern supports broadcast communication where a single event triggers updates to multiple listeners.

Q: How does the Strategy pattern enable algorithms to be selected at runtime?
A: The Strategy pattern defines a family of algorithms, encapsulates each one in a separate class, and makes them interchangeable within that family. Clients can select algorithms at runtime without altering the code that uses them, as all strategies implement a common interface that the context invokes. This pattern eliminates conditional statements for selecting behavior by delegating to strategy objects instead of using switch statements or if-else chains. Strategies promote code reuse and make it easy to add new algorithms without modifying existing context classes, following the Open-Closed Principle.

Q: What problem does the Command pattern solve in application design?
A: The Command pattern encapsulates a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations. Each command object contains all the information needed to execute an action, including the method to call, the method owner, and any required parameters. This decoupling between the object invoking the operation and the object knowing how to perform it enables features like macro recording, transaction systems, and progress tracking. Commands can be stored, serialized, and transmitted, making them ideal for implementing undo-redo functionality or distributed computing scenarios.

Q: How does the Template Method pattern define the skeleton of an algorithm while allowing customization?
A: The Template Method pattern defines the skeleton of an algorithm in a base class method, deferring some steps to subclasses without changing the algorithm's overall structure. The template method calls abstract or hook methods that subclasses override to provide specific behavior while keeping the invariant parts of the algorithm in the base class. This pattern implements the Hollywood Principle where the base class calls subclass methods rather than the reverse, reducing code duplication by factoring common behavior into a single location. Template methods are particularly useful for frameworks where the overall workflow is fixed but specific steps need customization.

Q: When should the State pattern be used to manage object behavior?
A: The State pattern allows an object to alter its behavior when its internal state changes, appearing to change its class by delegating behavior to state objects. It is particularly valuable when an object's behavior depends on its state and must change at runtime, eliminating large conditional statements that check object state before every operation. Each state is represented by its own class that implements a common interface, making it easy to add new states without modifying existing state classes or the context. This pattern localizes state-specific behavior and partitions behavior for different states, making state transitions explicit and manageable.

Q: How does the Chain of Responsibility pattern decouple senders from receivers of requests?
A: The Chain of Responsibility pattern avoids coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Handlers are linked in a chain, and each handler decides either to process the request or to pass it to the next handler in the chain. This pattern is useful when multiple objects may handle a request and the handler is not known a priori, or when the set of handlers should be specified dynamically. Common applications include event bubbling in GUI systems, middleware pipelines in web frameworks, and validation chains where each validator checks one aspect of the input before passing it along.
