Q: What is lexical analysis and what role does a lexer play in compilation?
A: Lexical analysis is the first phase of compilation where the source code is converted into a stream of tokens. The lexer (or scanner) reads characters from the input, groups them into lexemes, and categorizes each as a token type such as keywords, identifiers, operators, or literals. This process strips away whitespace and comments while providing a clean token stream that the parser can process. Modern lexers are often generated from regular expression specifications using tools like Flex or hand-written using finite automata implementations.

Q: How does recursive descent parsing work and what are its limitations?
A: Recursive descent parsing is a top-down parsing technique where each non-terminal in the grammar corresponds to a function that recognizes that construct. The parser starts from the start symbol and recursively expands productions by calling the appropriate functions based on lookahead tokens. Its primary limitation is that it cannot handle left-recursive grammars directly, as they cause infinite recursion. Additionally, basic recursive descent parsers may require backtracking for ambiguous grammars, though LL(k) parsers with k tokens of lookahead can make deterministic decisions for appropriately structured grammars.

Q: What is an Abstract Syntax Tree and how does it differ from a parse tree?
A: An Abstract Syntax Tree (AST) is a hierarchical representation of the syntactic structure of source code that captures the essential meaning while omitting syntactic details. Unlike a parse tree (concrete syntax tree), which faithfully represents every grammar production including punctuation and grouping symbols, an AST abstracts away these details to focus on the semantic structure. For example, an AST for "3 + 4 * 5" would directly represent the operator precedence without including parentheses nodes. ASTs serve as the primary intermediate representation for semantic analysis, optimization, and code generation phases.

Q: What is type inference and how do algorithms like Hindley-Milner work?
A: Type inference is the automatic deduction of types for expressions without requiring explicit type annotations from the programmer. The Hindley-Milner algorithm, used in languages like ML and Haskell, works by generating type constraints from the program structure and then solving them through unification. The algorithm assigns fresh type variables to unknown types, collects equality constraints based on how values are used, and iteratively unifies these constraints to find the most general type. This approach guarantees principal types, meaning the inferred type is the most general type that satisfies all constraints, enabling polymorphic functions to be typed correctly.

Q: What are the main phases of code generation in a compiler?
A: Code generation transforms the intermediate representation (typically an AST or IR) into target machine code through several phases. First, instruction selection maps IR operations to target machine instructions, often using pattern matching or tree-covering algorithms. Next, register allocation assigns variables and temporaries to physical registers using techniques like graph coloring or linear scan. Instruction scheduling reorders operations to maximize pipeline utilization and minimize stalls. Finally, the code emitter produces the actual binary encoding or assembly text, handling details like addressing modes and instruction formats.

Q: What is Static Single Assignment (SSA) form and why is it useful for optimization?
A: Static Single Assignment form is an intermediate representation where each variable is assigned exactly once and every use of a variable refers to exactly one definition. Variables that would be assigned multiple times in the original code are split into distinct versions (e.g., x1, x2, x3), with special phi functions at control flow merge points to select the appropriate version. SSA simplifies many optimizations because def-use chains are explicit and trivial to compute. Constant propagation, dead code elimination, and common subexpression elimination become more effective because the single-assignment property makes data flow analysis straightforward and precise.

Q: How does dead code elimination work as an optimization pass?
A: Dead code elimination removes instructions that compute values never used by the program, reducing code size and execution time. The algorithm typically works backward from program outputs, marking instructions as live if they contribute to observable effects like return values, I/O operations, or memory stores. Any unmarked instructions after this analysis are considered dead and can be safely removed. In SSA form, this becomes particularly elegant because each definition has a clear list of uses, making it trivial to identify definitions with no uses. Iterative application may be needed since eliminating dead code can make previously live code become dead.

Q: What is the difference between mark-and-sweep and reference counting garbage collection?
A: Mark-and-sweep garbage collection periodically traces all reachable objects starting from root references (stack, globals), marking them as live, then sweeps through the heap freeing unmarked objects. This approach handles cyclic references naturally but requires stopping the program (stop-the-world pauses) and has unpredictable latency. Reference counting maintains a count of references to each object, deallocating when the count reaches zero, providing immediate reclamation and predictable performance. However, reference counting cannot collect cyclic garbage without additional cycle detection algorithms and incurs overhead on every pointer assignment. Modern collectors often combine both techniques with generational and concurrent strategies.

Q: How does Just-In-Time (JIT) compilation improve performance over interpretation?
A: JIT compilation converts bytecode or intermediate representation to native machine code at runtime, combining the portability of interpretation with the performance of ahead-of-time compilation. When a method or basic block executes frequently (becomes "hot"), the JIT compiles it to optimized native code, eliminating interpretation overhead for subsequent executions. JIT compilers can perform optimizations impossible at compile time, such as inlining virtual method calls based on observed receiver types or specializing code for actual runtime values. The tradeoff is increased memory usage for compiled code and compilation latency, which techniques like tiered compilation address by using faster, less optimal compilation initially.

Q: What are the fundamental tradeoffs between interpreters and compilers?
A: Interpreters execute source code directly by traversing the AST or dispatching bytecode instructions, offering fast startup time, excellent debugging support, and platform independence at the cost of slower execution. Compilers transform source code into machine code before execution, enabling extensive optimizations and producing efficient executables but requiring a separate compilation step and platform-specific output. Interpreters can implement dynamic language features more naturally since they maintain runtime representations of program structures. Modern language implementations often blur this distinction through bytecode compilation, JIT compilation, and hybrid approaches that interpret cold code while compiling hot paths.

Q: What is bytecode and why do many languages use bytecode virtual machines?
A: Bytecode is a compact, platform-independent intermediate representation consisting of instructions for a virtual machine rather than a physical CPU. Languages like Java, Python, and C# compile source code to bytecode, which is then executed by a virtual machine (JVM, CPython, CLR). This approach provides portability across different hardware architectures while being more efficient than interpreting source code directly, as bytecode is denser and designed for efficient dispatch. Bytecode VMs can also implement security features like bytecode verification and sandboxing, and serve as a stable compilation target that decouples language front-ends from platform-specific back-ends.

Q: How do peephole optimizations improve generated code?
A: Peephole optimization examines small sequences of adjacent instructions (the "peephole") and replaces them with more efficient equivalents. Common patterns include replacing multiplication by powers of two with shifts, eliminating redundant loads after stores to the same location, and combining multiple operations into single complex instructions. The optimization works by pattern matching against a database of known improvements, making it simple to implement and extend. While each individual improvement is small, the cumulative effect across an entire program can be significant, and peephole optimization catches inefficiencies introduced by earlier, more general code generation phases.

Q: What is escape analysis and how does it enable optimization?
A: Escape analysis determines whether an object allocated within a method can be accessed outside that method's scope, either by being returned, stored in a global, or passed to another method that captures it. Objects that don't escape can be allocated on the stack instead of the heap, eliminating garbage collection overhead and improving cache locality. Non-escaping objects may also have their fields scalar replaced, promoting object fields to local variables and enabling further optimizations like register allocation. This analysis is particularly valuable in object-oriented languages where short-lived temporary objects are common but heap allocation would normally be required.

Q: How does loop-invariant code motion optimize loops?
A: Loop-invariant code motion (LICM) identifies computations within a loop whose results don't change across iterations and moves them outside the loop. An expression is loop-invariant if all its operands are either constants, defined outside the loop, or themselves loop-invariant. By hoisting these computations to the loop preheader, the optimization ensures they execute once rather than on every iteration. LICM must be careful about expressions that might fault (like division) or have side effects, only moving them when execution is guaranteed. This optimization often combines with strength reduction, which replaces expensive operations like multiplication with cheaper additions that accumulate across iterations.

Q: What role does control flow analysis play in compiler optimization?
A: Control flow analysis constructs a control flow graph (CFG) representing all possible execution paths through a program, with basic blocks as nodes and branches as edges. This graph enables dataflow analyses that propagate information along execution paths, such as reaching definitions, live variables, and available expressions. Dominance analysis identifies which blocks must execute before others, essential for placing SSA phi functions and proving loop properties. The CFG also reveals natural loops, enabling loop optimizations, and identifies unreachable code for elimination. Control flow analysis forms the foundation for nearly all intraprocedural optimizations and is extended with call graphs for interprocedural analysis.
