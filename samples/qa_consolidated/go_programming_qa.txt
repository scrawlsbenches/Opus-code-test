Q: What are goroutines and how do they differ from traditional threads?
A: Goroutines are lightweight, user-space threads managed by the Go runtime rather than the operating system. Unlike OS threads which typically require megabytes of stack space, goroutines start with just a few kilobytes and can grow dynamically. The Go scheduler multiplexes thousands of goroutines onto a smaller number of OS threads using an M:N scheduling model, making concurrent programming highly efficient. This design allows Go programs to spawn millions of goroutines with minimal overhead compared to traditional threading models.

Q: How do channels work in Go and what is their primary purpose?
A: Channels are typed conduits that enable safe communication between goroutines, following Go's philosophy of "share memory by communicating" rather than "communicate by sharing memory." They can be unbuffered (synchronous) or buffered (asynchronous), with unbuffered channels blocking until both sender and receiver are ready. Channels provide built-in synchronization, eliminating many common concurrency bugs like race conditions. You create a channel with make(chan Type) and use the <- operator for sending and receiving values.

Q: What is the select statement and when should you use it?
A: The select statement allows a goroutine to wait on multiple channel operations simultaneously, proceeding with whichever case becomes ready first. It is essential for implementing timeouts, cancellation, and multiplexing multiple channels in concurrent programs. If multiple cases are ready, select chooses one at random to prevent starvation. A default case makes select non-blocking, which is useful for polling or implementing try-send/try-receive patterns. This construct is fundamental for building robust concurrent systems in Go.

Q: How do interfaces work in Go and what makes them unique?
A: Go interfaces are implemented implicitly rather than explicitly, meaning a type satisfies an interface simply by implementing all its methods without declaring intent. This structural typing enables loose coupling and makes it easy to define interfaces that existing types already satisfy. The empty interface (interface{} or 'any' in Go 1.18+) can hold values of any type, providing a form of generics before Go added type parameters. Interface values consist of a type and value pair, and nil interface values require careful handling since an interface containing a nil concrete value is itself not nil.

Q: What are Go's error handling conventions and best practices?
A: Go treats errors as values rather than exceptions, with functions typically returning an error as their last return value. The idiomatic pattern is to check errors immediately after each call using if err != nil, handling or propagating them explicitly. Since Go 1.13, errors can be wrapped using fmt.Errorf with %w to preserve the error chain, and errors.Is/errors.As enable checking wrapped errors. Custom error types should implement the error interface and can carry additional context. This explicit approach makes error paths visible and encourages developers to handle failures thoughtfully.

Q: How do defer, panic, and recover work together in Go?
A: Defer schedules a function call to execute when the surrounding function returns, commonly used for cleanup tasks like closing files or releasing locks. Multiple defers execute in LIFO order (last deferred runs first), and deferred functions can access and modify named return values. Panic halts normal execution, runs deferred functions, and propagates up the call stack until caught or the program terminates. Recover, when called inside a deferred function, stops the panic propagation and returns the panic value, enabling graceful error recovery. This mechanism should be used sparingly, primarily for truly exceptional situations rather than routine error handling.

Q: What is the context package used for in Go?
A: The context package provides a standard way to carry deadlines, cancellation signals, and request-scoped values across API boundaries and between goroutines. It is essential for managing the lifecycle of operations in servers, preventing resource leaks when requests are cancelled or time out. Context values form an immutable tree, with child contexts derived from parents using WithCancel, WithDeadline, WithTimeout, or WithValue. Functions that may block or perform I/O should accept a context.Context as their first parameter and respect cancellation. The context should never be stored in structs but passed explicitly through function calls.

Q: What is the difference between slices and arrays in Go?
A: Arrays in Go have a fixed length that is part of their type (e.g., [5]int is different from [10]int), and assigning an array copies all elements. Slices are dynamic, flexible views into underlying arrays, consisting of a pointer, length, and capacity. Slices are reference types, so passing a slice to a function allows modification of the underlying array without copying. The make function creates slices with specified length and capacity, while append grows slices automatically, potentially allocating a new backing array. Most Go code uses slices rather than arrays due to their flexibility and efficiency.

Q: How does struct embedding work and what is its purpose?
A: Struct embedding allows one struct type to include another without an explicit field name, promoting the embedded type's fields and methods to the outer type. This provides composition over inheritance, enabling code reuse without the complexity of class hierarchies. The embedded type's methods are automatically promoted, though the outer type can override them by defining methods with the same name. Embedding is commonly used to share behavior across types, implement interfaces through delegation, and extend types from external packages. Unlike inheritance, embedding does not establish an is-a relationship; the embedded value is simply a field accessed by its type name.

Q: How do you write tests in Go using the testing package?
A: Go's testing package provides built-in support for unit tests, benchmarks, and examples with the go test command. Test functions must be named TestXxx, accept *testing.T, and reside in files ending with _test.go in the same package. The testing.T type provides methods like Error, Fatal, Log, and Run for subtests, enabling table-driven test patterns. Benchmarks use BenchmarkXxx functions with *testing.B, automatically running the code multiple times to measure performance. The -cover flag generates coverage reports, and the -race flag enables the race detector for finding concurrency bugs.

Q: What are Go modules and how do they manage dependencies?
A: Go modules, introduced in Go 1.11 and default since Go 1.16, provide dependency management with versioned modules identified by their module path. The go.mod file declares the module path, Go version, and direct dependencies with their versions using semantic versioning. The go.sum file contains cryptographic hashes ensuring reproducible builds by verifying dependency integrity. Commands like go get, go mod tidy, and go mod vendor manage dependencies, with the module cache storing downloaded packages. Modules support major version suffixes (v2, v3) in import paths for backward-incompatible changes, enabling multiple major versions to coexist.

Q: What is the worker pool pattern and how is it implemented in Go?
A: The worker pool pattern limits concurrency by distributing tasks across a fixed number of goroutines that process work from a shared channel. You create a buffered jobs channel for incoming work and a results channel for outputs, then spawn N worker goroutines that range over the jobs channel. This pattern prevents resource exhaustion, controls memory usage, and provides natural backpressure when the jobs channel fills up. Workers automatically terminate when the jobs channel is closed, and you can use a WaitGroup to synchronize completion. This pattern is ideal for rate limiting, batch processing, and managing connections to external services.

Q: How does the fan-out/fan-in concurrency pattern work?
A: Fan-out involves starting multiple goroutines to handle input from a single channel, distributing work across concurrent processors for parallelism. Fan-in combines results from multiple channels into a single channel, aggregating outputs from concurrent operations. This pattern is implemented by spawning multiple worker goroutines (fan-out) that send results to a shared output channel, with a coordinating goroutine that closes the output channel when all workers complete. A sync.WaitGroup typically tracks worker completion, ensuring the output channel closes only after all results are sent. This pattern maximizes CPU utilization for computationally intensive tasks and improves throughput for I/O-bound operations.

Q: What is a mutex and when should you use it versus channels in Go?
A: A sync.Mutex provides mutual exclusion, ensuring only one goroutine accesses a critical section at a time using Lock() and Unlock() methods. Use mutexes when protecting shared state that requires multiple operations to remain consistent, such as updating a map or incrementing a counter. Channels are preferred for communicating data between goroutines and coordinating their execution flow. The Go proverb suggests: use channels for passing ownership of data, and use mutexes for protecting shared state accessed by reference. sync.RWMutex provides read-write locking when reads greatly outnumber writes, allowing multiple concurrent readers.

Q: How do you implement graceful shutdown in a Go server?
A: Graceful shutdown involves stopping a server without dropping active connections, typically using signal handling and context cancellation. Register handlers for SIGINT and SIGTERM using signal.Notify to catch shutdown requests, then call server.Shutdown(ctx) with a timeout context. The Shutdown method stops accepting new connections while waiting for existing requests to complete within the timeout. Background goroutines should accept a context and check ctx.Done() to clean up when shutdown is signaled. This pattern ensures data integrity, allows in-flight requests to finish, and properly releases resources like database connections before the program exits.
