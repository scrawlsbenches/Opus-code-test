Software Architecture Patterns - Q&A

Q: What are the key differences between microservices and monolithic architecture, and when should you choose one over the other?
A: Microservices architecture decomposes an application into small, independently deployable services that communicate via APIs, while monolithic architecture packages all functionality into a single deployable unit. Microservices offer better scalability, technology flexibility, and fault isolation, but introduce complexity in distributed communication, data consistency, and operational overhead. Choose monoliths for smaller teams, simpler domains, or when starting a new project; migrate to microservices when you need independent scaling, have multiple teams working on distinct bounded contexts, or require technology diversity across components.

Q: What is event-driven architecture and what problems does it solve in distributed systems?
A: Event-driven architecture is a design paradigm where system components communicate through the production, detection, and consumption of events rather than direct synchronous calls. This pattern solves problems of tight coupling between services, enables better scalability through asynchronous processing, and improves system resilience by allowing components to operate independently. It excels in scenarios requiring real-time data processing, complex event correlation, and systems where components need to react to state changes without polling or direct dependencies on other services.

Q: How does CQRS (Command Query Responsibility Segregation) work, and what benefits does it provide?
A: CQRS separates read and write operations into distinct models, using commands for writes that change state and queries for reads that return data without side effects. This separation allows each model to be optimized independently: write models can focus on business logic and validation, while read models can be denormalized and optimized for specific query patterns. The pattern is particularly valuable in systems with asymmetric read/write loads, complex domains where read and write representations differ significantly, or when you need to scale reads and writes independently.

Q: What is hexagonal architecture (ports and adapters) and how does it promote maintainability?
A: Hexagonal architecture, also known as ports and adapters, organizes code around a central domain core that is isolated from external concerns through well-defined ports (interfaces) and adapters (implementations). The domain core contains business logic and is agnostic to databases, UI frameworks, or external services, which connect through adapters that implement the port interfaces. This structure promotes maintainability by making the domain testable in isolation, allowing infrastructure components to be swapped without affecting business logic, and creating clear boundaries that prevent technical concerns from leaking into domain code.

Q: What are the core concepts of Domain-Driven Design (DDD) and how do they help manage complexity?
A: Domain-Driven Design centers on building software that deeply reflects the business domain through concepts like bounded contexts, aggregates, entities, value objects, and ubiquitous language shared between developers and domain experts. Bounded contexts define clear boundaries where a particular domain model applies, preventing model pollution across different subdomains. DDD manages complexity by focusing development effort on the core domain, establishing explicit boundaries between different parts of the system, and ensuring the codebase vocabulary matches the business vocabulary, reducing translation errors and miscommunication.

Q: What is a service mesh and what capabilities does it provide for microservices deployments?
A: A service mesh is a dedicated infrastructure layer that handles service-to-service communication, providing capabilities like load balancing, service discovery, encryption, authentication, and observability without requiring changes to application code. Implemented through sidecar proxies deployed alongside each service instance, service meshes centralize cross-cutting concerns that would otherwise need to be implemented in every service. Popular implementations like Istio and Linkerd provide traffic management, security policies, and comprehensive telemetry, enabling operators to control and observe microservices communication at scale.

Q: How does the API Gateway pattern work and what problems does it address in distributed architectures?
A: An API Gateway serves as a single entry point for client requests, routing them to appropriate backend services while handling cross-cutting concerns like authentication, rate limiting, request transformation, and response aggregation. It addresses the problem of clients needing to know about and communicate with multiple microservices directly, which creates tight coupling and exposes internal architecture. The gateway can also aggregate responses from multiple services into a single response, implement different API versions, and provide tailored APIs for different client types such as mobile applications versus web browsers.

Q: What is the Saga pattern and how does it manage distributed transactions across microservices?
A: The Saga pattern manages distributed transactions by breaking them into a sequence of local transactions, where each service completes its work and publishes an event that triggers the next step, with compensating transactions defined to undo changes if a step fails. Unlike traditional ACID transactions that lock resources across services, sagas maintain data consistency through eventual consistency and explicit compensation logic. There are two main implementations: choreography, where services react to events autonomously, and orchestration, where a central coordinator directs the saga flow, with the choice depending on complexity and coupling requirements.

Q: What is the sidecar pattern and how does it extend service functionality without code changes?
A: The sidecar pattern deploys a helper container alongside the main application container, sharing the same lifecycle and network namespace to provide supplementary functionality like logging, monitoring, configuration management, or security features. This pattern enables separation of concerns by extracting infrastructure capabilities into a dedicated component that can be developed, deployed, and updated independently of the application code. Sidecars are fundamental to service mesh implementations and are particularly valuable for polyglot environments where consistent infrastructure behavior is needed across services written in different languages.

Q: What is the Strangler Fig pattern and how does it enable safe migration from legacy systems?
A: The Strangler Fig pattern, named after vines that gradually envelop and replace host trees, enables incremental migration from legacy systems by routing specific functionality to new implementations while the legacy system continues to handle remaining features. A facade or proxy intercepts requests and directs them to either the legacy system or new services based on the migration progress, allowing teams to replace components one at a time rather than attempting risky big-bang rewrites. This approach reduces migration risk by maintaining continuous operation, enabling rollback of individual components, and allowing teams to learn and adjust their approach as the migration progresses.

Q: How do you decide whether to implement event sourcing alongside CQRS, and what are the trade-offs?
A: Event sourcing stores state as a sequence of events rather than current state snapshots, naturally complementing CQRS by providing an immutable audit log and enabling temporal queries about past states. The combination excels in domains requiring complete audit trails, complex event replay for debugging, or the ability to reconstruct state at any point in time. However, event sourcing adds significant complexity including eventual consistency challenges, event schema evolution concerns, and the need for snapshots to prevent unbounded event replay, making it appropriate only when its specific benefits outweigh the substantial implementation and operational overhead.

Q: What role do bounded contexts play in preventing domain model corruption in large systems?
A: Bounded contexts establish explicit boundaries within which a particular domain model maintains its integrity and meaning, preventing the creation of a single complex model that tries to satisfy all system requirements. Within each bounded context, terms have precise definitions that may differ from the same terms in other contexts; for example, a Customer in the sales context may have different attributes and behaviors than Customer in the shipping context. Context mapping techniques like anti-corruption layers, shared kernels, and published languages define how bounded contexts interact while protecting each domain model from external influences.

Q: How does the API composition pattern differ from API Gateway, and when should you use each?
A: API composition is a specific data aggregation pattern where a service queries multiple microservices and combines their responses to fulfill a client request, while API Gateway is a broader architectural pattern providing routing, security, and protocol translation at the system edge. Use API Gateway when you need centralized cross-cutting concerns, client-specific APIs, or protocol mediation between clients and services. Use API composition when clients need data that spans multiple services and you want to avoid coupling clients to multiple service APIs, though be cautious of the complexity introduced by distributed queries and potential performance bottlenecks.

Q: What are the key considerations when implementing the saga pattern with choreography versus orchestration?
A: Choreography-based sagas use events to trigger subsequent steps, resulting in loosely coupled services that react autonomously but can become difficult to understand and debug as the number of participating services grows. Orchestration-based sagas use a central coordinator that explicitly controls the flow, making the overall process easier to understand and modify but creating a potential single point of failure and tighter coupling to the orchestrator. Choose choreography for simpler sagas with few participants and when you want maximum service autonomy; choose orchestration for complex multi-step workflows where explicit flow control, error handling, and visibility are priorities.

Q: How do hexagonal architecture and domain-driven design complement each other in building maintainable systems?
A: Hexagonal architecture provides the structural foundation that keeps domain logic isolated from infrastructure concerns, while DDD provides the modeling techniques to build rich, expressive domain cores that accurately represent business concepts. The ports in hexagonal architecture naturally align with DDD's repository and service interfaces, and the adapters implement the technical integration that DDD explicitly pushes to the periphery. Together, they create systems where domain experts can understand and validate the core business logic without wading through technical details, while developers can modify infrastructure components without risking domain model corruption.
