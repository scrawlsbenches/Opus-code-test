Operating Systems Concepts - Q&A

Q: What is the fundamental difference between a process and a thread?
A: A process is an independent execution unit with its own memory space, file descriptors, and system resources, while a thread is a lightweight execution unit that exists within a process and shares memory and resources with other threads in the same process. Processes are isolated from each other for security and stability, meaning one crashing process cannot directly corrupt another. Threads enable concurrent execution within a single process with lower overhead since they share address space, but this shared access requires careful synchronization to prevent race conditions and data corruption.

Q: How does virtual memory work, and why is it essential for modern operating systems?
A: Virtual memory creates an abstraction layer between a program's logical address space and the physical RAM, allowing each process to operate as if it has exclusive access to a large, contiguous block of memory. The operating system, working with the Memory Management Unit (MMU), translates virtual addresses to physical addresses using page tables, and can swap infrequently used memory pages to disk when RAM becomes scarce. This mechanism enables running programs larger than physical memory, provides memory protection between processes, and simplifies memory allocation for applications. Virtual memory also facilitates features like copy-on-write, memory-mapped files, and shared libraries by mapping the same physical pages into multiple virtual address spaces.

Q: What is a page fault, and how does the operating system handle it?
A: A page fault occurs when a program attempts to access a memory address that is valid in its virtual address space but is not currently mapped to physical memory. When this happens, the CPU generates an exception that transfers control to the operating system's page fault handler. The handler determines whether the access is valid; if so, it allocates a physical frame, loads the required page from disk or initializes it, updates the page table, and resumes the interrupted instruction. If the access is invalid (such as accessing unmapped memory or violating permissions), the OS terminates the process with a segmentation fault.

Q: Explain the difference between preemptive and non-preemptive (cooperative) scheduling.
A: In preemptive scheduling, the operating system can forcibly interrupt a running process and switch the CPU to another process based on events like timer interrupts or higher-priority tasks becoming ready. In non-preemptive (cooperative) scheduling, a process retains the CPU until it voluntarily yields control, blocks for I/O, or terminates. Preemptive scheduling provides better responsiveness and fairness since no single process can monopolize the CPU, making it suitable for multi-user and real-time systems. Non-preemptive scheduling is simpler to implement and avoids some synchronization issues, but a misbehaving process can starve other processes indefinitely.

Q: What are the four necessary conditions for a deadlock to occur?
A: The four Coffman conditions that must all hold simultaneously for a deadlock are: mutual exclusion (resources cannot be shared and must be held exclusively), hold and wait (processes holding resources can request additional resources), no preemption (resources cannot be forcibly taken from a process), and circular wait (a circular chain exists where each process waits for a resource held by the next process in the chain). Deadlock prevention strategies work by ensuring at least one of these conditions cannot hold, such as requiring processes to request all resources at once (eliminating hold and wait) or imposing a total ordering on resource acquisition (preventing circular wait). Detection and recovery approaches allow deadlocks to occur but periodically check for them and resolve them through process termination or resource preemption.

Q: How do system calls provide an interface between user applications and the kernel?
A: System calls are the controlled gateway through which user-mode applications request services from the kernel, such as file operations, process management, and network communication. When a program invokes a system call, it triggers a software interrupt or trap instruction that switches the CPU from user mode to kernel mode, where privileged operations can be performed safely. The kernel validates the request, performs the operation on behalf of the process, and returns the result before switching back to user mode. This mechanism ensures that user programs cannot directly access hardware or kernel data structures, maintaining system security and stability while still providing necessary functionality.

Q: What is the role of the Translation Lookaside Buffer (TLB) in memory management?
A: The Translation Lookaside Buffer is a specialized hardware cache that stores recent virtual-to-physical address translations to accelerate memory access. Without the TLB, every memory access would require traversing the page table structure in main memory, adding significant latency to each operation. When a virtual address is accessed, the MMU first checks the TLB; a hit returns the physical address almost instantly, while a miss requires a page table walk and subsequent TLB update. TLB management is critical for performance, and context switches typically require TLB flushes or use address space identifiers (ASIDs) to distinguish between processes' translations.

Q: Compare and contrast the Round Robin and Multilevel Feedback Queue scheduling algorithms.
A: Round Robin is a simple preemptive algorithm that allocates each process a fixed time quantum in circular order, providing fair CPU distribution but potentially poor turnaround times for short jobs if the quantum is too large. Multilevel Feedback Queue (MLFQ) uses multiple queues with different priority levels and time quanta, automatically adjusting process priority based on behavior: CPU-bound processes that exhaust their quantum are demoted to lower-priority queues with longer quanta, while I/O-bound processes that yield early are promoted or remain at higher priorities. MLFQ adapts to process characteristics without requiring prior knowledge of burst times, achieving good interactive responsiveness while still efficiently handling batch workloads. The complexity of MLFQ lies in tuning parameters like the number of queues, quantum sizes, and promotion/demotion policies to prevent starvation and gaming.

Q: What is the difference between kernel space and user space, and why is this separation important?
A: Kernel space is the privileged memory region where the operating system kernel executes with full access to hardware and system resources, while user space is the restricted region where application programs run with limited privileges. This separation is enforced by the CPU's hardware protection rings or privilege levels, preventing user programs from directly executing privileged instructions or accessing kernel memory. If a user program attempts a forbidden operation, the CPU generates an exception that the kernel handles, typically by terminating the offending process. This architecture provides isolation, security, and stability: a bug in one application cannot corrupt the kernel or other applications, and malicious code cannot directly compromise system integrity.

Q: How do file systems organize and manage data on storage devices?
A: File systems provide a hierarchical abstraction for organizing persistent data, translating human-readable paths and filenames into physical storage locations through data structures like inodes (in Unix-like systems) or the Master File Table (in NTFS). They manage free space allocation using bitmaps, free lists, or extent trees, and track file metadata including permissions, timestamps, and size. Modern file systems implement journaling or copy-on-write techniques to maintain consistency after crashes by ensuring that metadata updates are atomic. They also provide features like symbolic and hard links, access control lists, quotas, and support for various access patterns through caching, read-ahead, and delayed writes.

Q: Explain the concept of direct memory access (DMA) and its benefits for I/O handling.
A: Direct Memory Access is a capability that allows peripheral devices to transfer data directly to and from main memory without requiring CPU involvement for each byte transferred. Without DMA, the CPU would need to execute instructions to move each data word between device registers and memory, consuming significant processor cycles for large transfers like disk reads or network packets. With DMA, the CPU initiates a transfer by programming the DMA controller with source, destination, and size, then continues executing other instructions while the transfer proceeds in parallel. When the transfer completes, the DMA controller signals the CPU via an interrupt, allowing efficient bulk data movement while keeping the CPU available for computation.

Q: What is the purpose of semaphores in process synchronization, and how do they differ from mutexes?
A: Semaphores are synchronization primitives that maintain a counter and provide atomic wait (P/down) and signal (V/up) operations, enabling processes to coordinate access to shared resources and signal events. A mutex (binary semaphore) allows only one process to hold it at a time, implementing mutual exclusion for critical sections, while counting semaphores can have values greater than one, useful for controlling access to a pool of identical resources. Unlike mutexes, counting semaphores can be signaled by any process, not just the one that performed the wait, making them suitable for producer-consumer patterns where different processes produce and consume. However, this flexibility also means semaphores lack ownership tracking, making debugging deadlocks and ensuring proper release more challenging than with strict mutexes.

Q: How does the operating system handle interrupts, and what is the interrupt handling sequence?
A: When an interrupt occurs (from hardware devices, timers, or software), the CPU suspends its current execution, saves essential state (program counter, flags) to the stack, and jumps to a predetermined interrupt handler address found in the Interrupt Descriptor Table (IDT) or equivalent structure. The interrupt handler, typically part of the kernel, identifies the interrupt source, services the request (such as reading data from a device buffer), and performs any necessary scheduling decisions. Before returning, the handler restores saved state and executes a special return-from-interrupt instruction that atomically restores the CPU to its previous mode and program location. Interrupt priorities ensure that critical interrupts can preempt handlers for less urgent ones, while interrupt masking prevents nested interrupts when necessary.

Q: What is thrashing, and how can an operating system detect and mitigate it?
A: Thrashing occurs when a system spends more time swapping pages between memory and disk than executing useful work, typically because the combined working sets of active processes exceed available physical memory. Symptoms include extremely high page fault rates, continuous disk activity, and severely degraded system responsiveness. Operating systems can detect thrashing by monitoring page fault frequency and CPU utilization; if page faults are high but CPU utilization is low, thrashing is likely occurring. Mitigation strategies include reducing the degree of multiprogramming by suspending or swapping out entire processes, implementing working set models that allocate memory based on each process's recent access patterns, and using local page replacement policies so that one process's excessive paging doesn't steal frames from well-behaved processes.

Q: Describe the difference between blocking and non-blocking I/O, and when each approach is appropriate.
A: In blocking I/O, when a process initiates an operation like reading from a socket, the process is suspended until the operation completes and data is available, simplifying program logic but potentially wasting resources while waiting. Non-blocking I/O returns immediately if no data is available (typically with an error code or partial result), allowing the process to continue executing or poll multiple I/O sources. Blocking I/O is appropriate for simple sequential programs or when using threads to handle concurrent connections, where each thread can block independently. Non-blocking I/O combined with event notification mechanisms (select, poll, epoll, kqueue) enables efficient event-driven architectures where a single thread can manage thousands of concurrent connections by handling only those that have pending data, avoiding the memory and context-switching overhead of one-thread-per-connection models.
