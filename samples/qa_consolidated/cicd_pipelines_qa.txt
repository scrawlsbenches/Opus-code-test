CI/CD Pipelines - Q&A Training Data

Q: What is the difference between continuous integration, continuous delivery, and continuous deployment?
A: Continuous integration (CI) is the practice of frequently merging code changes into a shared repository and automatically running builds and tests to detect integration issues early. Continuous delivery (CD) extends CI by ensuring code is always in a deployable state, with automated testing through staging environments, but requires manual approval for production releases. Continuous deployment goes further by automatically deploying every change that passes all pipeline stages directly to production without human intervention. The progression from CI to continuous deployment represents increasing levels of automation and trust in your pipeline's quality gates.

Q: What are the typical stages in a CI/CD pipeline and what happens at each stage?
A: A typical CI/CD pipeline consists of several key stages: source (code checkout and dependency resolution), build (compilation and artifact creation), test (unit tests, integration tests, and static analysis), staging (deployment to a pre-production environment for validation), and deploy (release to production). Each stage acts as a quality gate where failures stop the pipeline to prevent defective code from progressing. Advanced pipelines may include additional stages for security scanning, performance testing, compliance checks, and approval workflows. The ordering ensures that faster, cheaper checks run before slower, more expensive ones to provide rapid feedback.

Q: How does artifact management work in CI/CD pipelines and why is it important?
A: Artifact management involves storing, versioning, and distributing the build outputs (binaries, container images, packages) produced by your CI/CD pipeline in a dedicated repository like Artifactory, Nexus, or container registries. This ensures that the exact same artifact tested in staging is deployed to production, eliminating "works on my machine" issues and enabling reproducible deployments. Good artifact management includes metadata tagging, retention policies, vulnerability scanning, and promotion workflows between repository stages. It also enables rapid rollbacks by maintaining previous artifact versions readily available for redeployment.

Q: What testing strategies should be implemented in a CI/CD pipeline?
A: A comprehensive CI/CD testing strategy follows the test pyramid model: numerous fast unit tests at the base, fewer integration tests in the middle, and minimal end-to-end tests at the top. Unit tests should run on every commit providing immediate feedback, while integration tests verify component interactions and can run in parallel with synthetic dependencies or test containers. Contract tests ensure API compatibility between services, and smoke tests validate critical paths after deployment. The key is balancing test coverage with pipeline speed, using techniques like test parallelization, test impact analysis, and flaky test quarantine to maintain reliable, fast feedback loops.

Q: What is blue-green deployment and when should it be used?
A: Blue-green deployment maintains two identical production environments where one (blue) serves live traffic while the other (green) hosts the new version for testing. Once the green environment is validated, traffic is switched instantaneously via load balancer configuration, making the green environment live and blue available for rollback. This strategy provides zero-downtime deployments and instant rollback capability by simply reverting the traffic switch. Blue-green is ideal for applications requiring high availability and quick recovery, though it requires double the infrastructure capacity and careful handling of database schema changes and stateful components.

Q: How does canary deployment differ from blue-green, and what are its advantages?
A: Canary deployment gradually routes a small percentage of traffic to the new version while monitoring for errors, latency, and business metrics before increasing exposure. Unlike blue-green's all-or-nothing switch, canary enables risk mitigation by limiting blast radius and allowing real-world validation with actual user traffic. The rollout percentage can be increased progressively (e.g., 1%, 5%, 25%, 100%) based on automated health checks or manual approval, with automatic rollback if anomalies are detected. Canary excels for high-traffic systems where subtle bugs might only manifest under realistic load patterns, and it requires sophisticated traffic routing and observability infrastructure.

Q: What is Infrastructure as Code (IaC) and how does it integrate with CI/CD?
A: Infrastructure as Code defines infrastructure resources (servers, networks, databases) in declarative configuration files (Terraform, CloudFormation, Pulumi) that can be version-controlled, reviewed, and deployed through the same CI/CD pipelines as application code. This enables consistent, repeatable environment provisioning, drift detection, and environment parity between development, staging, and production. IaC pipelines typically include linting, plan/preview stages showing proposed changes, approval gates for production changes, and automated testing of infrastructure modules. Integrating IaC with CI/CD eliminates manual infrastructure changes, provides audit trails, and enables disaster recovery through infrastructure recreation from code.

Q: What is GitOps and how does it relate to traditional CI/CD approaches?
A: GitOps is an operational framework where Git serves as the single source of truth for both application code and infrastructure configuration, with automated agents continuously reconciling the live environment to match the declared state in Git. Unlike traditional CI/CD where pipelines push changes to environments, GitOps uses a pull-based model where cluster agents (like ArgoCD or Flux) detect Git changes and apply them automatically. This provides enhanced security by eliminating direct cluster access, complete audit trails through Git history, easy rollbacks via git revert, and self-healing infrastructure that automatically corrects drift. GitOps is particularly powerful for Kubernetes environments and multi-cluster deployments.

Q: How should secrets be managed in CI/CD pipelines?
A: Secrets management in CI/CD requires dedicated tools like HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault rather than storing credentials in code, environment variables, or CI/CD platform variables. Pipelines should retrieve secrets at runtime using short-lived tokens with minimal required permissions, and secrets should be injected as environment variables or mounted files rather than passed as command arguments that appear in logs. Implement secret rotation policies, audit logging for secret access, and separate secrets per environment to limit blast radius. Additionally, use secrets scanning tools to prevent accidental commits and implement branch protection rules requiring security review for changes touching secret configurations.

Q: What are effective rollback strategies in CI/CD and when should each be used?
A: Effective rollback strategies include artifact rollback (redeploying a previous known-good version), configuration rollback (reverting environment settings via IaC), database rollback (applying reverse migrations), and feature flag disabling (turning off problematic features without deployment). Artifact rollback is fastest and safest when database schema is compatible; blue-green enables instant traffic switch back. Forward-fix involves quickly deploying a hotfix rather than rolling back, preferred when rollback is complex or risky. Automated rollback triggers based on error rates, latency, or health checks reduce mean time to recovery. The choice depends on change type, database impact, and organizational risk tolerance, with teams needing runbooks for each scenario.

Q: What challenges exist with monorepo CI/CD pipelines and how are they addressed?
A: Monorepo pipelines face challenges including long build times, unnecessary rebuilds of unchanged components, complex dependency graphs, and coordinating releases across multiple services. Solutions include build graph analysis tools (Bazel, Nx, Turborepo) that determine affected targets based on changed files and only rebuild what's necessary. Caching strategies at multiple levels (dependency cache, build cache, test results cache) significantly reduce pipeline duration. Path-based triggers configure pipelines to run specific jobs based on which directories changed. Code ownership rules and selective testing ensure changes are validated by appropriate teams and test suites. Large organizations often implement distributed build systems and remote execution to parallelize builds across many machines.

Q: How do you implement pipeline security and prevent supply chain attacks?
A: Pipeline security requires multiple layers: securing the CI/CD platform itself with access controls, audit logging, and network isolation; validating all inputs including branch names, commit messages, and pull request data to prevent injection attacks; signing and verifying artifacts to ensure integrity through the deployment chain. Implement least-privilege access for pipeline service accounts, use ephemeral build environments to prevent persistence attacks, and scan dependencies for vulnerabilities using tools like Dependabot or Snyk. Supply chain security includes pinning dependency versions, verifying package signatures, using private registries with vulnerability scanning, and implementing SLSA (Supply-chain Levels for Software Artifacts) framework practices for provenance attestation.

Q: What metrics and observability should be implemented for CI/CD pipelines?
A: Essential CI/CD metrics include deployment frequency, lead time for changes (commit to production), mean time to recovery (MTTR), and change failure rate, collectively known as DORA metrics. Pipeline-specific metrics track build duration, test execution time, queue wait time, cache hit rates, and stage success rates to identify bottlenecks. Implement distributed tracing through pipeline stages, alerting on abnormal durations or failure patterns, and dashboards showing trends over time. Correlate deployment events with application metrics to measure deployment impact and detect regressions. This observability enables data-driven optimization, capacity planning, and demonstrates the value of CI/CD investments to stakeholders.

Q: How do you handle database migrations in CI/CD pipelines safely?
A: Safe database migration in CI/CD requires separating schema changes from application deployments using expand-contract patterns: first deploy schema additions (expand) that are backward compatible, then deploy application changes using the new schema, finally remove deprecated schema elements (contract). Implement migration versioning and tracking, run migrations in transactions where supported, and test migrations against production-like data volumes. Blue-green database strategies use read replicas promoted during cutover, while online schema change tools (gh-ost, pt-online-schema-change) enable non-blocking alterations on large tables. Always maintain rollback scripts, implement migration dry-runs in staging, and consider feature flags to decouple feature activation from deployment timing.

Q: What are branch protection rules and how do they enhance CI/CD quality?
A: Branch protection rules enforce quality gates on critical branches (main, release) by requiring status checks to pass before merging, mandating code review approvals, preventing force pushes, and requiring signed commits. These rules ensure that all code reaching production has passed CI validation, been reviewed by appropriate team members, and maintains audit trail integrity. Advanced configurations include requiring specific reviewers based on changed file paths (CODEOWNERS), enforcing linear history through squash merging, and requiring up-to-date branches before merge to ensure CI ran against the latest base. Branch protection integrates with CI/CD by making pipeline success a merge prerequisite, creating a quality gate that prevents broken code from progressing.
