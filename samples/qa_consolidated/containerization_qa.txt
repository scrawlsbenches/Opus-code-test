Q: What is the difference between a Docker image and a Docker container?
A: A Docker image is a read-only template containing the application code, runtime, libraries, and dependencies needed to run an application, essentially serving as a blueprint. A container is a running instance of an image, representing an isolated process with its own filesystem, network, and process space. You can create multiple containers from the same image, each running independently. Images are stored in registries and are immutable, while containers are ephemeral and can be started, stopped, and deleted without affecting the underlying image.

Q: What are the best practices for writing efficient Dockerfiles?
A: Start with a minimal base image like Alpine or distroless to reduce attack surface and image size. Order instructions from least to most frequently changing to maximize layer caching, placing COPY for source code near the end. Use multi-stage builds to separate build dependencies from runtime dependencies, keeping final images lean. Combine RUN commands with && to reduce layers, and always clean up package manager caches in the same layer they are created. Avoid running containers as root by creating a non-root user with USER instruction.

Q: How does container networking work in Docker?
A: Docker provides several network drivers including bridge, host, overlay, and macvlan for different use cases. The default bridge network creates an isolated network namespace where containers can communicate using IP addresses or container names as DNS. Containers expose ports to the host using port mapping with the -p flag, translating host ports to container ports. For multi-host networking, overlay networks enable containers across different Docker hosts to communicate securely through encrypted tunnels. Network policies and firewalls can be applied to control traffic flow between containers.

Q: What is a Kubernetes Pod and why is it the smallest deployable unit?
A: A Pod is a group of one or more containers that share storage, network, and a specification for how to run the containers, representing the smallest deployable unit in Kubernetes. Containers within a Pod share the same IP address and port space, can communicate via localhost, and have access to shared volumes. Pods are designed this way because tightly coupled application components often need to be co-located and co-scheduled, such as a main application container with a sidecar for logging. Pods are ephemeral by nature and are typically managed by higher-level controllers like Deployments rather than created directly.

Q: How do Kubernetes Services enable communication between Pods?
A: Services provide a stable network endpoint for accessing a set of Pods, abstracting away the ephemeral nature of individual Pod IP addresses. A Service uses label selectors to identify which Pods should receive traffic, automatically updating its endpoints as Pods are created or destroyed. ClusterIP Services expose Pods internally within the cluster, NodePort Services expose them on each node's IP at a static port, and LoadBalancer Services integrate with cloud providers to provision external load balancers. Services also provide basic load balancing, distributing traffic across healthy Pods using round-robin by default.

Q: What is a Kubernetes Deployment and how does it manage application updates?
A: A Deployment is a controller that manages the desired state for Pods and ReplicaSets, ensuring the specified number of Pod replicas are running at all times. It enables declarative updates by allowing you to describe the desired end state, and Kubernetes handles the transition from current to desired state. Rolling updates are the default strategy, gradually replacing old Pods with new ones while maintaining availability and allowing rollback if issues occur. Deployments track revision history, enabling you to roll back to previous versions using kubectl rollout undo, and support pause/resume for canary-style deployments.

Q: What is container orchestration and why is it necessary?
A: Container orchestration automates the deployment, scaling, networking, and management of containerized applications across clusters of machines. It is necessary because manually managing containers at scale becomes impractical, requiring automated solutions for scheduling, service discovery, load balancing, and self-healing. Orchestration platforms like Kubernetes handle complex tasks such as bin packing containers onto nodes efficiently, maintaining desired replica counts, and performing rolling updates without downtime. They also provide essential features like secrets management, configuration distribution, and resource quota enforcement that are critical for production environments.

Q: What is a container registry and how is it used in the deployment pipeline?
A: A container registry is a storage and distribution system for container images, functioning similarly to how package managers store software libraries. Popular options include Docker Hub, Amazon ECR, Google Container Registry, and self-hosted solutions like Harbor. In a typical CI/CD pipeline, the build stage creates an image and pushes it to the registry with a unique tag, and the deployment stage pulls that specific tagged image to ensure consistency across environments. Registries support features like image scanning for vulnerabilities, access control through authentication, and image signing for supply chain security.

Q: How do volumes work in Docker and Kubernetes for persistent storage?
A: Volumes provide a mechanism for containers to store data that persists beyond the container lifecycle and enables data sharing between containers. Docker supports named volumes managed by Docker, bind mounts that map host directories into containers, and tmpfs mounts for sensitive data stored in memory. Kubernetes abstracts storage through PersistentVolumes representing actual storage resources and PersistentVolumeClaims that pods use to request storage. Storage classes enable dynamic provisioning, automatically creating storage when claims are made, and support different performance tiers and backup policies.

Q: What are health checks in containers and why are they important?
A: Health checks are mechanisms that allow container runtimes and orchestrators to monitor whether an application inside a container is functioning correctly, not just whether the process is running. Docker supports HEALTHCHECK instructions in Dockerfiles that run commands periodically to verify application health, marking containers as healthy, unhealthy, or starting. Kubernetes provides three types of probes: liveness probes that restart containers when they fail, readiness probes that remove pods from service endpoints when not ready, and startup probes for slow-starting applications. Properly configured health checks enable self-healing, prevent traffic routing to broken instances, and support zero-downtime deployments.

Q: How does Kubernetes handle horizontal scaling of applications?
A: Kubernetes supports both manual scaling through kubectl scale commands and automatic scaling through the Horizontal Pod Autoscaler (HPA). The HPA monitors metrics like CPU utilization, memory usage, or custom application metrics and adjusts the number of pod replicas to maintain target thresholds. It works with Deployments, ReplicaSets, and StatefulSets, scaling up during high demand and scaling down during low usage to optimize resource utilization. The Cluster Autoscaler complements HPA by adding or removing nodes when pods cannot be scheduled due to resource constraints or when nodes are underutilized.

Q: What is the difference between Docker Compose and Kubernetes?
A: Docker Compose is a tool for defining and running multi-container applications on a single host using a YAML file to configure services, networks, and volumes. It is ideal for local development, testing, and simple deployments where high availability is not required. Kubernetes is a full-featured orchestration platform designed for production workloads across multiple nodes, providing advanced features like self-healing, rolling updates, service discovery, and automatic scaling. While Compose is simpler and faster to set up, Kubernetes offers the resilience, scalability, and operational tooling needed for mission-critical applications.

Q: How do you implement secrets management in Kubernetes?
A: Kubernetes Secrets store sensitive information like passwords, tokens, and certificates separately from pod specifications and container images. Secrets can be mounted as files in a volume or exposed as environment variables, with the data base64-encoded at rest in etcd. For enhanced security, enable encryption at rest for etcd, use RBAC to restrict access to secrets, and consider external secrets managers like HashiCorp Vault or AWS Secrets Manager for rotation and audit capabilities. The CSI Secrets Store Driver allows mounting secrets from external providers directly into pods, keeping sensitive data outside the Kubernetes control plane.

Q: What are init containers in Kubernetes and when should you use them?
A: Init containers are specialized containers that run before app containers in a Pod and must complete successfully before the main containers start. They are useful for setup tasks like waiting for dependent services to become available, running database migrations, fetching configuration or secrets from external sources, or setting file permissions on shared volumes. Init containers run sequentially, each completing before the next begins, and if any init container fails, Kubernetes restarts the Pod according to its restart policy. This pattern keeps initialization logic separate from the main application, following the single responsibility principle.

Q: How do you implement zero-downtime deployments with Kubernetes?
A: Zero-downtime deployments require a combination of rolling update strategy, proper health checks, and graceful shutdown handling. Configure the Deployment with maxUnavailable and maxSurge parameters to control how many pods can be unavailable or created in excess during updates. Implement readiness probes to ensure new pods only receive traffic after fully initializing, and configure preStop lifecycle hooks to allow in-flight requests to complete before termination. Set terminationGracePeriodSeconds appropriately for your application's shutdown time, and ensure your application handles SIGTERM by completing current work and refusing new connections.
