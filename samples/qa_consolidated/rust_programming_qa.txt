Q: What is ownership in Rust and why is it important?
A: Ownership is Rust's core memory management system where each value has exactly one owner variable, and the value is dropped when the owner goes out of scope. This eliminates the need for garbage collection while preventing memory leaks and double-free errors at compile time. The ownership system enforces memory safety without runtime overhead, making Rust programs both safe and performant. When a value is assigned to another variable, ownership transfers (moves) unless the type implements the Copy trait.

Q: How does borrowing work in Rust, and what are the rules governing references?
A: Borrowing allows you to reference data without taking ownership, using either immutable references (&T) or mutable references (&mut T). The borrowing rules state that you can have either one mutable reference OR any number of immutable references to a value at any given time, but never both simultaneously. References must always be valid, meaning they cannot outlive the data they point to. These rules are enforced at compile time by the borrow checker, preventing data races and dangling pointer bugs.

Q: What are lifetimes in Rust and when do you need to annotate them explicitly?
A: Lifetimes are Rust's way of tracking how long references remain valid, ensuring that borrowed data outlives all references to it. The compiler can often infer lifetimes through elision rules, but explicit annotations (like 'a in &'a str) are needed when the compiler cannot determine relationships between multiple references. Common cases requiring explicit lifetimes include functions returning references derived from parameters, structs holding references, and trait implementations involving references. Lifetime annotations describe relationships between lifetimes but do not change how long values live.

Q: How do traits work in Rust, and how do they compare to interfaces in other languages?
A: Traits define shared behavior through method signatures that types can implement, similar to interfaces but with key differences like default method implementations and the ability to implement traits for external types. Unlike traditional OOP interfaces, traits support static dispatch through monomorphization, generating specialized code for each concrete type at compile time. Traits also enable powerful abstractions through trait bounds, where generic code specifies required capabilities. The orphan rule requires that either the trait or the type must be local to your crate when implementing traits.

Q: What is the difference between Result and Option in Rust, and when should each be used?
A: Option<T> represents an optional value that is either Some(T) or None, used when absence of a value is a normal possibility rather than an error condition. Result<T, E> represents either success with Ok(T) or failure with Err(E), carrying error information and used for operations that can fail in meaningful ways. Use Option for cases like finding an element in a collection or optional configuration values, and Result for I/O operations, parsing, and other fallible computations. Both types integrate with the ? operator for ergonomic error propagation and support combinators like map, and_then, and unwrap_or for functional-style handling.

Q: How does pattern matching work in Rust, and what makes it powerful?
A: Pattern matching in Rust through match expressions and if let provides exhaustive checking of all possible variants, ensuring you handle every case at compile time. Patterns can destructure complex types like enums, structs, and tuples, binding inner values to variables while testing structure. Match arms can include guards for additional conditions and use the | operator to match multiple patterns. The compiler verifies exhaustiveness and warns about unreachable patterns, making pattern matching both safe and expressive for control flow.

Q: What is "fearless concurrency" in Rust and how does the language achieve it?
A: Fearless concurrency refers to Rust's compile-time guarantees that eliminate data races, allowing developers to write concurrent code without fear of subtle threading bugs. The ownership and borrowing rules naturally prevent shared mutable state between threads unless explicitly synchronized. The Send trait marks types safe to transfer between threads, while Sync marks types safe to share references across threads. These marker traits are automatically derived by the compiler, and thread-safety violations become compile errors rather than runtime bugs.

Q: What are zero-cost abstractions in Rust and how do they work?
A: Zero-cost abstractions mean that high-level features like iterators, closures, and generics compile down to code as efficient as hand-written low-level equivalents. Rust achieves this through monomorphization, where generic code is specialized for each concrete type at compile time, eliminating virtual dispatch overhead. Iterators, for example, are often fully inlined into tight loops with no heap allocation or function call overhead. This design philosophy lets developers write expressive, maintainable code without sacrificing runtime performance.

Q: When and why would you use unsafe Rust, and what are the safety invariants you must uphold?
A: Unsafe Rust allows operations the compiler cannot verify as safe, including dereferencing raw pointers, calling unsafe functions, accessing mutable statics, and implementing unsafe traits. You use unsafe when interfacing with C code through FFI, implementing low-level data structures, or when you can prove safety properties the compiler cannot infer. Within unsafe blocks, you must uphold invariants like valid pointer alignment, proper initialization, and maintaining reference aliasing rules. The goal is to encapsulate unsafe code behind safe abstractions, limiting the surface area where bugs can occur.

Q: What are the main smart pointer types in Rust and what problems do they solve?
A: Box<T> provides heap allocation with single ownership, useful for recursive types and large data that should not be copied. Rc<T> enables multiple ownership through reference counting for single-threaded scenarios, while Arc<T> provides thread-safe reference counting for concurrent contexts. RefCell<T> and Mutex<T> enable interior mutability, allowing mutation of data even when you only have an immutable reference, with RefCell checking borrow rules at runtime and Mutex providing thread-safe access. These types extend Rust's ownership system to handle complex ownership patterns that single-owner stack allocation cannot express.

Q: How do iterators work in Rust, and what makes them efficient?
A: Iterators in Rust are lazy sequences that implement the Iterator trait with a next() method returning Option<Item>, processing elements one at a time only when consumed. Iterator adapters like map, filter, and flat_map chain together without allocating intermediate collections, building a pipeline that is evaluated in a single pass. The compiler aggressively inlines and optimizes iterator chains, often producing assembly identical to hand-written loops. Iterators are the idiomatic way to process collections in Rust, combining expressiveness with performance through zero-cost abstraction.

Q: What are Rust macros and how do declarative macros differ from procedural macros?
A: Macros in Rust enable metaprogramming by generating code at compile time, reducing boilerplate and enabling domain-specific syntax. Declarative macros (macro_rules!) use pattern matching on syntax trees, matching against token patterns and expanding to new tokens, ideal for simple code generation and DRY patterns. Procedural macros are Rust functions that receive and produce token streams, enabling derive macros, attribute macros, and function-like macros with full programmatic control. Procedural macros can perform arbitrary computation, access external resources, and are used for complex code generation like serialization derives and async transformations.

Q: How does Rust's enum type differ from enums in other languages, and why is this significant?
A: Rust enums are algebraic data types (sum types) where each variant can hold different types and amounts of data, unlike C-style enums that are merely integer constants. This makes enums perfect for modeling states with associated data, like Option and Result, where each variant carries relevant information. Combined with exhaustive pattern matching, enums enable type-safe state machines and make invalid states unrepresentable at the type level. The discriminant is typically a single byte, and the compiler optimizes enum layouts, even performing null-pointer optimization for types like Option<&T>.

Q: What is the Deref trait in Rust and how does deref coercion work?
A: The Deref trait allows types to behave like references by implementing a target method that returns a reference to inner data, enabling the dereference operator (*) to work on custom types. Deref coercion automatically converts references to types implementing Deref into references to the target type, so &String coerces to &str and &Box<T> coerces to &T. This enables functions accepting &str to work with String, Vec, and other types seamlessly without explicit conversion. The pattern is fundamental to smart pointers, making Box<T>, Rc<T>, and user-defined wrapper types ergonomic to use.

Q: How does Rust handle error propagation, and what is the purpose of the ? operator?
A: The ? operator provides concise error propagation by returning early from a function if a Result is Err or an Option is None, otherwise unwrapping the success value. When applied to a Result, ? extracts the Ok value or returns the Err after converting it through the From trait if the function's return type differs from the error type. This replaces verbose match statements with a single character while maintaining explicit error handling and type safety. The ? operator works in functions returning Result, Option, or types implementing the Try trait, and is the idiomatic way to propagate errors up the call stack.
