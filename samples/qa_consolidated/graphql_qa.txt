Q: What is the difference between queries, mutations, and subscriptions in GraphQL?
A: Queries are read-only operations used to fetch data from the server without causing side effects. Mutations are write operations that create, update, or delete data on the server and return the modified result. Subscriptions establish a persistent connection to the server, enabling real-time updates when specific events occur. While queries and mutations follow a request-response model, subscriptions use WebSockets or similar protocols to push data to clients as changes happen.

Q: How do you define a schema in GraphQL and what are its core components?
A: A GraphQL schema is defined using the Schema Definition Language (SDL), which describes the types, fields, and relationships in your API. The core components include object types that define the shape of data, scalar types like String, Int, Boolean, Float, and ID for primitive values, and special root types Query, Mutation, and Subscription that serve as entry points. The schema acts as a contract between client and server, enabling strong typing, introspection, and automatic documentation generation.

Q: What are resolvers in GraphQL and how do they work?
A: Resolvers are functions that execute when a specific field is requested, responsible for fetching or computing the actual data for that field. Each resolver receives four arguments: parent (the result from the parent resolver), args (field arguments), context (shared data like authentication), and info (query metadata). Resolvers can return values directly, promises, or arrays of promises, and GraphQL will automatically unwrap them. The resolver chain starts at root fields and cascades down through nested fields, with each resolver building upon its parent's returned data.

Q: What is the N+1 problem in GraphQL and why does it occur?
A: The N+1 problem occurs when fetching a list of N items triggers N additional database queries to resolve nested fields for each item. For example, querying 100 users with their posts would result in 1 query for users plus 100 separate queries for each user's posts. This happens because GraphQL resolvers execute independently and have no knowledge of sibling resolvers executing the same query pattern. The problem severely degrades performance and can overwhelm databases, making it one of the most critical performance issues in GraphQL implementations.

Q: How does DataLoader solve the N+1 problem in GraphQL?
A: DataLoader batches multiple individual requests for the same resource type into a single bulk query by collecting all keys within a single tick of the event loop. Instead of executing 100 separate queries for user posts, DataLoader combines them into one query fetching posts for all 100 user IDs at once. It also provides request-level caching, so if the same entity is requested multiple times within a single request, it returns the cached result. DataLoader must be instantiated per-request to prevent data leakage between users and ensure proper cache invalidation.

Q: What are fragments in GraphQL and when should you use them?
A: Fragments are reusable units of fields that can be included in multiple queries, reducing code duplication and improving maintainability. You define a fragment on a specific type and then spread it into queries using the spread operator (...FragmentName). Fragments are particularly useful when multiple components need the same fields from a type, when working with interfaces and unions to specify type-specific fields, or when building complex queries that would otherwise repeat field selections. They also help with code organization in large applications by co-locating data requirements with components.

Q: What are GraphQL directives and how are built-in directives used?
A: Directives are annotations that modify the execution behavior of fields, fragments, or operations, prefixed with the @ symbol. GraphQL includes three built-in directives: @include(if: Boolean) conditionally includes a field when the argument is true, @skip(if: Boolean) excludes a field when true, and @deprecated(reason: String) marks schema elements as deprecated. Custom directives can be created for various purposes such as authentication (@auth), caching (@cacheControl), or data transformation (@uppercase). Directives enable dynamic query behavior without changing the query structure itself.

Q: How do you implement authentication in a GraphQL API?
A: Authentication in GraphQL is typically handled at the HTTP layer before requests reach resolvers, with credentials passed via headers like Authorization Bearer tokens. The validated user information is then attached to the GraphQL context object, making it accessible to all resolvers throughout the request. Authorization can be implemented at multiple levels: field-level using custom directives or resolver middleware, type-level by wrapping resolvers, or at the schema level using schema transforms. Many implementations combine JWT tokens for authentication with role-based access control in resolvers, often using libraries like graphql-shield for declarative permission rules.

Q: What pagination strategies are available in GraphQL and which is recommended?
A: GraphQL supports offset-based pagination using skip and limit arguments, which is simple but suffers from inconsistencies when data changes between pages. Cursor-based pagination, standardized by the Relay Connection specification, uses opaque cursors to mark positions and provides edges, nodes, and pageInfo for navigation. The Relay approach is recommended because it handles real-time data changes gracefully, works efficiently with database indexes, and provides consistent results even when items are added or removed. Each connection returns pageInfo with hasNextPage, hasPreviousPage, startCursor, and endCursor for complete navigation control.

Q: How should errors be handled in GraphQL responses?
A: GraphQL returns errors in a dedicated errors array alongside partial data, allowing clients to receive successful fields even when some fail. Each error object contains a message, optional locations pointing to the query position, a path indicating which field failed, and optional extensions for custom error data. Best practices include categorizing errors by type (validation, authentication, business logic) using error codes in extensions, never exposing internal implementation details in production, and implementing error masking to replace sensitive information. Field-level errors with null values and non-null type handling require careful schema design to prevent error propagation up the resolver chain.

Q: What is schema stitching and when would you use it?
A: Schema stitching combines multiple GraphQL schemas into a single unified schema, enabling clients to query across different services with one request. It works by merging type definitions and creating delegation resolvers that forward field requests to the appropriate underlying schema. Schema stitching is useful for gradually migrating monoliths to microservices, combining third-party APIs with internal services, or creating a gateway layer over legacy systems. However, schema stitching has been largely superseded by Apollo Federation for new projects, as federation provides better separation of concerns, independent service deployment, and clearer ownership boundaries.

Q: What is Apollo Federation and how does it differ from schema stitching?
A: Apollo Federation is a specification for building distributed GraphQL architectures where each service (subgraph) owns and extends specific types in a single unified graph. Unlike schema stitching which merges schemas at the gateway, federation allows services to contribute fields to types owned by other services using @key for entity identification and @external, @requires, @provides for cross-service relationships. The gateway uses query planning to fetch data from multiple subgraphs in optimal order, handling joins automatically. Federation provides better scalability, clearer service boundaries, independent deployability, and built-in support for entity references across service boundaries.

Q: How do you handle the N+1 problem when using GraphQL with SQL databases specifically?
A: For SQL databases, the N+1 problem can be addressed through multiple strategies beyond DataLoader. Query builders like Knex or Prisma can generate efficient JOINs based on the requested fields. The graphql-parse-resolve-info library extracts requested fields from the info argument, allowing resolvers to construct targeted queries with only necessary JOINs. Some ORMs like Prisma automatically batch queries, while others require explicit include or eager loading configurations. For complex scenarios, implementing a lookahead pattern that analyzes the entire query tree before execution enables generating a single optimized SQL query that fetches all needed data in one round trip.

Q: What security considerations are important when deploying a GraphQL API?
A: GraphQL APIs face unique security challenges including query complexity attacks where deeply nested or aliased queries consume excessive resources. Implement query depth limiting, complexity analysis with cost calculation, and rate limiting based on query complexity rather than just request count. Disable introspection in production to prevent schema discovery, or use persisted queries to allow only pre-approved operations. Field-level authorization must be enforced in resolvers since clients control field selection. Validate all input arguments thoroughly, implement proper error masking to avoid information leakage, and consider using automatic query timeout limits to prevent long-running operations from degrading service availability.

Q: How do you design a GraphQL schema for optimal client experience and server performance?
A: Effective schema design starts with thinking in graphs rather than REST resources, modeling relationships between entities naturally. Use nullable fields by default and reserve non-null for truly required data to prevent resolver failures from propagating. Design mutations to return the affected data including related entities clients commonly need afterward, reducing follow-up queries. Implement connections for lists that might need pagination, even if initially small. Use input types for complex mutation arguments and enums for finite value sets. Consider future extensibility by using object types for fields that might gain properties later, and leverage interfaces and unions for polymorphic types to enable type-specific field queries while maintaining a clean, discoverable API structure.
