Q: What are the key differences between SQL and NoSQL databases?
A: SQL databases are relational, using structured tables with predefined schemas and supporting ACID transactions, making them ideal for complex queries and data integrity requirements. NoSQL databases offer flexible schemas and are designed for horizontal scaling, with four main types: document stores (MongoDB), key-value stores (Redis), column-family stores (Cassandra), and graph databases (Neo4j). SQL excels at structured data with relationships, while NoSQL handles unstructured or semi-structured data and high-velocity writes better. The choice depends on your data model, consistency requirements, scaling needs, and query patterns. Modern applications often use polyglot persistence, combining both SQL and NoSQL databases to leverage each type's strengths.

Q: How does database indexing work and when should you use indexes?
A: Database indexes are data structures (typically B-trees or hash tables) that provide faster lookup paths to rows without scanning entire tables. When you create an index on a column, the database maintains a sorted structure that maps column values to row locations, reducing query time from O(n) to O(log n) for B-tree indexes. Use indexes on columns frequently used in WHERE clauses, JOIN conditions, and ORDER BY statements. However, indexes have tradeoffs: they speed up reads but slow down writes because the index must be updated with each INSERT, UPDATE, or DELETE. Avoid over-indexing, particularly on columns with low cardinality or tables with heavy write loads. Composite indexes can serve multiple queries but column order matters significantly for query optimization.

Q: What is database normalization and what are the normal forms?
A: Database normalization is the process of organizing tables to minimize data redundancy and dependency anomalies through a series of progressive normal forms. First Normal Form (1NF) eliminates repeating groups by ensuring atomic values in each column. Second Normal Form (2NF) removes partial dependencies by ensuring non-key columns depend on the entire primary key. Third Normal Form (3NF) eliminates transitive dependencies where non-key columns depend on other non-key columns. Boyce-Codd Normal Form (BCNF) strengthens 3NF by ensuring every determinant is a candidate key. While normalization reduces redundancy and update anomalies, over-normalization can hurt read performance due to excessive joins, leading to strategic denormalization in read-heavy systems.

Q: Explain the ACID properties in database transactions.
A: ACID properties ensure reliable database transactions in the presence of errors, power failures, and concurrent access. Atomicity guarantees that all operations in a transaction succeed or all fail together, with no partial completion. Consistency ensures that a transaction brings the database from one valid state to another, maintaining all defined rules and constraints. Isolation prevents concurrent transactions from interfering with each other, with various levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) trading off between concurrency and consistency. Durability guarantees that once a transaction commits, the changes persist even after system crashes, typically through write-ahead logging. Understanding ACID is crucial for designing systems that require data integrity, such as financial applications.

Q: What are common query optimization techniques?
A: Query optimization involves multiple strategies to improve database performance. Use EXPLAIN or EXPLAIN ANALYZE to understand query execution plans and identify bottlenecks like full table scans or inefficient joins. Proper indexing is foundational, but ensure indexes are actually being used by avoiding functions on indexed columns in WHERE clauses. Write selective queries that filter data early, use appropriate JOIN types, and avoid SELECT * in favor of specific columns. Consider query restructuring: sometimes rewriting a correlated subquery as a JOIN dramatically improves performance. For large result sets, implement pagination using LIMIT/OFFSET or keyset pagination. Statistics maintenance is crucial as the query optimizer relies on accurate table statistics to choose efficient execution plans.

Q: How does database caching improve performance?
A: Database caching stores frequently accessed data in faster storage tiers to reduce database load and latency. Application-level caching with tools like Redis or Memcached stores query results, session data, or computed values in memory. Query result caching stores entire query results, while object caching stores serialized objects. The cache-aside pattern (lazy loading) fetches from cache first, falling back to the database on misses. Write-through caching updates both cache and database synchronously, while write-behind (write-back) batches database writes for better performance. Cache invalidation remains challenging: time-based expiration (TTL), event-driven invalidation, and versioning are common strategies. Effective caching requires understanding access patterns and accepting eventual consistency tradeoffs.

Q: What is the difference between horizontal and vertical scaling in databases?
A: Vertical scaling (scaling up) involves adding more resources (CPU, RAM, storage) to a single server, which is simpler but has hardware limits and creates a single point of failure. Horizontal scaling (scaling out) distributes data across multiple servers through sharding or replication, offering theoretically unlimited scalability and fault tolerance. Sharding partitions data across nodes using strategies like hash-based, range-based, or directory-based distribution, but complicates queries spanning multiple shards and requires careful shard key selection. Replication creates copies of data across nodes, improving read scalability and availability but requiring consistency management. SQL databases traditionally favor vertical scaling, while NoSQL databases are designed for horizontal scaling, though modern distributed SQL databases like CockroachDB and TiDB bridge this gap.

Q: What are database transactions and isolation levels?
A: A database transaction is a sequence of operations treated as a single logical unit of work that either completes entirely or fails entirely. Isolation levels define how transactions interact with concurrent operations. Read Uncommitted allows dirty reads (seeing uncommitted changes), offering highest concurrency but lowest consistency. Read Committed prevents dirty reads but allows non-repeatable reads (same query returning different results). Repeatable Read ensures consistent reads within a transaction but may allow phantom reads (new rows appearing). Serializable provides complete isolation as if transactions executed sequentially, preventing all anomalies but reducing concurrency. Choosing the right isolation level involves balancing consistency requirements against performance, with most applications defaulting to Read Committed as a reasonable compromise.

Q: How do you design a database schema for a many-to-many relationship?
A: Many-to-many relationships require a junction table (also called bridge, associative, or linking table) that references both related entities. This junction table contains foreign keys to both parent tables, transforming the many-to-many into two one-to-many relationships. For example, students and courses have a many-to-many relationship resolved by an enrollments table with student_id and course_id foreign keys. The junction table can include additional attributes specific to the relationship, like enrollment_date or grade. Create a composite primary key from both foreign keys, or use a surrogate key if the junction table needs to be referenced elsewhere. Add indexes on both foreign key columns to optimize JOIN queries from either direction, and consider adding unique constraints to prevent duplicate relationships.

Q: What is database sharding and what are common sharding strategies?
A: Database sharding horizontally partitions data across multiple database instances to improve scalability and performance beyond single-server limits. Hash-based sharding applies a hash function to the shard key (like user_id), providing even distribution but making range queries difficult. Range-based sharding partitions by value ranges (like dates or alphabetical ranges), supporting range queries but risking hotspots if access patterns are uneven. Directory-based sharding uses a lookup service to map keys to shards, offering flexibility but adding latency and a potential single point of failure. Geographic sharding places data near users for lower latency. Key considerations include choosing shard keys that evenly distribute data and queries, handling cross-shard queries and transactions, managing schema changes across shards, and planning for resharding as data grows.

Q: What is the CAP theorem and how does it affect database design?
A: The CAP theorem states that distributed systems can only guarantee two of three properties simultaneously: Consistency (all nodes see the same data), Availability (every request receives a response), and Partition tolerance (the system continues operating despite network failures). Since network partitions are unavoidable in distributed systems, the practical choice is between CP (consistency over availability, like traditional RDBMS and ZooKeeper) and AP (availability over consistency, like Cassandra and DynamoDB). Many modern databases offer tunable consistency, letting applications choose consistency levels per operation. Understanding CAP helps architects make informed tradeoffs: financial systems typically prioritize consistency, while social media feeds might accept eventual consistency for higher availability. The PACELC theorem extends CAP to also consider latency-consistency tradeoffs during normal operation.

Q: How do you implement optimistic vs pessimistic locking?
A: Pessimistic locking acquires locks before reading data, assuming conflicts are likely, blocking other transactions from modifying the same data until the lock is released. This prevents conflicts but reduces concurrency and can cause deadlocks. Optimistic locking assumes conflicts are rare, allowing concurrent reads and only checking for conflicts at commit time using version numbers or timestamps. If another transaction modified the data, the commit fails and the application must retry. Optimistic locking typically adds a version column that increments on each update; the UPDATE statement includes the expected version in the WHERE clause. Use pessimistic locking for high-contention scenarios where conflicts are common and retry costs are high. Use optimistic locking for read-heavy workloads with infrequent updates, as it provides better throughput and scalability.

Q: What are materialized views and when should you use them?
A: Materialized views are database objects that store the results of a query physically, unlike regular views which execute their query each time they are accessed. They precompute expensive aggregations, joins, or complex calculations, trading storage space for query performance. Materialized views excel at speeding up analytical queries, dashboard data, and reporting workloads where the underlying data changes infrequently relative to read frequency. The main challenge is refresh strategy: full refresh recomputes the entire view (simple but expensive), while incremental refresh updates only changed portions (complex but efficient). Refresh can be triggered manually, on a schedule, or on-commit. Consider materialized views when queries are expensive to compute, results are accessed frequently, and some staleness is acceptable. Monitor storage costs and refresh overhead as the underlying tables grow.

Q: What is database connection pooling and why is it important?
A: Connection pooling maintains a cache of reusable database connections rather than creating new connections for each request. Database connections are expensive to establish, involving TCP handshakes, authentication, session initialization, and memory allocation on both client and server. A connection pool pre-creates connections that application threads can borrow and return, amortizing connection overhead across many requests. Key configuration parameters include minimum and maximum pool size, connection timeout, idle timeout, and validation queries. Pool size should balance concurrency needs against database server capacity; too few connections cause request queuing, while too many overwhelm the database. Popular implementations include HikariCP for Java, pgBouncer for PostgreSQL, and built-in pooling in most ORMs. Connection pooling is essential for web applications serving concurrent users and dramatically improves both response times and resource utilization.

Q: How do you handle database migrations in production systems?
A: Database migrations manage schema changes in a controlled, versioned, and reversible manner. Use migration tools like Flyway, Liquibase, or framework-specific tools (Rails migrations, Django migrations, Alembic) that track applied changes and enforce ordering. Each migration should be atomic, idempotent, and include both up and down scripts for rollback capability. For production systems, implement zero-downtime migrations using patterns like expand-contract: first add new columns or tables (expand), deploy application code that works with both schemas, migrate data, then remove old columns (contract). Avoid long-running locks by using online schema change tools like pt-online-schema-change or gh-ost for MySQL. Always test migrations against production-like data volumes, have rollback plans ready, and schedule changes during low-traffic periods. Version control your migrations alongside application code to ensure schema and code stay synchronized.

Q: What are the fundamental differences between SQL and NoSQL databases?
A: SQL databases are relational, storing data in structured tables with predefined schemas and using SQL for queries, making them ideal for complex queries and transactions. NoSQL databases are non-relational, supporting flexible schemas with document, key-value, column-family, or graph data models. SQL databases excel at ACID compliance and complex joins, while NoSQL databases prioritize horizontal scalability and handling unstructured data. The choice depends on your data structure, consistency requirements, and scaling needs. SQL databases like PostgreSQL are better for financial systems requiring strict consistency, while NoSQL databases like MongoDB suit rapidly evolving applications with flexible data requirements.

Q: How do database indexes work and when should you use them?
A: Database indexes are data structures that maintain a sorted reference to rows based on specific column values, similar to a book index that points to page numbers. B-tree indexes are most common, organizing data in a balanced tree structure for O(log n) lookups instead of O(n) full table scans. You should create indexes on columns frequently used in WHERE clauses, JOIN conditions, and ORDER BY statements. However, indexes have trade-offs: they speed up reads but slow down writes since every INSERT, UPDATE, or DELETE must also update the index. Composite indexes on multiple columns should order columns by selectivity and query patterns. Over-indexing wastes storage and degrades write performance, so monitor query patterns and use EXPLAIN plans to guide indexing decisions.

Q: What are the ACID properties and why are they important for databases?
A: ACID stands for Atomicity, Consistency, Isolation, and Durability, forming the foundation of reliable database transactions. Atomicity ensures transactions are all-or-nothing; if any part fails, the entire transaction rolls back to maintain data integrity. Consistency guarantees that transactions bring the database from one valid state to another, enforcing all defined rules and constraints. Isolation ensures concurrent transactions execute as if they were sequential, preventing dirty reads, phantom reads, and other anomalies through various isolation levels. Durability guarantees that committed transactions persist even after system failures, typically through write-ahead logging. These properties are critical for financial systems, inventory management, and any application where data corruption or loss would have serious consequences.

Q: What is database normalization and what are its main forms?
A: Database normalization is the process of organizing tables to minimize redundancy and dependency issues, improving data integrity and reducing anomalies during updates. First Normal Form (1NF) requires atomic values in each column with no repeating groups, eliminating arrays or nested structures. Second Normal Form (2NF) builds on 1NF by removing partial dependencies, ensuring non-key columns depend on the entire primary key, not just part of it. Third Normal Form (3NF) eliminates transitive dependencies where non-key columns depend on other non-key columns rather than directly on the primary key. Boyce-Codd Normal Form (BCNF) is a stricter version of 3NF addressing certain edge cases. While normalization reduces redundancy, over-normalization can harm read performance through excessive joins, so denormalization is sometimes used strategically for read-heavy workloads.

Q: What strategies can optimize slow database queries?
A: Query optimization begins with analyzing execution plans using EXPLAIN or EXPLAIN ANALYZE to identify bottlenecks like full table scans, inefficient joins, or missing indexes. Adding appropriate indexes on filtered and joined columns often provides the biggest improvement, but ensure you are not over-indexing. Rewrite queries to avoid SELECT * and only fetch needed columns, reducing I/O and memory usage. Use query hints sparingly to guide the optimizer when it makes poor choices, and consider query restructuring to leverage index-only scans. For large result sets, implement pagination using keyset pagination rather than OFFSET for better performance at scale. Regularly update table statistics so the query planner makes informed decisions, and consider partitioning large tables to reduce the data scanned for time-range queries.

Q: How does database sharding work and what are its challenges?
A: Sharding horizontally partitions data across multiple database servers, with each shard holding a subset of rows based on a shard key like user ID or geographic region. This enables near-linear scalability since each shard handles only a fraction of total queries and storage. The shard key selection is critical: it should distribute data evenly and align with query patterns to avoid cross-shard queries. Challenges include cross-shard joins and transactions, which require distributed coordination and significantly impact performance. Resharding when data distribution becomes uneven is operationally complex, often requiring data migration with minimal downtime. Application complexity increases as code must route queries to correct shards and handle shard failures. Consider alternatives like read replicas or vertical scaling before committing to sharding, as the operational overhead is substantial.

Q: What is database replication and what are the common replication topologies?
A: Database replication copies data from a primary server to one or more replica servers, providing high availability, disaster recovery, and read scaling. Synchronous replication waits for replicas to confirm writes before committing, ensuring zero data loss but adding latency. Asynchronous replication commits immediately and propagates changes later, offering better performance but risking data loss if the primary fails before replication completes. Primary-replica topology sends all writes to one server while replicas handle reads, simple but creating a single point of failure for writes. Multi-primary replication allows writes to any node but requires conflict resolution for concurrent updates to the same data. Chain replication passes writes through a sequence of nodes, while circular replication creates a ring topology. The choice depends on latency tolerance, consistency requirements, and geographic distribution needs.

Q: How do database transactions prevent concurrent access issues?
A: Transactions use isolation levels and locking mechanisms to prevent concurrent access problems like dirty reads, non-repeatable reads, and phantom reads. Read Uncommitted allows seeing uncommitted changes from other transactions, offering maximum concurrency but risking data inconsistency. Read Committed prevents dirty reads by only showing committed data, but the same query might return different results within a transaction. Repeatable Read ensures consistent reads within a transaction by locking read rows, preventing non-repeatable reads but not phantom reads from new insertions. Serializable provides complete isolation by making transactions appear sequential, preventing all anomalies but significantly reducing concurrency. Databases implement these through pessimistic locking that acquires locks before access, or optimistic concurrency control that validates at commit time and retries on conflicts. Choosing the right isolation level balances data consistency needs against performance requirements.

Q: What is the CAP theorem and how does it affect distributed database design?
A: The CAP theorem states that distributed systems can guarantee at most two of three properties: Consistency, Availability, and Partition tolerance. Consistency means all nodes see the same data simultaneously, Availability means every request receives a response, and Partition tolerance means the system continues operating despite network failures between nodes. Since network partitions are inevitable in distributed systems, the practical choice is between CP and AP systems. CP systems like traditional SQL databases sacrifice availability during partitions to maintain consistency, refusing requests rather than returning stale data. AP systems like Cassandra prioritize availability, allowing nodes to serve potentially inconsistent data during partitions and reconciling later. Many modern databases offer tunable consistency, letting you choose the trade-off per operation. Understanding CAP helps select the right database for your consistency and availability requirements.

Q: What are the best practices for database connection pooling?
A: Connection pooling maintains a cache of database connections that can be reused across requests, avoiding the overhead of establishing new connections for each query. Set pool size based on your database server capacity and application concurrency; too few connections create bottlenecks while too many overwhelm the database. A common formula is connections = ((core_count * 2) + effective_spindle_count) for the database server, then distribute across application instances. Implement connection validation to detect and remove stale connections, using lightweight validation queries or TCP keepalive. Set appropriate timeouts: connection timeout for acquiring from pool, idle timeout for releasing unused connections, and maximum lifetime to prevent issues from long-lived connections. Monitor pool metrics like wait times, active connections, and pool exhaustion events to tune configuration. Consider separate pools for different workloads, such as transactional operations versus reporting queries, to prevent one from starving the other.

Q: How do you design an effective database backup and recovery strategy?
A: An effective backup strategy combines full backups, incremental backups, and transaction log backups based on recovery point objectives (RPO) and recovery time objectives (RTO). Full backups capture the entire database but are time and storage intensive, typically scheduled weekly or during low-activity periods. Incremental backups capture only changes since the last backup, reducing backup windows and storage while requiring full backup plus all incrementals for recovery. Transaction log backups enable point-in-time recovery and should run frequently, often every 15 minutes for critical systems, with logs shipped to separate storage. Test recovery procedures regularly; backups are worthless if restoration fails when needed. Store backups across multiple locations and media types, following the 3-2-1 rule: three copies, two different storage types, one offsite. Document and automate the recovery process, including steps for different failure scenarios like hardware failure, corruption, or accidental deletion.

Q: What is eventual consistency and when is it appropriate?
A: Eventual consistency is a consistency model where updates propagate asynchronously across distributed nodes, guaranteeing that all replicas will converge to the same state given sufficient time without new updates. This differs from strong consistency where reads always return the most recent write, regardless of which node handles the request. Eventual consistency enables higher availability and lower latency in distributed systems since nodes can respond without coordinating with others. It suits use cases where temporary inconsistency is acceptable, such as social media feeds, product catalogs, or analytics data where slightly stale reads cause no harm. Techniques like read-your-writes consistency, monotonic reads, and conflict resolution through vector clocks or CRDTs can provide stronger guarantees within eventual consistency. Avoid eventual consistency for financial transactions, inventory systems with oversell risk, or any domain where inconsistent reads could cause business logic errors or compliance issues.

Q: How do you handle schema migrations in production databases?
A: Production schema migrations require careful planning to avoid downtime, data loss, and application errors during deployment. Use version-controlled migration files that apply changes incrementally, tools like Flyway, Liquibase, or framework-specific migrations track which changes have been applied. Prefer backward-compatible changes: add nullable columns, create new tables, or add indexes; avoid renaming or dropping columns during high-traffic periods. For complex changes, use expand-contract pattern: first expand the schema to support both old and new formats, migrate data and update application code, then contract by removing old structures. Test migrations against production-sized datasets in staging environments to catch performance issues and estimate execution time. Schedule potentially slow migrations during maintenance windows and monitor lock contention. Consider online schema change tools like pt-online-schema-change or gh-ost for MySQL that copy data to modified tables without blocking writes.

Q: What are materialized views and when should you use them?
A: Materialized views store the precomputed results of complex queries as physical tables, trading storage space and maintenance overhead for dramatically faster read performance. Unlike regular views that execute their defining query each time, materialized views return stored results instantly, making them ideal for expensive aggregations, complex joins, or frequently accessed reports. They are particularly valuable when underlying data changes infrequently relative to read frequency, such as daily sales summaries or monthly analytics dashboards. Refresh strategies include complete refresh that rebuilds entirely, incremental refresh that applies only changes, and on-commit refresh that updates immediately after source changes. Choose refresh frequency based on staleness tolerance and refresh cost; real-time needs might require triggers or change data capture instead. Consider materialized views when you have repetitive complex queries causing performance issues, but ensure you have processes to monitor and maintain them as source schemas evolve.

Q: What is write-ahead logging and how does it ensure durability?
A: Write-ahead logging (WAL) is a technique where changes are first recorded in a sequential log file before being applied to the actual data pages, ensuring durability and enabling crash recovery. When a transaction commits, the database writes log records describing the changes to disk before acknowledging success; if the system crashes, the log can replay committed transactions and undo uncommitted ones during recovery. WAL improves performance because sequential log writes are faster than random data page writes, and dirty pages can be flushed to disk lazily in the background. The log sequence number (LSN) tracks which log records have been applied, allowing the database to know its recovery starting point. Checkpoints periodically force dirty pages to disk and record a recovery point, limiting how much log must be replayed after a crash. WAL also enables features like point-in-time recovery and replication by shipping log records to replica servers. Understanding WAL helps with capacity planning since logs require separate high-performance storage and must be sized for peak write workloads.
